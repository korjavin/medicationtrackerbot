## 2025-03-08 - [Insecure Direct Object Reference (IDOR) via Server-Level User ID]
**Vulnerability:** The workout endpoints in `internal/server/workout_handlers.go` and `internal/server/workout_adhoc_handlers.go` were using the server-level configured `s.allowedUserID` to fetch and modify data instead of the user ID verified by the authentication middleware and stored in the request context (`r.Context().Value(UserCtxKey).(*TelegramUser).ID`).
**Learning:** While the application is currently designed as a single-user bot where `s.allowedUserID` and the authenticated user ID are often the same, relying on global or server-wide state for authorization completely bypasses the auth middleware's protections. If multi-user support were added in the future, this pattern would immediately result in widespread IDOR vulnerabilities, allowing any authenticated user to read/write the single configured user's workout data. It's a critical security boundary failure between the authentication layer and the resource access layer.
**Prevention:** Always extract user identification and authorization claims directly from the verified request context populated by the authentication middleware. Never rely on server-level configuration variables to identify the currently acting user.
