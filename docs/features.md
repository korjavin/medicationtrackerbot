# Feature Implementation Patterns

## Today Dashboard

Read-only landing surface (`web/static/js/features/today.js`, `window.TodayDashboard`). The unconditional home view on every cold start — `features/bootstrap.js` always calls `switchTab('today')` after auth. Section views (BP, Weight, Meds, Workouts, Food, Health (labelled "Vitals" in the bottom nav), Settings) are reached via the bottom nav, card deep-links, or URL hash / `tgWebAppStartParam`.

**DOM skeleton** (`#today-content` render order, via `features/today.js`):

1. `.wg-today-shortcuts` — up to 5-tile row: Log food / Scan food / Photo meal / Add BP / Add weight. Most tiles open the **existing** styled modal directly (`window.showAddFoodModal` / `window.showBPRecordModal` / `window.showWeightModal`) rather than navigating to the feature screen. The "Photo meal" tile (camera icon, rendered alongside "Log food" only when the food feature is enabled) calls `window.FoodActions.triggerPhotoPicker()` to open the system file/camera picker directly — no Food-section navigation, and the upload routes into the same in-app summary card flow as the in-section Photo button (see Food Tracking). The "Scan food" tile (barcode icon, also gated on the food feature) opens the Add Food modal and immediately launches the barcode scanner overlay, collapsing the previous 3-tap scan flow into a single tap.
2. `.wg-today-metrics` — 2-tile grid: BP tile (value + unit + status tag + sparkline, deeplinks to `bp`) and Weight tile (kg + delta tag + sparkline, deeplinks to `weight`). No SpO2 or HR tiles on Today.
3. `.wg-fuel-card.wg-today-food` — clickable food card: mono kcal display + "% of target" + 4 `WGMacroBar` rows (Energy / Protein / Carbs / Fat).
4. `.wg-today-wo-sleep` — 2-tile grid: Workout (name + group/time) and Sleep (duration + range).
5. `.wg-today-meds` — plain card (no sun-yellow background banner): header row with icon tile + "Next · HH:MM · in X" label + "Take" gloss-sun button that opens `#med-confirm-modal`; divider; vertical list of upcoming meds (sun-dot + name).

**Aggregation contract** — `aggregateToday(bootstrap, swrCaches, now)` is pure and synchronous; `Date.now()` is injected for testability. Returns a flat object where each field is `{ value, deeplink, status }`. Status values:

- `ok` — data present and fresh
- `missing` — feature enabled, no data yet
- `stale` — cached data older than its freshness threshold (BP: 24h, weight: 7d, sleep: 2d; the 1h `FRESHNESS_MS` constant only gates the offline-banner trigger via `isOfflineStale`)
- `overdue` — scheduled event passed without action (5-min grace period for `nextMed`)
- `disabled` — feature disabled; renderer omits the card entirely

**Fields and deep-link targets**:

| Field | Source | Deeplink |
|-------|--------|----------|
| `greeting` | local hour (good morning/afternoon/evening/night) | — |
| `nextMed` | `bootstrap.next_intake` | `meds` |
| `bpLatest`, `bpTrend7d` | `bootstrap.bp.readings` (7-day anchors) | `bp` |
| `weightLatest`, `weightTrend7d` | `bootstrap.weight.logs` (7-day anchors) | `weight` |
| `caloriesToday`, `caloriesTarget` | SWR `food_today` cache + `settings_bundle` food_targets | `food` |
| `macrosToday`, `macrosTarget` | SWR `food_today` cache + `settings_bundle` food_targets | `food` |
| `nextWorkout` | SWR `workout_next` cache | `workouts` |
| `sleepLastNight` | SWR `health_overview.sleep_stats_7d` (most recent) | `health` |

`loadToday()` (app.js) reads these caches via `ApiCache.getWithMeta` for `settings_bundle`, `next_intake`, `bp`, `weight`, `workout_next`, `health_overview`, and today's food key (`food_YYYY-MM-DD_day`).

**Data sources**: no new backend endpoints in Phase 1 — everything reads from `/api/bootstrap` and the existing SWR caches in `data-store.js`. A Phase 2 `GET /api/today` server-side aggregate is deferred.

**Live updates**: `TodayDashboard.subscribe()` re-renders on `BOOTSTRAP_UPDATED` `postMessage` from the SW (skipped in the subscriber; the app-level handler already reloads the current tab) and on `online` / `offline` window events and `datastore:changed` CustomEvent. `isOfflineStale({ online, cacheTimestamp, now })` toggles the dashboard's offline banner when cached data exceeds 1h while offline.

**Trend arrows**: 7-day trend computed from two SWR-cached anchors (oldest within the 7-day window and most recent). Fewer than 2 usable samples → status becomes `missing`. A `flat` direction (delta within ~0.5% of the anchor magnitude) renders `7d flat` without a signed number.

## Medication Tracking

- **Sub-tabs**: History (default — day-grouped intake log with med + day-range filters and offline/rejected badges), Schedule (hour-grouped dose list with next-action card on top), Upcoming (the read-only 7-day forecast, bd med-4oxj), Inventory (per-medication stock with low-stock alerts and Refill button that posts to `/api/medications/{id}/restock`). The "+ Add" medication button (`#add-btn`, `.wg-toolbar-btn .wg-toolbar-btn--primary`) lives inside a `.wg-meds-schedule-header` wrapper at the top of the Schedule tab only (round-2 Task 7) — it is hidden on History, Upcoming and Inventory. Sub-tab state persists under `mt-meds-subtab` in `sessionStorage` (default `history`, round-2 Task 4); legacy `localStorage` values are purged on module load. On the History tab, the "Next scheduled intake" pane (`.wg-meds-next-intake-card` with a `.wg-toolbar-btn--primary` "Take Now" CTA, round-2 Task 8) renders as the first block above the MEDICATION / RANGE filter row.
- **Un-marking a taken med** (History tab): opening a grouped `✅ Taken` intake and un-checking a med posts a `PENDING` revert to `POST /api/intakes/update`; on success the row flips back to `⏳ Pending`. Partial failures are now surfaced rather than swallowed — the handler returns a per-update `{updated, failed, failures}` body, and the frontend only shows "Updated!" + commits the optimistic flip when every update persisted. If any update fails, it rolls back the affected rows and shows an error naming the failed med(s) instead of a false "Updated!". See [api.md → `/api/intakes/update`](archive/api.md#health-data).
- **Schedule order**: hour-of-next-dose buckets (each under a `HH:MM · in Xh Ym` section label, earliest first) → `Scheduled` fallback for entries with no computable next dose → `As needed` → `Archived`. Entries within a bucket are sorted by next-dose time (fallback buckets by most-recent intake). The 7-day forecast used to sit between `Scheduled` and `As needed`; it is now the Upcoming sub-tab (bd med-4oxj).
- **Schedule bucketing is plan-aware** (bd med-gut.1): the bucket times come from `GET /api/medications/upcoming?days=7`, which runs the same engine as Home's next-intake card (`web/domain/medintake.js` → `planDosesWithTzPlan`), so the tracked IANA timezone, an approved tz transition plan, start/end dates and legacy `"HH:MM"` schedule strings are all honoured and the two screens cannot disagree. Each row carries its wall-clock `local_date` / `local_time` / `day_offset` in the tracked zone, so the renderer does no timezone math of its own. When the route is unavailable (offline cold start, or the legacy bot server, which does not implement it) the tab falls back to the device-local computation in `features/medication-utils.js`.
- **Upcoming sub-tab** (bd med-gut.2, promoted to its own pill in bd med-4oxj): a read-only `.wg-meds-upcoming` list in `#med-upcoming-tab`, sitting between Schedule and Inventory in the pill strip, showing the next 7 days of doses grouped by day in the tracked timezone (`Today` / `Tomorrow` / weekday). No section label inside the pane — the pill names it. Doses sourced from an approved tz transition plan's steps carry a `transition step N/M` `.wg-tag--mono` badge and show the step's own note (`tzplan.js` `buildNote`), which spells out the old-zone and new-zone clock times. No take/skip actions — the Today screen owns those. A forecast that answered with no doses renders a "no scheduled doses in the next 7 days" line, so an empty window is distinguishable from the feature not being there; a forecast that is *unavailable* (offline cold start / legacy bot server) renders nothing at all, because the device-local fallback is driving the Schedule buckets and any "nothing upcoming" claim would be unfounded. One fetch backs both views: `loadMeds()` still calls `loadUpcomingDoses()` for the Schedule buckets (bd med-gut.1) and repaints this pane off the same module state, and `switchMedTab('upcoming')` → `loadUpcoming()` re-fetches on tab entry.
- **Archiving & Deleting**: active medications can be archived; archived medications can be permanently deleted only if they have no intake history
- **Schedule Types**: Daily, Weekly, As-Needed with optional Start/End dates
- **Duplicate Prevention**: HTTP 409 on creation when name (case-insensitive) + dosage matches an existing medication (including archived)
- **Drug Interactions**: automatic checking via RxNorm API when adding/unarchiving
- **Notifications**: Telegram alerts with scheduled time and dosage; hourly retry if not confirmed
- **Timezone Shift Policy** (`tz_shift_policy`): per-medication field controlling how doses are rescheduled when the user's timezone changes. Values: `flexible` (default — shift immediately in one step), `medium` (gradual, max 3h per dose), `strict` (very gradual, max 2h per step). When a timezone change is detected and an active plan is approved, the scheduler uses the plan's transition steps instead of normal schedule times until all steps are consumed.

## Blood Pressure Tracking

- **Classification**: ISH 2020 guidelines (configurable for age <65)
- **Target**: <130/80 mmHg
- **Tracking**: 2–3x daily recommended
- **Statistics**: daily-weighted averaging — each day with readings gets equal weight regardless of measurement count (prevents frequency bias). Day boundaries use the user's stored timezone (falls back to UTC).
- **UI layout**: the "+ Log" BP button renders **inline** with the range selector (14d / 30d / 60d, **default `14d`**) inside `.wg-bp-range-selector__track`, not as a floating FAB. `#add-bp-btn` is a `.wg-toolbar-btn .wg-toolbar-btn--primary` pill (round-2 Task 5) that re-renders with the range selector. The initial fetch still hits `/api/bp?days=60` so 30- and 60-day averages stay available client-side; active-range filtering happens in `filterReadingsByRange`. The chart emits numeric y-axis mmHg ticks ({60, 80, 100, 120, 140, 160, 180} ladder, clamped to range) and x-axis date ticks; the `bp-current-card` top summary pane was removed in round-2 Task 2.
- **Export**: CSV

## Weight Tracking

- **UI layout** (Wandergeek Phase 6; round-2 Task 12): `#weight-view` opens with the optional goal card (hidden when no goal is set, progress bar when shown), followed by the range-selector row. The range-selector row is a flex track containing the `7d / 30d / 90d / All` pills (persisted via `mt-weight-range`, default `30d`) plus the `+ Log` button (`#add-weight-btn`, `.wg-toolbar-btn .wg-toolbar-btn--primary`) pinned to the right. Below the selector: the `WGWeightChart` panel — whose card surface, guide lines, and axis ticks consume the shared `--wg-chart-*` tokens so it stays visually flush with the BP chart (round-2 Task 13). The chart renders numeric y-axis kg ticks, first/last x-axis date ticks, a dashed `GOAL · {value} kg` horizontal line, a "plan trajectory" line from the first actual log to the goal at the last data point, the actual-weight spline, and a dashed 14-point regression "trend" line. A chart legend (Actual / Plan / Goal) mounts in `#weight-chart-legend` below the chart. A goal-prognosis card (`#weight-prognosis-card`) shows `Time to goal` ("in N days" when the trend points toward the goal and is ≥0.05 kg/week, "At goal" within 0.05 kg of the goal, or "—" when trend is flat or points away) and `Trend` as ±N.N kg/week with a good/bad/flat variant class. All numeric outputs are NaN/Infinity-guarded and fall back to "—". A day-grouped history list sits at the bottom; there is no bottom CTA. The previous "Latest" current-weight pane (`.wg-weight-header-row` + `.wg-weight-current-card`) was removed in round-2 Task 12; the chart is the first visual after the goal card.
- **Edit modal**: kg/lb unit toggle (replaces the paper-era drag ruler). Editing an existing entry deletes the original and POSTs the replacement because the backend has no PATCH route for `/api/weight`.
- **Unit preference**: each user has a preferred weight unit (`kg` or `lb`) stored on the singleton `settings` table (column `weight_unit_preference`, default `kg`). Storage is always in kg; the preference only affects input default and display in the web app and bot replies. The preference is bumped to whichever unit the user last chose: submitting the modal in lb, sending `/weight 150lb`, or flipping the Settings segmented control all PATCH `/api/settings/weight-unit`. The bot's `/weight` command parses trailing `kg` / `lb` / `lbs` / `pound(s)` (case-insensitive); a bare number uses the saved preference. The reply confirms in the user's unit with kg in parentheses (e.g. `Weight recorded: 154.3 lb (70.0 kg)`). The MCP contract is unaffected — `get_weight` and `analyze_fitness` always return `_kg`-suffixed fields regardless of preference.
- **Trend**: exponential moving average for smooth visualization
- **Export**: CSV in Libra format (compatible with Libra app)
- **Reminders**: weekly if no weight logged

## Food Tracking

- **UI layout**: no outer sub-tab strip. `#food-view` opens directly on the daily log — the day navigator sits at the top with an inline `#add-food-inline-btn` sun-gloss "+ Add" pill; below it, the macros card (`#food-macros-card`) carries an in-card Daily / Weekly segmented toggle. Daily shows today's totals; Weekly shows the 7-day total plus an "avg N kcal/day · 7d" subtitle. The meal list stays daily regardless of the toggle. A `.wg-food-subtabs` pill strip at the top of `#food-view` switches between two panes — **Log** (default, `#food-log-tab`: day navigator + macros card + meal list) and **Food DB** (`#food-fooddb-tab`: searchable/sortable product catalogue). The meal-template surface (My Meals pane, save-as-meal modal, log multi-select) was removed in med-ejq.3; `is_meal` products still exist server-side, still rank first in food search, and still autofill their total weight when picked. Round-2 Task 3 removed the sticky `.wg-food-cta-dock` at the bottom of `#food-log-tab`; the inline header `+ Add` is now the sole Add-food entry point.
- **Manual logging**: web UI (Open Food Facts search) and multi-item "Meals" templates with aggregated macros
- **Barcode**: `#food-modal` supports barcode auto-lookup (type into `#food-barcode`) and camera scanning via `#food-scanner-modal` (`#food-scan-btn` opens the camera, "Use Photo" decodes a picked image)
- **Photo-to-meal (AI vision)**: the inline header `#add-food-photo-btn` (sun-yellow `wg-toolbar-btn--primary` with a runtime-injected camera SVG) and the Today `Photo meal` shortcut both fire the hidden `#food-photo-input` picker, which uploads to `POST /api/food/log/from-photo`. The handler returns one `{id, name, weight, carbs, protein, fat, calories}` row per parsed item plus an optional `failed` reason. On success the frontend mounts an in-app summary card (`web/static/js/features/food-photo-summary.js` → `showFoodPhotoSummary`) that floats above the bottom nav, listing each item with weight + kcal, a totals row, and an Undo button. Undo issues parallel `DELETE /api/food/log/{id}` for every just-logged item, then swaps the card to a brief "Removed N items" confirmation; partial failures surface a retry state inside the card. The card auto-dismisses after ~8s, has an explicit close button, and never blocks the page (no `alert()`). The picker and its change handler are bound at `DOMContentLoaded` so the Today shortcut works on a cold session without first visiting the Food section.
- **Parse with AI (web text)**: the `#food-modal` carries a `#food-parse-ai` checkbox ("Parse my meal from a description") that toggles `.wg-food-modal--ai-mode` on the modal root. In AI mode the weight/barcode/macros/per-100g rows are CSS-hidden, the `#food-name` field is repurposed as a multi-line "Describe your meal" input, autocomplete is suppressed, and Save POSTs `{description, eaten_at}` to `POST /api/food/log/from-description` — a thin parse-and-save endpoint that calls `domain.FoodAIService.ParseMealDescription` and writes one `food_log` row per parsed item (mirroring the bot `/food` command). The response feeds the same `showFoodPhotoSummary` card + per-item Undo affordance used by the photo flow; the shared undo helper lives in `web/static/js/features/food/ai-undo.js` (`undoFoodAIItems`). Manual entry is unchanged when the checkbox is off.
- **`/food` Telegram command**: natural-language meal logging via AI. The AI splits complex meals into atomic items (one row per distinct food/ingredient) and normalizes dish names to common English terms regardless of input language (e.g., Russian "куриная грудка с рисом" → two items named "chicken breast" and "rice"). Each item becomes its own `food_log` row sharing the same `eaten_at` timestamp. The bot replies with a per-item breakdown plus an aggregate total. On partial failure, remaining items still persist and the reply reports "Logged N of M items".
- **Telegram photo food logging** (`internal/bot/photo_food.go`): any photo sent to the bot is treated as a food photo and routed to `FoodAIService.ParseMealPhoto` (the same domain method that backs the web `POST /api/food/log/from-photo` flow). The largest `PhotoSize` is downloaded via `b.api.GetFile`, capped at 8 MB and MIME-sniffed before the AI call. EXIF `DateTimeOriginal` is parsed in-process by `parseExifDateTimeOriginal` (no third-party EXIF dep — a small `encoding/binary` walk of APP1 → IFD0 → ExifIFD → tag `0x9003`, with optional tag `0x9011` `OffsetTimeOriginal` for the timezone). If the EXIF time is more than 1 hour older than now, the bot caches the image bytes in `pendingPhotoStore` (10-minute TTL, crypto-random hex token) and replies with two inline buttons (`food_photo_time:exif:<token>` / `food_photo_time:now:<token>`); if EXIF is within 1 hour, the bot uses the EXIF capture time directly so the `food_log` row matches when the user ate (mirroring `resolveFoodPhotoEatenAt` in `web/static/js/features/food.js:1003`); if there is no EXIF at all, the bot falls back to `time.Now()`. The time-picker callback re-checks `GetFoodIntakeEnabled` before saving so a flag flip during the 10-minute window can't slip past the gate. Each parsed item becomes its own `food_log` row sharing one `eaten_at`. The reply uses the same `renderFoodSummary` as `/food`, with an inline `[Undo]` button (callback `food_photo_undo:<token>`); the batch is stored in `undoBatchStore` and a `time.AfterFunc(5*time.Second)` strips the keyboard after the window closes. Undo deletes every row in the batch via `food.DeleteFoodLog` and edits the message to append "↩️ Undone". Feature is gated by `GetFoodIntakeEnabled` and silently no-ops when `foodAI` is unconfigured (clean error message, no panic). No new HTTP routes, no new env vars, no new migrations.
- **MCP agent workflow (search-first reuse)**: agents using `mcp_execute` should call `food.products.search` (or `food.products.frequent` for the user's most-logged items) before `food.log.create` and pass the matching `product_id` so reused meals roll up under the same `food_products` row. When only `name` is provided, both the modern `/api/food/log` handler and the legacy HMAC `/api/mcp-food-log` endpoint upsert a `food_products` entry by `(user_id, name)` and bump its `usage_count`. The `food.log.create` response carries `{status, id, product_id, name}`, where `product_id` is the resolved or freshly-upserted product id (null only when no name was provided). The `food` topic in `mcp_help` and the `python/examples/food_log.py` example both demonstrate this contract.

## Workout Tracking

- **Naming** (med-prk.3, implements the `docs/design/2026-07-11-workouts-ia.md` IA rework): user-facing labels are **"Plan"** (was "Group") and **"Day"** (was "Variant"), and the schedule copy reads **"Repeats on"** (was "days of week"). This is a relabel of rendered strings only — internal ids, `data-tab="groups"` values, the `mt-workouts-subtab` localStorage key, `is_rotating` / `rotation_order` / `days_of_week` fields, and DB columns are unchanged (same relabel-keep-the-id precedent as the Vitals nav slot). A newly created Plan defaults to a single flat exercise list with no Day/rotation UI; the auto-created hidden variant is never labeled. Rotation is an explicit "Rotate through days" opt-in, and turning it off is blocked while the Plan still has more than one Day.
- **UI layout** (Wandergeek Phase 7; round-2 Tasks 6/10/11): four sub-tabs (History / Plans / Exercises / Stats) persisted via `mt-workouts-subtab` (default `history`); History surfaces a day-grouped session list with per-row view/edit/delete actions, Plans and Exercises sub-tabs render as `.wg-card` lists. The Exercises tab carries a `.wg-workouts-exercises-header` row with a "Library" label on the left and the `#add-exercise-library-btn` sun-gloss pill on the right (the full-width bottom "+ Add exercise" CTA was removed in round-2 Task 6). Stats renders a view toggle (Consistency / Load / Balance, persisted via `mt-workouts-stats-view` — see [Stats views](#stats-views-med-904)) above a 7d/30d/90d/All range selector (persisted via `mt-workouts-stats-range`). Consistency draws an activity calendar over the range; Load draws a `WGWorkoutChart` weekly-tonnage bar chart with numeric y-axis ticks and 4 date ticks across the visible window, under a `.wg-workouts-stats__legend` chip row ("Volume · per week") so future multi-series charts slot into the same legend. The range selector drives the whole tab, not just the chart: it rides along as `?range=` on `/api/workout/stats`, and the domain scopes the counts and Top Exercises to that window. Stats also shows a 2×2 stat-tile grid (Streak / Sessions / Done / Skipped) — Streak is `current_streak_weeks`, consecutive weeks holding ≥1 completed session (whole-history by design, and an untrained current week doesn't break it), Done is the completion rate — and a Top Exercises list. The "Ready to start" / "Next workout" card (`.wg-workouts-next-card`) uses the shared elevated-teal-card recipe with a `.wg-toolbar-btn--primary` action (Start Scheduled / View / Cancel Skip) and `.wg-toolbar-btn--secondary` outlines (Start AdHoc / Skip / Finish / Next Day); no emoji prefixes in labels or kickers. The ad-hoc start (med-2fc) is the **leftmost** action of that row in every status branch — there is no separate ad-hoc button anywhere on the screen — and when nothing is scheduled the card still renders, carrying `Start AdHoc` alone so the entry point never moves. Exercise rows inside the Edit Day modal (`.wg-workouts-exercise-row`) carry a token-only dark-surface recipe (round-2 Task 11). The session-detail modal's header is **pinned** (`position: sticky` against `.wg-modal`, which is itself the scroll container) because the exercise list rarely fits one screen: it carries the session identity — slot tag · date · weekday · status, injected by `renderWorkoutSessionHeader` — plus the only "+ Exercise" entry point and an icon-only Close. The body no longer repeats the identity above the first exercise card, and the bottom action row is Finish workout alone.
- **Hierarchy** (UI labels; internal ids in parens): Plans → Days → Exercises (`groups` → `variants` → `exercises`)
- **Exercise library by reference** (med-prk.2): `exercise_library` is the single source of truth for exercise names. Each `workout_exercises` plan row carries a nullable `exercise_library_id` FK; reads resolve the display name through it via `COALESCE(el.name, we.exercise_name)`, falling back to the denormalized `exercise_name` cache when the FK is null. Consequence: **renaming a library exercise renames it in plans too** (surfaced in the library edit modal copy). Past session history keeps its point-in-time `exercise_name` snapshot and is not rewritten by a rename. Create/update dedupe by name into the library (`UNIQUE(user_id,name)` + `ON CONFLICT DO NOTHING`), so the same name twice = one library row. Mirrored in cloud mode by `web/domain/workout.js` (`promoteExerciseToLibrary` → `toExerciseResponse` resolve-on-read), with a one-time idempotent boot backfill in `web/cloud/js/cloud-boot.js`. Cross-mode parity is guarded by `TestExerciseLibraryReference_CreateDedupeRename` (Go) + `cloud.shim-contract.workout-crud.test.js` (shim). This makes the Exercises tab / library the canonical exercise set by construction — closes med-spp.
- **Non-destructive session history** (med-qj4.2.1, cloud domain): a completed session is an immutable record of the plan *as performed*. On completion, `completeSession` (`web/domain/workout.js`) snapshots the variant's exercise list + targets into an additive `exercise_snapshot` field on the session record — `[{ exercise_id, exercise_name, target_sets, target_reps_min, target_reps_max, target_weight_kg, order_index }]` — written only for real variants (ad-hoc `variant_id === -1` is skipped; it renders from logs alone), and only when absent so a repeat completed-status call can't rewrite the immutable record. Readers **prefer the snapshot, else fall back to the live variant**: `listSessions` counts `exercises_count` from `exercise_snapshot.length` when present, and the session modal (`web/static/js/features/workout/sessions.js`) builds the planned/un-logged rows from the snapshot (deduping logged rows by `exercise_id` when the row has one — so a plan carrying the same exercise name twice keeps both un-logged rows — else by `exercise_name` for legacy id-less rows) instead of re-fetching `/api/workout/exercises?variant_id=…`. Each snapshot row carries its `exercise_id` so editing an un-logged planned row can save a `logs/create`. Effect: editing a variant's exercises/targets or renaming a library exercise no longer retroactively rewrites past sessions. The field is optional, so legacy + in-flight sessions with no snapshot keep today's live-variant behavior. No migration/route/catalog/sync change — it's an opaque field on the vault session blob (and, being write-only history, is excluded from vault export like other workout schedule snapshots). Guarded by `cloud.shim-contract.workout-sessions.test.js` + `features.workout-sessions.test.js`.
- **Print a plan** (med-ac5h): each Plans-sub-tab row carries a Print icon button that builds one standalone A4 sheet — Plan name, training goal, "Repeats on Mon, Wed, Fri · 18:00", each Day in `rotation_order` with its exercises in `order_index` (`sets × reps[-range] [@ weight]` in the user's kg/lb preference), and an empty box per target set to fill in by hand at the gym. A flat Plan prints with no Day heading (the auto-created hidden variant is never labeled). Built entirely in the browser from the existing `/api/workout/{variants,exercises}` reads and printed through `web/cloud/js/print-doc.js`'s offscreen iframe — the same path as the doctor brief, so nothing leaves the device and the sheet is black-on-white regardless of theme. One-page fit is CSS only (A4, two columns of Day blocks that never break mid-block); a very large Plan legitimately runs to a second sheet and the browser's own print dialog offers scaling.
- **Rotation**: automatic A/B/C/D progression (e.g., PPL, PHUL splits)
- **Scheduling**: configurable days of week, notification advance time (default 15 min)
- **Scheduled ad-hoc workouts (MCP-only creation)**: a one-off workout for a future date/time can be created via the `workouts.sessions.schedule` MCP operation (`POST /api/workout/sessions/schedule`). The operation takes `scheduled_date` (YYYY-MM-DD), `scheduled_time` (HH:MM, 24h), and an `exercises[]` list with `target_sets`, `target_reps_min`, optional `target_reps_max` / `target_weight_kg`, and either a library `exercise_id` or a free-form `exercise_name`. The result is a pending session with `group_id = -1` / `variant_id = -1` and one pending `workout_exercise_logs` row per planned exercise. The scheduler notifies the user at the scheduled local time (no rotation, no cross-TZ cooldown); execution at workout time reuses the standard `workouts.sessions.start` and `workouts.sessions.logs.update` flow, finalized with `workouts.sessions.status` (`status="completed"`) — without that final status flip the session row stays `in_progress` and the scheduler treats it as stale (notifies after 90 min, auto-skips after 4 h). There is no web UI for creation; cancellation is via `workouts.sessions.delete`. Editing a scheduled session and recurring scheduled ad-hoc are out of scope.
- **Snooze**: 1-hour or 2-hour options
- **Logging**: exercise-by-exercise with sets, reps, weight
- **Weight/Reps Propagation**: when a user logs or edits exercise weight/reps/sets in a pending/notified/in-progress session, the new values propagate back to the `workout_exercises` schedule definition (best-effort, errors logged but don't fail the request). Only applies to exercises belonging to the session's variant — user-added and ad-hoc session exercises are excluded.
- **Prompt Batching**: at most 3 exercise prompts shown at once; remaining queued in-memory (`pendingExercises` map on Bot struct) and sent one-at-a-time as user completes/skips

### Stats views (med-904)

Stats carries **two** stacked segmented strips: a view toggle above the 7d/30d/90d/All range strip. The range strip owns the fetch; the view toggle never refetches — one `/api/workout/stats` response feeds all three views, and switching is a client-side re-render (cloud mode is all-local, so a refetch would be pure latency for nothing). The active view persists via `mt-workouts-stats-view` (default `consistency`), the same way the range persists via `mt-workouts-stats-range`. The range applies to all three views.

- **Consistency** (default) — *did I show up*. A GitHub-contribution-style **activity calendar** (`.wg-workouts-stats__calendar`) over the active range: N week rows × 7 weekday columns (Mon…Sun), **newest week on top**, one cell per day, one weekday initial per column (M T W T F S S) as a header row and no month row. **med-djsa.1 transposed it**: GitHub's 7-rows-×-N-columns orientation ran time along the phone's narrow axis, so `range=all` either squeezed the cells to the 11px floor or scrolled sideways. Weeks-as-rows puts time on the long, natively scrollable axis and the 7-wide axis always fits; newest-first so the week you act on sits under the pills and history reads as scroll-down. Then Streak / Sessions / Done / Skipped tiles and Top Exercises. **med-zte replaced the sessions-per-week line chart with the grid** — a 2-vs-3-sessions line is jagged noise, while a row read horizontally *is* that week's session count, so the calendar strictly contains the line's information and adds which days you trained. Cells shade by session **status** — completed (sun fill) / skipped (muted outline) / nothing logged (faint) — never by volume, because a bodyweight session logs zero tonnage and would render as a rest day. A day holding both a completed and a skipped session reads as completed. Each cell carries a `date · what happened` tooltip and the grid carries one summarizing `role="img"` aria-label. The grid is capped at **26 week rows** (~6 months) so `range=all` on a long history stays one comfortable scroll rather than pushing the tiles two screens down. **Cells are fluid** (med-iyu): the grid takes the card's width and splits it seven ways, bounded by `--wg-workouts-calendar-cell-{min,max}` — the max keeps 7 columns on a wide card from inflating into wall-sized squares (`aspect-ratio` makes width height), and the header row shares the grid's template and width bound so each initial sits over its column. Nothing overflows horizontally any more. Note that 7d is **two rows by construction**. The body-part split moved out entirely: the Balance view owns it, and rendering it in both was duplication.
- **Load** — *how much work did I do*. Volume / Hard sets / Reps / PRs tiles over the range, a weekly-tonnage **bar** chart (`WGWorkoutChart` in `metric: 'volume', variant: 'bars'` mode fed from `weekly_volume`), and the volume-sorted exercise list. med-zte swapped the line for bars: weekly tonnage is a set of discrete buckets, and a spline through them implies a continuous quantity that was never measured between Mondays. The bars variant forces a **zero baseline** (a truncated axis would make a 900 kg week look like a tenth of a 1000 kg one) and skips LTTB downsampling (a dropped bucket reads as an untrained week). The line stays the default variant, so exercise-detail's est-1RM / top-weight / reps charts are untouched. Warm-up sets count for nothing. The Hard sets tile names the rated-easy sets it excluded ("Hard sets · 3 easy", see below). Zero logged working sets — hard *or* easy — renders "No logged sets in this range" rather than a wall of empty tiles. Under the chart legend, med-djsa.5 adds the week-over-week caption (`.wg-workouts-stats__delta`): "Last week 12.3t · 18 hard sets · +23% vs the week before", folded in `stats.js` off `weekly_volume` — presentation tier, no domain field. It compares the last two **complete** ISO weeks: the current Monday's bucket is partial until Sunday, and counting it would report a crash every Tuesday for someone training exactly as usual (the same honesty rule the hard-set band applies by using rolling 7-day windows). `weekly_volume` is sparse — an untrained week is *absent*, not a zero row — so when the Monday one week before the last complete one is missing (or its volume is 0) the caption keeps the line and drops the delta rather than dividing by zero; with no complete week at all it is omitted entirely.
- **Balance** — *what am I neglecting*. Sets per body part (folded from `exercise_totals` through the static exercise catalog, client-side), each row showing `N sets · X%`, plus a **"Not Trained"** chip row naming the catalog body parts with zero sets in the range. The absence list is the point: it's the JEFIT-BodyMap question ("what am I missing") that a top-N list structurally cannot answer. A catalog that fails to load skips the split rather than showing an all-uncategorized one.

  **med-904.3 appends two follow-ups below the split.** **Movement Balance** — `Pull : Push` and `Hinge : Squat` rows over the same working sets, the JEFIT Movement-Balance-Engine axis that Strong and Hevy both omit. The catalog carries body parts, not movement patterns, so `WorkoutExerciseCatalog.resolveMovementPattern` *derives* one from the exercise **name** (the name is what encodes the movement — "row" vs "press" — while a body part cannot tell a pull-up from a bench press), gated first on the body part having a pattern at all: core, calves, forearms, neck and cardio resolve to `null` rather than to a guess, and the leg rules are checked before the arm ones so "leg curl" is a hinge and "leg press" a squat. The rules also carry a vertical/horizontal `axis` where the movement has one; nothing renders it yet — it is what a hex radar would read. **Hard Sets · Last 7 Days** — the own-baseline band (see the API section), read out as "In your usual range" / "Below your usual" / "Above your usual" with the user's own `low–high`. The ratios sit behind the same guards as the split (same rows, same catalog); the band does **not** — it is whole-history, range-independent and catalog-free, so it renders even on the paths where the split says "no exercises logged" or "body-part catalog unavailable". Both sections say **"Keep logging to unlock…"** when there is nothing to fold yet: an empty state, not an error.

### Stats API (`/api/workout/stats`)

Returns `active_weeks` (count of weeks with at least one completed session), `total_sessions` (sum of completed and skipped), `current_streak_weeks`, `weekly_activity[]` and `top_exercises[]` (top 8 by volume), all scoped by `?range=` except the whole-history streak.

med-zte added `daily_activity[{date, completed, skipped}]` for the Consistency calendar: one entry per **local** calendar day inside the active range that saw a completed or skipped session, ascending by date. It is **sparse** — a rest day is simply absent, exactly like an untrained week in `weekly_activity` — and the calendar fills the gaps itself. Unlike `weekly_activity` (which keeps a wider ≥12-week heatmap span), `daily_activity` is scoped to the active range only, so the grid covers exactly the window the range pills claim. Like every other list on this response it is `null`, never `[]`, when the window holds nothing.

med-904.1 added the load aggregates on the same response: `totals{volume_kg, hard_sets, easy_sets, reps, pr_count}` over the range, `weekly_volume[{week, volume_kg, hard_sets, reps}]` sharing `weekly_activity`'s ISO-Monday buckets and wider ≥12-week span, and `exercise_totals[{exercise_name, session_count, sets, hard_sets, reps, total_volume_kg, max_weight_kg}]` covering **every** exercise trained in the range (not the top-8 slice — that's what lets Balance fold a complete body-part split). Sets marked `set_type: "warmup"` are excluded from all three. `pr_count` counts in-range logs whose heaviest working set beat every earlier log of the same exercise, including out-of-range history.

med-djsa.2 named those records: `prs[{exercise_name, date, weight_kg, previous_kg}]`, one entry per counted PR, **newest first**. `date` is the session's **local** calendar day (the `YYYY-MM-DD` prefix, same rule as `daily_activity`); `previous_kg` is the record that was broken, `0` for a first-ever weighted lift. Warm-up sets are excluded by the same `max_weight_kg` fold, so a warm-up-only log — and a zero-weight bodyweight one — can never set a weight PR. **Weight PRs only**: est-1RM and rep records stay in `web/domain/workout-analysis.js` and the per-exercise detail view rather than being re-derived here. Like every other list on this response it is `null`, never `[]`. The Load view renders it as a "Records · this range" list under the tiles and omits the section entirely when it is `null`.

med-904.3 added `hard_set_band{current, baseline, low, high, status}` — the user's **own** volume baseline (JEFIT's Stimulus Volume Engine / Strava's Relative Effort), so the Balance view can say "in range / below / above" instead of an absolute nobody can calibrate. `current` is the hard sets of the last 7 days; `baseline` averages the three 7-day windows before it; `low`/`high` are ±20% around it, floored and ceiled **outward** so a small baseline still leaves a band instead of collapsing to a point; `status` is `below` | `in_range` | `above`. **Rolling 7-day windows, not the ISO weeks `weekly_volume` buckets by** — a calendar week is partial until Sunday, so an ISO-week comparison would report "below" every Monday through Thursday for someone training exactly as much as always. It is `null` (never a zero band) until the vault holds at least four windows of history and the baseline is non-zero: a two-week-old account has no "usual" yet, and averaging a partial history would call every honest session "above". Like `current_streak_weeks` it is **range-independent**. Cloud-only: it is computed in `web/domain/workout.js`, and the legacy Go handler does not return it.

**A hard set is effort, not a set count (med-vov).** A working set counts toward `hard_sets` only when it was taken near failure — RIR ≤ `NEAR_FAILURE_RIR` (4), i.e. the logged per-set `rpe` ≥ 6. Per-set RPE is optional and rating only the top set is normal practice, so an **unrated working set still counts as hard** ("no opinion", never "too easy") — the same rule the progression RIR gate applies to `minRpe` — and a flat-scalar log, which carries no effort at all, keeps counting every set. `totals.easy_sets` reports the rated-but-easy working sets that were excluded, so the Load view labels the tile "Hard sets · 3 easy" instead of silently shrinking a number the user already saw. Volume and reps are unaffected: an easy set is still work done. One flat threshold for every exercise — goal-differentiated proximity is noted as an upgrade path in `web/domain/workout-goals.js`, not implemented.

**Effort and coverage are separate fields; read the one you mean.** `exercise_totals[].sets` is **coverage** — every working set, ungated, unchanged by med-vov — and `exercise_totals[].hard_sets` is the effort-gated twin alongside it. The Balance view folds coverage, because it prints the body parts with zero sets under **"Not Trained"**: gating that count on effort would tell a user who squatted three honest RPE-5 sets that they never trained legs, while a user who logs no RPE at all keeps getting the truth. Rating honestly must never produce falser data than not rating at all. `totals.hard_sets`, `totals.easy_sets` and `weekly_volume[].hard_sets` are the effort side, and the Load view is where effort belongs.

`top_exercises` is the top-8 slice of `exercise_totals` (med-7pq), so both views report the same volume for the same exercise. Before that it carried the pre-per-set derived-scalar product (stored set count × **max** reps × **max** weight, warm-ups included), which over-counted a realistic ramp roughly 3× — 40 kg×10 warm-up + 80 kg×5 + 85 kg×5 reported 2550 kg against a true 825 kg.

## Diary Notes

- **Backing table**: `diary_notes` (id, user_id, content, created_at, tag). The `tag` column is nullable — legacy rows stay NULL and the column was added by migration `054_add_diary_notes_tag.sql`.
- **Tag enum**: one of `SLEEP | STRESS | HR | SPO2 | STEPS | NOTE`, or NULL. The domain service (`internal/domain/notes.go` — `NotesService`) normalizes the tag on the way in: incoming values are upper-cased and matched against the 6-value enum; anything else is coerced to NULL so the handler returns `201` with the sanitized record rather than a `400`.
- **Frontend composer** (`#health-notes-tab`): `.wg-card.wg-health-notes-compose` with a "New note" mono label on the left and a horizontally-scrollable 6-chip radiogroup on the right (`SLEEP / STRESS / HR / SPO2 / STEPS / NOTE`). The active chip carries `.wg-tag--sun`; tapping the active chip again deselects it. Below the header sits a textarea + footer row with a live char count and a `.wg-gloss--sun` "+ Add note" button (disabled when empty). Submit POSTs `{content, tag}` to `/api/notes` (the `tag` field is omitted when no chip is selected), prepends the new row to the list, and clears the composer.
- **List rendering**: each note row shows a `.wg-tag--high.wg-health-notes-row__tag` pill with the tag label when `note.tag` is one of the 6 enum values; NULL and unknown values render no pill. Round-2 Task 5 made the tag pills clickable: tapping a row's chip filters the notes list to only rows carrying that tag and marks the chip `.wg-health-notes-row__tag--active`; tapping the active chip again clears the filter. Filter state is module-local (not persisted) and repaints from the in-memory `_notesAll` cache without refetching. Create/delete invalidates via `DataStore.invalidateTags(['health-notes'])` so Today tiles and other listeners refresh without reload.
- **Edit**: the legacy `#note-modal` still opens from a list row for editing an existing note's content (tag editing is not exposed in the edit modal yet — only the inline composer creates tagged rows).
- **Bot**: `/note` command (`internal/bot/note_commands.go`) routes through the domain service with `tag = nil` — the bot surface has no tag picker.

## Settings → Import/Export

- **One shared screen, both runtimes** (`web/static/js/features/settings/importexport.js`, hung off `loadSettings` like `SettingsIntegrations`; block `.wg-settings-importexport` in `index.html`). The **no-lock-in guarantee (C2e)**: your entire per-user dataset (meds + intake log, BP, weight, food, workouts, vitals, sleep, diary, full tz-plan history, reminder prefs + reminder state, gamification, API tokens, settings) exports to and imports from one canonical JSON file — the same format in bot/server mode and cloud mode. The vault is the seamless server-migration mechanism: `export → new server → import` reproduces the install, down to a previously-minted API token still authenticating. Format spec: [vault-format.md](vault-format.md).
- **Export**: "Download" produces `medtracker-vault-<date>.json`. Bot mode fetches `GET /api/export?include_secrets=1|0`; cloud mode builds it fully client-side (`window.CloudVault.exportAll({ includeSecrets })`, reading unmasked provider keys module-to-module — never over the `/api` shim). An optional passphrase field encrypts the file with **age** (scrypt recipient, binary `.age`, decryptable anywhere with `age -d`); the server never sees the passphrase. Leaving the passphrase blank shows a one-line nudge (the backup carries your provider API keys) but does not block.
- **"Include API keys and external provider settings"** — a checkbox, **checked by default**. Unchecked, the export omits `settings.integrations` and `api_tokens` entirely, so the file can be shared or stored casually (the unencrypted-export nudge disappears with it). On import an **absent** block leaves the target's existing keys/tokens alone; a **present** block replaces them. This is the only non-replace path in the vault, and it is deliberate — a secrets-free vault must not silently unconfigure the destination.
- **Import**: file picker accepting `.json` / `.age`. An `.age` file prompts for the passphrase; the plaintext JSON is then applied. Import is **replace-only** — a destructive-action confirm states that it wipes and replaces the current dataset before anything happens. Bot mode `POST /api/import` with `"mode":"replace"` (one all-or-nothing transaction); cloud mode `window.CloudVault.importAll(json)` lands the records as **one snapshot** (`replaceAllRecords` + forced snapshot upload), so months of history don't flood the oplog. On success the UI reloads to render the replaced dataset.
- **age crypto is browser-only** (`web/static/js/core/backup-crypto.js` → `window.BackupCrypto`, over the vendored `typage` build `web/static/vendor/age.min.js`). Go never links an age library; interop with the reference `age` CLI is pinned by a known-answer test.
- **Not backed up**: push subscriptions (device-bound), intake reminders (Telegram message ids), change events, sync cursors, workout schedule snapshots (write-only — nothing reads them), the cloud device/push key. Merge-mode import (adding to existing data instead of replacing) is a documented non-goal.

## Voice Agent Call

- **Surfaces**: a "Call agent" card on the Today screen (`web/static/js/features/elevenlabs-call.js`) and a persistent floating pill above the bottom nav (`web/static/js/features/call-indicator.js`). Both are driven by the same `wg-call-state` event and the `window.WGCallAgent` API; the pill keeps the call accessible after switching tabs.
- **Transport**: the ElevenLabs JS SDK (`@elevenlabs/client`) opens the live conversation using a signed URL fetched from `/api/elevenlabs/signed-url`. Disabled when `ELEVENLABS_API_KEY` or `ELEVENLABS_AGENT_ID` is unset (handler returns 503 and the card hides itself).
- **Mute / unmute**: tap toggles the user's mic via `Conversation.setMicMuted()`. Mute state lives in module-scope mirrors so it survives a Today re-render mid-call and is reflected on both the card and the pill (`muted` is included in the `wg-call-state` event detail). Mute resets to off whenever the call returns to `idle` or `error`.
- **Send photo**: a hidden `<input type="file" accept="image/*" capture="environment">` opens the system picker (camera-capable on mobile). The chosen image is uploaded — bot mode via the `POST /api/elevenlabs/upload-file` server proxy, cloud mode browser-direct to `api.elevenlabs.io` with the vault key (`window.CloudElevenLabs.uploadFile`, bd med-eas.55) — and announced to the agent via `sendMultimodalMessage({ fileId })`. Non-image blobs are rejected client-side; upload failures surface a status message but keep the call alive. The button is disabled while uploading and during `connecting`, and now renders in both bot and cloud mode.
- **Agent-side prerequisites** (one-time, configured in the ElevenLabs dashboard, not in this repo): `file_input: true` on the agent's `ConversationConfig`, and a multimodal-capable LLM (e.g., GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro). Without `file_input`, `sendMultimodalMessage` is silently ignored by the platform; without a multimodal LLM, the message is delivered but the agent cannot reason about the image.

## MCP Server

- **Purpose**: AI-assistant access to health data, including scripted multi-step workflows
- **Transport**: Streamable HTTP (2025-03-26 spec) via `mcp.NewStreamableHTTPHandler`; legacy SSE at `/sse`
- **Authentication**: OAuth via Pocket-ID, plus long-lived `mcp_*` API tokens for non-interactive clients
- **Recommended path**: `mcp_help` (discover operations) + `mcp_execute` (run a sandboxed Python script that calls those operations through a local proxy). The helper exposes only `medtracker.api.call` / `output`; the runner env passed to the script is scrubbed of authority secrets and outbound network knobs. In the long-term `mcp-runner` side-container deployment those become enforced boundaries; in the MVP in-process executor they are operational shields and not full sandboxing — see the [MVP gap note](archive/mcp-python-executor.md#known-mvp-gap-in-process-executor-isolation). Modes: `read_only` (default) and `write` (requires non-empty `intent`).
- **Granular tools (kept, not deprecated)**: `get_blood_pressure`, `get_weight`, `get_medication_intake`, `get_workout_history`, `get_sleep_logs`, `get_food_intake`, `get_step_history`, `get_diary_notes`, plus vitals and health-overview tools. `log_food_intake` and `workout_log` cover the write path for clients without script execution.
- **Composite analysis tools (kept for now)**:
  - `analyze_cardiovascular` — BP + meds + sleep + HR + SpO2 + notes
  - `analyze_fitness` — workouts + steps + nutrition totals + weight + notes
  - No new `analyze_*` tools are planned; cross-domain analyses are expected to move to `mcp_execute` scripts. The two existing ones will be downgraded to compatibility shims once the registry fully covers their inputs.
- **Context Notes**: all granular read tools automatically include diary notes from the queried date range. Pass `exclude_notes=true` to suppress.
- **Configuration**: separate from main bot, runs on a different port; the executor side spawns a sandboxed runner subprocess (see [mcp-deployment.md](archive/mcp-deployment.md#python-executor-service))

See [mcp-deployment.md](archive/mcp-deployment.md) for deployment details and [docs/mcp-python-executor.md](archive/mcp-python-executor.md) for the executor architecture decision record.

### Claude connector (cloud mode)

Server-mode's MCP server above runs in-process against plaintext data. Cloud mode is zero-knowledge, so it instead exposes two consent-driven connector modes from the Devices screen (Settings → "Claude connector" row → Devices):

- **Remote connector (claude.ai, ChatGPT) — primary.** Enable → a consent dialog states the trade-off (the server can read MCP requests/answers while relaying them; nothing is stored; the pairing key is kept server-side, at rest, until Disconnect) → the page shows a connector URL (`https://<account-subdomain>/mcp/<token>`) to paste into claude.ai/ChatGPT's custom-connector settings. Requires an unlocked PWA tab somewhere to actually answer queries.
- **Local shim (Claude Code) — alternative.** A one-time pairing code plus a `claude mcp add` one-liner wire `cmd/mcpshim` (a local stdio↔relay binary) into Claude Code/Desktop. Zero-knowledge throughout — the server only ever sees encrypted relay frames.

The two modes are mutually exclusive per account (one relay pairing at a time); switching modes disconnects the other. See [docs/cloud-mode.md → MCP](cloud-mode.md#mcp) for the full tier breakdown and leakage summary.
