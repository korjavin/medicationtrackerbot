# Feature Implementation Patterns

## First run (onboarding v3)

Open and use: an installed app (and a claimed account) shows the `WGFirstRun` overlay once, driven by `needs_first_run`. **W1** is a single module picker (*Skip* = everything on, *Continue with N*); a local-shell footer offers **F1** "Have an invite?" (paste or scan). **W2** (AI trial offer) follows only when Food was picked and a trial is on offer. Then Today carries **W3** "Start here" hints, and later **W4** (local mode) the protect-your-data card. Sync is a feature turned on from Settings → **Sync & backup** (W5) or by an invite link (**P3**); there is no native first-run choice screen. Full flow, state and paths: [onboarding-wizard.md](onboarding-wizard.md).

## Today Dashboard

Read-only landing surface (`web/static/js/features/today.js`, `window.TodayDashboard`). The home view on cold start — `features/bootstrap.js` opens Today after auth unless the user was active in another section within the last 30 minutes. Section views are reached via the five-tab bar (Today · Food · Meds · Train · Health, where Health switches between BP / Weight / Vitals), the app-bar gear (Settings) and Today route icon (Journey), card deep-links, or URL hash / messenger start param — see [frontend.md → Navigation](frontend.md#navigation).

**DOM skeleton** (`#today-content` render order, via `features/today.js`):

Kit v2 (med-xso6.13); `renderToday()` is the source of truth, each block carries a `data-section`:

1. `callbar` — call card, **Log** (opens the `#today-log-sheet` `.wg-sheet`: food fast paths Search / Photo meal / Scan barcode / Describe, then BP / Weight / Note; disabled features drop out; each tile runs the existing opener — `showAddFoodModal`, `FoodActions.triggerPhotoPicker`, `FoodLog.openAdd` + the barcode scanner, the add-food AI mode, `showBPRecordModal`, `showWeightModal`, the Notes composer) and the cloud-only Doctor brief icon.
2. `next-up` — missed doses first (danger lead, "Missed HH:MM"), then the next dose and the next workout by time. The first scheduled item owns the view's single `.wg-btn--primary` (Take → `showMedicationConfirmModal`, Start / Resume → `WorkoutSessions`). The workout row always carries View (opens Train plus the planned Day's Plan → Day pages via `WorkoutNextCard.openEdit`); tapping the row itself outside its buttons does the same. An ad-hoc session has no plan and opens Train alone. Empty → "Nothing scheduled" with Add medication / Create plan (omitted while `start-here` shows).
   - `start-here` (W3, bd med-ta2n.3) — "Start here · N picked", one inline hint per picked module with no live record yet, in W1 order, each running the module's existing add flow; its first action is the sun unless Next up holds one. `GET /api/today/start-here` → `{picked, missing}` from `settings.getStartHere` (read-only; picks from the firstrun record, minus features that are off, Diary riding `health`, which W1 keeps on when Diary is picked; no stored picks → the six flags, but only for a vault with no user content — a pre-v3 vault in use gets no block). Read on every Today render, so a row goes once its module has a record.
   - `protect` (local mode only, W4, bd med-ta2n.4) — "Keep your week safe · N records · only on this phone", shown while `GET /api/protection/status` answers `nudge` (20 records or 7 days since first run, no confirmed backup yet — only a resolved Backup ready Share calls `CloudVault.markBackup`; a Save to device can't report a cancelled picker, so its `wg.backup.last` stamp just snoozes 14 days — not snoozed: × or the sheet's Later snoozes 14 days, the second stops it for good; a failed × rolls back through `DataStore.applyOptimistic`). "Protect my records" opens `#today-protect-sheet`: Save a backup file (preselected → Settings → Backup & import's export sheet) or Turn on sync (P3 when the shell holds an invite, else the Backup page).
   - `kit-nudge` (cloud only, its twin in the same slot, bd med-ta2n.15) — "Save your Emergency Kit · N records synced · no kit saved", shown while `GET /api/protection/kit-nudge` answers `nudge`: the kit is not saved (no `emergencykit` record or `how: 'none'`), 2 days after sync is on (that record's `savedAt`, else the firstrun record) with ≥10 records; × (`POST {action: 'later'}`) stamps `protection.kitNudge` and brings it back once the record count doubles or after 30 days; "Don't remind me again" (`'never'`) stops it for good. Save kit opens Settings → Devices, whose Kit row starts the kit. The Settings Kit chip ignores the opt-out. Constants live together in `web/domain/settings.js`. Then the AI-trial offer (`ai-trial`).
3. `vitals` — BP (value + AHA class chip + age), Weight (value + 7d delta + age), Fuel (kcal + meter). Age signal: Pending chip for a device-saved row, "cached" offline, stale chip when old.
4. `goal-line` — the Goal Line card (docs/gamification.md §0.3.2).
5. `macros`, `sleep-steps` — below the fold.

No cache of any kind → skeleton while the first fetch runs, the offline state when offline, error + Retry once the fetch settles empty.

**Aggregation contract** — `aggregateToday(bootstrap, swrCaches, now)` is pure and synchronous; `Date.now()` is injected for testability. Returns a flat object where each field is `{ value, deeplink, status }`. Status values:

- `ok` — data present and fresh
- `missing` — feature enabled, no data yet
- `stale` — cached data older than its freshness threshold (BP: 24h, weight: 7d, sleep: 2d; the 1h `FRESHNESS_MS` constant only gates the offline-banner trigger via `isOfflineStale`)
- `overdue` — scheduled event passed without action (5-min grace period for `nextMed`)
- `disabled` — feature disabled; renderer omits the card entirely

**Fields and deep-link targets**:

| Field | Source | Deeplink |
|-------|--------|----------|
| `greeting` | local hour (good morning/afternoon/evening/night) | — |
| `nextMed` | `bootstrap.next_intake` (offline fallback: cached medications list) | `meds` |
| `missedDoses` | `bootstrap.intake_history` — the Meds pending set (`readPendingDoses`, `GET /api/doses?status=due,snoozed&to=now`, key `doses_pending`, the badge's read): every due or snoozed dose of any day, grouped per slot | `meds` |
| `bpLatest`, `bpTrend7d` | `bootstrap.bp.readings` (7-day anchors) | `bp` |
| `weightLatest`, `weightTrend7d` | `bootstrap.weight.logs` (7-day anchors) | `weight` |
| `caloriesToday`, `caloriesTarget` | SWR `food_today` cache + `settings_bundle` food_targets | `food` |
| `macrosToday`, `macrosTarget` | SWR `food_today` cache + `settings_bundle` food_targets | `food` |
| `nextWorkout` | SWR `workout_next` cache | `workouts` |
| `sleepLastNight` | SWR `health_overview.sleep_stats_7d` (most recent) | `health` |
| `stepsLatest` | SWR `health_overview.step_stats_7d` (latest day with steps) | `health` |
| `goalLine` | SWR `gamification_goal_line` | `journey` |

`loadToday()` (`features/today-loader.js`) reads these caches via `ApiCache.getWithMeta` for `settings_bundle`, `next_intake`, `medications`, `history_1_`, `bp`, `weight`, `workout_next`, `health_overview`, `gamification_goal_line`, and today's food key (`food_YYYY-MM-DD_day`).

**Data sources**: no new backend endpoints in Phase 1 — everything reads from `/api/bootstrap` and the existing SWR caches in `data-store.js`. A Phase 2 `GET /api/today` server-side aggregate is deferred.

**Live updates**: `TodayDashboard.subscribe()` re-renders on `BOOTSTRAP_UPDATED` `postMessage` from the SW (skipped in the subscriber; the app-level handler already reloads the current tab) and on `online` / `offline` window events and `datastore:changed` CustomEvent. `isOfflineStale({ online, cacheTimestamp, now })` toggles the dashboard's offline banner when cached data exceeds 1h while offline.

**Trend arrows**: 7-day trend computed from two SWR-cached anchors (oldest within the 7-day window and most recent). Fewer than 2 usable samples → status becomes `missing`. A `flat` direction (delta within ~0.5% of the anchor magnitude) renders `7d flat` without a signed number.

## Medication Tracking

- **Sub-tabs**: Timeline (default, kit MT1, bd med-wi09.3 — replaced History and Upcoming), Schedule (dose-slot buckets, kit M1), Stock (`data-tab="inventory"`, kit v2 ST4: "Needs attention" (Out · N over / Low) above "Fine", "N left · lasts N days", one Update per row).
- **Stock ledger** (bd med-wi09.13, `web/domain/stock.js`): stock is derived, never stored as a counter. `stock` records are append-only `refill {n, at}` and `audit {count, at}` rows, and stock = the latest audit's count + refills after it (legacy `restock` rows included) − TAKEN doses with `taken_at` after it. So an offline dose and a refill on another device both land, and correcting a dose's time moves stock only across an audit. `medication.inventory_count` is a write-only mirror for older clients: reads return the derived value, and an old client's edit of the field is ignored. A tracked med that has no audit gets a floored seed audit before its first stock-moving write (see [cloud-mode.md → Sync protocol](cloud-mode.md#sync-protocol)). The Update sheet (`openStockSheet()` in `features/meds.js`, kit ST1–ST3) has an Added | Counted switch. Added offers "+1 pack (N)" when `pack_size` is set, then +30/+60/+90 and a stepper, and posts `/api/medications/{id}/restock`. Counted is prefilled with the app's number and posts `/api/medications/{id}/stock-audit` (MCP `medications.stock_audit`). Both go through `DataStore.applyOptimistic`. Below the form is the read-only history; corrections are new counts. The Add medication button (`#add-btn`) is the Meds app-bar primary; `syncMedsAddButton()` (`features/meds.js`) hides it while the visible pane's empty state carries its own Add (kit M4/MT5 — zero medications). Sub-tab state persists under `mt-meds-subtab` in `sessionStorage` (default `timeline`; a stored `history` / `upcoming` from an older build maps to `timeline`); legacy `localStorage` values are purged on module load.
- **Timeline sub-tab** (`#med-timeline-list`, `loadTimeline()` / `renderTimeline()` in `features/meds.js`): kit v2 TL1–TL4 (bd med-ry7b), in time order and opening at its top on every visit: the future — "Show 3 more days ahead" at the very top, then one folded, dashed "Planned" row per day, farthest first ("Tomorrow · Sat 24.10", "3 doses · first 08:20"; a tap unfolds that day's planned doses, no buttons) → Today, led by the focus card (the one accent card: exactly one pending dose, the latest of every pending dose, with a "Yesterday" / "N days ago" chip when it isn't today's and Take as the primary; "+N more pending" as a count only; then "Next today", the next dose due today with a raised Take; nothing pending and nothing left today → "All done for today · Next: tomorrow 08:20 · 3 meds", no accent, no buttons), then today's other doses (`Pending` with "Due Xh ago" / "Snoozed until HH:MM", `Later today`, `Done` with "Taken HH:MM" / "Skipped"); the card's doses are not repeated → History, Yesterday and the day before, newest first ("N of M taken" / "N pending" — a day whose dose is in the card still counts it / "No doses"), over "Show 3 earlier days". Two reads: the display window `GET /api/doses?from&to` (the shown days plus one page each side, so a "Show 3 …" tap renders at once from local rows, then re-reads the widened window — no spinner, no auto-load) and the pending-only `GET /api/doses?status=due,snoozed&to=<now>` (cached as `doses_pending`) the focus card picks from, so a dose left pending beyond the shown History is still the card. No "missed": a dose stays pending until taken or skipped. Rows group by the projection's own `(localDate, localTime, tz, state)` — never the device clock — so a dose keeps its date across a zone change and the same local time in two zones never merges; a row in another zone reads "HH:MM · City" with the tracked-zone time as meta, and a "Times are <zone> time." note shows while the device sits in another zone. Names resolve by `String(medId)` against the medications list. Actions (bd med-wi09.17), each on the row's own `data-occ-ids` through `POST /api/doses/act`, flipped in place first (`DataStore.applyOptimistic` on `doses_timeline`, the cached projection `loadTimeline` reads back while a write is pending): a pending row carries Skip / Take (Take stamps now) and a tap opens the take sheet in `confirm` mode (take at a picked time, Skip, Snooze); a taken or skipped row opens it in `edit` mode (kit MT3); upcoming rows are read-only. Each History day that still has pending doses gets one "Mark all taken" / "Skip all" pair under its own day head (kit MT4 · pile-up): only that day's pending occIds at tap time (a repeat finds nothing left), taken_at = each dose's planned time, no dialog — an 8 s toast ("6 doses marked taken" · the day) whose Undo sends `undo` for exactly those ids. MT6: `showMedsReminderOutOfDate({medId, scheduled, tz})` opens Meds → Timeline under a warn note "Reminder for HH:MM <City> is out of date. Pick the dose you mean." (Dismiss), scrolled to that med's first row in Today; nothing is preselected or logged (the landing bd med-wi09.4 deep-links to).
- **Take sheet** (`#med-confirm-modal`, kit M2; `showMedicationConfirmModal()` in `features/meds.js`, write handlers in `features/meds-history.js`): one sheet opened from push, Today's Take, Schedule "Take N" / "Log late" and timeline rows. Modes: `confirm` (primary "Take N" counting the checked rows, Snooze 10m / Skip as ghost actions), `edit` ("Update", "Update N" for a group; a "This dose was" segment Taken / Skipped / Not taken, the time row only for Taken) and `log_past` ("Log", posts `/api/medications/log-past`). Take / Skip / Update post explicit dose actions (below) on the sheet's own occIds — the opener's row id, else the slot's deterministic `intake-<medId>-<slotUnix>` — so a slot-mate absent from or unchecked on the sheet is never touched. The "Time taken" row starts at now in `confirm` mode and sends `taken_at` only when the user picks a different time.
- **Explicit dose actions** (bd med-wi09.2): `POST /api/doses/act {occ_ids, action: take|skip|undo|edit_time|snooze, taken_at?, minutes?, until?}` (`act` in `web/domain/medintake.js`, MCP `medications.doses.act`). take: PENDING or not-yet-recorded → TAKEN (created at the planned instant only when the projection has that slot — since bd med-wi09.12 due doses are derived from medication history and never written as PENDING placeholders), −1 derived stock; skip: PENDING or not-yet-recorded → SKIPPED; undo: TAKEN/SKIPPED → PENDING, which gives the stock back since stock is derived from TAKEN doses; edit_time: `taken_at` of a TAKEN dose; snooze (bd med-4j49, the take sheet's "Snooze 10m"): a due PENDING or not-yet-recorded dose → `snoozed_until` = `until`, else now + `minutes` (default 10), written on its own `snoozed_at` branch — status and rev unchanged, so a concurrent take still wins; a dose not due yet fails `not_due`, an end past the 7-day reminder horizon is a 400. The reminder horizon (`computeReminderHorizon`) fires every dose whose `snoozed_until` is ahead at that instant, with its own slot's `s:<slot>` callback however old the slot, so web push, Telegram and the device scheduler all get it; a snooze-end reminder also names the slot's still-due mates. The act route reconciles the relay's hourly chain for the slot (which `ReplaceSchedule` keeps): every open dose snoozed → `cancel-refire`; some still due → `rearm-refire {keep_fire_at: true}` narrows the pending re-fire to them at its own time. A Telegram Snooze tap's edit text carries no duration ("⏰ Snoozed — I'll remind you again."): the vault's 10-minute snooze end and the relay's +1h fallback both serve it, whichever fires first. A dose already in the target state is `unchanged` (repeating a bulk take is safe); anything else is a per-id failure in `{updated, unchanged, failed, failures, doses}`. Per-day bulk is the same route with many ids. `confirm-schedule` is additive always — the old slot-mate revert pass is gone.
- **Medication editor** (`#med-modal`, kit M5–M6; `fillMedEditor()` in `features/meds-history.js`, `saveMedication()` in `features/meds.js`): a pushed `.wg-page` with Basics / Schedule / Inventory / Advanced sections and Cancel / Save in the page bar. Opening an existing medication or committing its name calls `GET /api/medications/rx-check` (`web/domain/medications.js` `rxCheck`, the same exact-only RxNorm match and best-effort interaction check create/update use). The previous Rx chip and warning clear before rechecking; only a fresh response for the current editor/name can display them, never a saved association supplied as `rxcui` or `normalized_name`. The post-save alert fires only when that check never resolved. Stock is a starting-count stepper only for a new or untracked med; a tracked med shows a "N left" row whose Update opens the stock sheet, plus a Pack size row (`pack_size`, `safePrompt`), the time-zone policy a value row opening `safeChoose`, Archived / Supplement are toggles, and "Delete medication" (destructive dialog) shows only for an archived med never taken.
- **Correcting a dose** (the take sheet's `edit` mode, opened from a taken or skipped timeline row, kit MT3): the checked doses get the segment's state and unchecked ones are left alone. From each dose's current state: Taken → Taken is `edit_time`; leaving Taken/Skipped is `undo` first, then `take` (at the picked time) or `skip`; Not taken is `undo` alone, so the row flips back to Pending. The frontend only shows "Updated!" + commits the optimistic flip when every id applied; otherwise it rolls back and shows an error naming the failed med(s).
- **Schedule order** (`renderMeds()` in `features/meds.js`): pending buckets (`HH:MM` / `HH:MM · yesterday` with a Pending chip — never "missed", bd med-wi09: the occurrence projection's `due` rows over the last 24h, the same set the Meds tab badge counts; head action "Log late" confirms them by occId) → one bucket per next-dose slot (`HH:MM · in Xh Ym`, earliest first; head action "Take N" opens the take sheet preselecting the bucket's meds for that `scheduled_at`) → `Scheduled` fallback for entries with no computable next dose → `As needed` (rows keep a per-row Log) → `Archived`. A med with a pending dose shows only in its pending bucket. Rows are kit `.wg-row`s: tap edits, swipe / overflow for Edit / Delete (scheduled rows also carry "Log a dose" there); stock / supplement / archived / sync state are chips. The 7-day forecast (`loadUpcomingDoses()`, `/api/medications/upcoming`) still feeds the buckets; its own Upcoming sub-tab became the Timeline (bd med-wi09.3).
- **One occurrence projection** (bd med-wi09.1): `projectOccurrences` in `web/domain/medintake.js`, served as `GET /api/doses?from=<ISO>&to=<ISO>` (default: last 24h → next 7 days; `&status=due,snoozed` keeps only those states and defaults `from` to the start of the ledger — pending never expires, so there is no age cap), is the only answer to "which doses exist and in what state". Rows `{occId, medId, name, dosage, plannedAt, tz, localDate, localTime, source: schedule|tz_step|manual, state: upcoming|due|snoozed|taken|skipped, takenAt?, snoozedUntil?, stepNote?}` = every stored intake row in range as-is ∪ the future forecast for slots with no stored row at their exact id; a tombstoned id is hidden; there is no `missed` state. Home next-intake, `/api/medications/upcoming`, `/api/history`, the Schedule missed buckets, the Meds badge, Today's missed line and the reminder horizon's med rows are all views over it.
- **Schedule bucketing is plan-aware** (bd med-gut.1): the bucket times come from `GET /api/medications/upcoming?days=7`, which runs the same engine as Home's next-intake card (`web/domain/medintake.js` → `planDosesWithTzPlan`), so the tracked IANA timezone, an approved tz transition plan, start/end dates and legacy `"HH:MM"` schedule strings are all honoured and the two screens cannot disagree. Each row carries its wall-clock `local_date` / `local_time` / `day_offset` in the tracked zone, so the renderer does no timezone math of its own. When the route is unavailable (offline cold start) the tab falls back to the device-local computation in `features/medication-utils.js`.
- **Archiving & Deleting**: active medications can be archived; archived medications can be permanently deleted only if they have no intake history
- **Schedule Types**: Daily, Weekly, As-Needed with optional Start/End dates
- **Duplicate Prevention**: HTTP 409 on creation when name (case-insensitive) + dosage matches an existing medication (including archived)
- **Drug identity lookup** (bd med-diu9): automatic matching accepts only one unique exact RxNorm concept, using NLM's case-insensitive `search=0` mode; duplicate copies of one ID count as one result. There is no automatic approximate spelling match, normalized-search fallback, or confidence threshold. An unresolved, ambiguous, malformed or unavailable result keeps the entered medication name without a matched-drug chip or a warning derived from a guessed identity. Opening/checking is read-only; ordinary Save refreshes or clears the derived `rxcui`/`normalized_name`. Existing saved associations elsewhere are unchanged until their ordinary update; this is not a migration or retrospective audit. Older cached app bundles retain their prior lookup behavior until updated.
- **Drug Interactions**: best-effort checking through the RxNorm port for matched medications when adding/updating/unarchiving. An unavailable interaction service returns no warning; absence of a warning does not establish medication safety.
- **Notifications**: Telegram alerts with scheduled time and dosage; hourly retry if not confirmed
- **Timezone Shift Policy** (`tz_shift_policy`): per-medication field controlling how doses are rescheduled when the user's timezone changes. Values: `flexible` (default — shift immediately in one step), `medium` (gradual, max 3h per dose), `strict` (very gradual, max 2h per step). When a timezone change is detected and an active plan is approved, the scheduler uses the plan's transition steps instead of normal schedule times until all steps are consumed.

## Blood Pressure Tracking

- **Classification**: ISH 2020 guidelines (configurable for age <65)
- **Target**: <130/80 mmHg
- **Tracking**: 2–3x daily recommended
- **Statistics**: daily-weighted averaging — each day with readings gets equal weight regardless of measurement count (prevents frequency bias). Day boundaries use the user's stored timezone (falls back to UTC).
- **UI layout**: the "+ Log" BP button renders **inline** with the range selector (14d / 30d / 60d, **default `14d`**) in the `.wg-range-row` beside the kit `.wg-seg--sm` range strip, not as a floating FAB. `#add-bp-btn` is a kit `.wg-btn--primary.wg-btn--sm` that re-renders with the range selector. The initial fetch still hits `/api/bp?days=60` so 30- and 60-day averages stay available client-side; active-range filtering happens in `filterReadingsByRange`. The chart emits numeric y-axis mmHg ticks ({60, 80, 100, 120, 140, 160, 180} ladder, clamped to range) and x-axis date ticks; the `bp-current-card` top summary pane was removed in round-2 Task 2.
- **Editing** (med-xso6.27): tapping a history row (or its Edit action) reopens the BP sheet prefilled; Save rewrites the same reading via `PUT /api/bp/{id}` (`web/domain/bp.js` `update`, category recomputed) through `DataStore.applyOptimistic`. Delete stays on the row actions with undo.
- **Export**: CSV

## Weight Tracking

- **UI layout** (Wandergeek Phase 6; round-2 Task 12): `#weight-view` opens with the optional goal card (hidden when no goal is set, progress bar when shown), followed by the range-selector row. The range-selector row is a flex track containing the `7d / 30d / 90d / All` pills (persisted via `mt-weight-range`, default `30d`) plus the `+ Log` button (`#add-weight-btn`, kit `.wg-btn--primary.wg-btn--sm`) pinned to the right. Below the selector: the `WGWeightChart` panel — whose card surface, guide lines, and axis ticks consume the shared `--wg-chart-*` tokens so it stays visually flush with the BP chart (round-2 Task 13). The chart renders numeric y-axis kg ticks, first/last x-axis date ticks, a dashed `GOAL · {value} kg` horizontal line, a "plan trajectory" line from the first actual log to the goal at the last data point, the actual-weight spline, and a dashed 14-point regression "trend" line. A chart legend (Actual / Plan / Goal) mounts in `#weight-chart-legend` below the chart. The goal card's progress comes from the Goal Line read-model (`GET /api/gamification/goal-line`, `goal.progress` / `distance_to_goal` — the same numbers Today shows) when gamification is on, with the labeled trend and the raw latest reading side by side; with gamification off it falls back to lifetime-highest (lose) / lowest (gain) → latest reading. The former goal-prognosis card (`#weight-prognosis-card`, a 14-day regression ETA) stays hidden; a projected date returns only via the Goal Line (med-8tur.7). A day-grouped history list sits at the bottom; there is no bottom CTA. The previous "Latest" current-weight pane (`.wg-weight-header-row` + `.wg-weight-current-card`) was removed in round-2 Task 12; the chart is the first visual after the goal card.
- **BMI** (epic med-a6fb, kit `screens-bmi.html` BM1/BM3): the loader also fetches `GET /api/weight/bmi` (`bmiRes` in the `weight` cache). With a height, the chart card shows "BMI 24.3" + a WHO class chip (Underweight · Healthy · Overweight · Obesity I/II/III; only Healthy is `--ok`) beside the Current badge, the fine print "Adult ranges; not meant for under-18s.", and `WGWeightChart` `bands` draws each WHO border that falls inside the data-plus-goal range as a labelled hairline ("Overweight · 25"), in the display unit, never stretching the axis and with no legend entry. `show_bmi: false` hides the read-out, borders and nudge. Without a height the payload's `nudge` flag adds an "Add your height to see BMI" ghost row (→ Settings → Units & body); × PATCHes `/api/settings/body {bmi_nudge_dismissed: true}` optimistically, gone for good. The goal dialog shows a non-blocking warn note when the target is below the BMI 18.5 border (hidden when `borders_kg` is null). ED-safe nulls the payload, so nothing renders.
- **Edit modal**: kg/lb unit toggle (replaces the paper-era drag ruler). Editing an existing entry deletes the original and POSTs the replacement because the backend has no PATCH route for `/api/weight`.
- **Unit preference**: each user has a preferred weight unit (`kg` or `lb`) stored on the singleton `settings` record (`weight_unit_preference`, default `kg`). Storage is always in kg; the preference only affects input default and display in the web app and chat replies. The preference is bumped to whichever unit the user last chose: submitting the modal in lb, or flipping the Settings segmented control, PATCHes `/api/settings/weight-unit`. Over Telegram chat `/weight` logs kilograms (`web/domain/tgcommand.js`). The MCP contract is unaffected — `health.weight.list` and `health.analyze_fitness` always return `_kg`-suffixed fields regardless of preference.
- **Trend**: exponential moving average for smooth visualization
- **Export**: CSV in Libra format (compatible with Libra app)
- **Reminders**: weekly if no weight logged

## Food Tracking

- **AI provider settings** (`features/settings/integrations.js`, med-ezux.2): Settings → AI & integrations offers OpenAI, Anthropic (Claude), Google Gemini, OpenRouter, or Other, derived from the existing saved URL. Only Other shows API URL; new/changed Other setups require URL + key, while legacy keyless data stays intact. Presets fill only blank/previous-recommendation models; saved/custom models and raw URLs remain unchanged on load/reselect. Switching clears the draft main key; reselect/Back restores the saved main setup. Model Choose uses saved credentials and permits manual entry when listing fails. Reverting a custom URL restores only an untouched saved mask; other draft keys require re-entry. Active/trial/own-key status reflects committed settings until Save succeeds. Provider examples are not feature certification.
- **Check key** (`med-ezux.3`): makes one tiny, health-data-free Chat Completions request with the chosen draft or saved provider key, URL and model, saves no settings, and discloses the small provider charge. It first checks the immutable permission snapshot of the actual loaded document. A new host requires explicit Save and reload; cloud offers Reload page only after successful hostname registration and asks before discarding subsequent edits. Cells shade by session **status** — completed (sun fill) / skipped (muted outline) / nothing logged (faint) — never by volume, because a bodyweight session logs zero tonnage and would render as a rest day. A day holding both a completed and a skipped session reads as completed. Each cell carries a `date · what happened` tooltip and the grid carries one summarizing `role="img"` aria-label. The grid is capped at **26 week rows** (~6 months) so `range=all` on a long history stays one comfortable scroll rather than pushing the tiles two screens down. **Cells are fluid** (med-iyu): the grid takes the card's width and splits it seven ways, bounded by `--wg-workouts-calendar-cell-{min,max}` — the max keeps 7 columns on a wide card from inflating into wall-sized squares (`aspect-ratio` makes width height), and the header row shares the grid's template and width bound so each initial sits over its column. Nothing overflows horizontally any more. Note that 7d is **two rows by construction**. The body-part split moved out entirely: the Balance view owns it, and rendering it in both was duplication.
- **Load** — *how much work did I do*. Volume / Hard sets / Reps / PRs tiles over the range, a weekly-tonnage **bar** chart (`WGWorkoutChart` in `metric: 'volume', variant: 'bars'` mode fed from `weekly_volume`), and the volume-sorted exercise list. med-zte swapped the line for bars: weekly tonnage is a set of discrete buckets, and a spline through them implies a continuous quantity that was never measured between Mondays. The bars variant forces a **zero baseline** (a truncated axis would make a 900 kg week look like a tenth of a 1000 kg one) and skips LTTB downsampling (a dropped bucket reads as an untrained week). The line stays the default variant, so exercise-detail's est-1RM / top-weight / reps charts are untouched. Warm-up sets count for nothing. The Hard sets tile names the rated-easy sets it excluded ("Hard sets · 3 easy", see below). Zero logged working sets — hard *or* easy — renders "No logged sets in this range" rather than a wall of empty tiles. Under the chart legend, med-djsa.5 adds the week-over-week caption (`.wg-workouts-stats__delta`): "Last week 12.3t · 18 hard sets · +23% vs the week before", folded in `stats.js` off `weekly_volume` — presentation tier, no domain field. It compares the last two **complete** ISO weeks: the current Monday's bucket is partial until Sunday, and counting it would report a crash every Tuesday for someone training exactly as usual (the same honesty rule the hard-set band applies by using rolling 7-day windows). `weekly_volume` is sparse — a week with nothing logged is *absent*, not a zero row — which the caption reads literally in both directions: when last week itself has no bucket it says "Last week no training" (never relabelling an older bucket's tonnage as last week's), and when the week *before* last is missing or zero it keeps the line and drops the delta rather than dividing by zero. With no complete week at all it is omitted entirely, so a brand-new account isn't nagged about a week it wasn't here for. Like the activity calendar, it anchors "this Monday" on the browser's local calendar day rather than the domain's configured timezone.
- **Balance** — *what am I neglecting*. Sets per body part (folded from `exercise_totals` through the static exercise catalog, client-side), each row showing `N sets · X%`, plus a **"Not Trained"** chip row naming the catalog body parts with zero sets in the range. The absence list is the point: it's the JEFIT-BodyMap question ("what am I missing") that a top-N list structurally cannot answer. A catalog that fails to load skips the split rather than showing an all-uncategorized one.

  **med-904.3 appends a follow-up below the split.** **Movement Balance** — `Pull : Push` and `Hinge : Squat` rows over the same working sets, the JEFIT Movement-Balance-Engine axis that Strong and Hevy both omit. The catalog carries body parts, not movement patterns, so `WorkoutExerciseCatalog.resolveMovementPattern` *derives* one from the exercise **name** (the name is what encodes the movement — "row" vs "press" — while a body part cannot tell a pull-up from a bench press), gated first on the body part having a pattern at all: core, calves, forearms, neck and cardio resolve to `null` rather than to a guess, and the leg rules are checked before the arm ones so "leg curl" is a hinge and "leg press" a squat. The rules also carry a vertical/horizontal `axis` where the movement has one; nothing renders it yet — it is what a hex radar would read. The ratios sit behind the same guards as the split (same rows, same catalog) and say **"Keep logging to unlock movement balance"** when nothing folds yet: an empty state, not an error. The **Hard Sets · Last 7 Days** band that med-904.3 also put here is gone from Balance — med-djsa.3 promoted it to the headline above the view strip, where a range-independent number belongs and where everyone sees it.

### Stats API (`/api/workout/stats`)

Returns `active_weeks` (count of weeks with at least one completed session), `total_sessions` (sum of completed and skipped), `current_streak_weeks` and `longest_streak_weeks` (the longest consecutive run anywhere in the history, ≥ the current streak), `weekly_activity[]` and `top_exercises[]` (top 8 by volume), all scoped by `?range=` except the two whole-history streaks.

med-zte added `daily_activity[{date, completed, skipped}]` for the Consistency calendar: one entry per **local** calendar day inside the active range that saw a completed or skipped session, ascending by date. It is **sparse** — a rest day is simply absent, exactly like an untrained week in `weekly_activity` — and the calendar fills the gaps itself. Unlike `weekly_activity` (which keeps a wider ≥12-week heatmap span), `daily_activity` is scoped to the active range only — widened back to the **Monday of the range's first day** (med-nw6r), because the calendar draws whole Mon–Sun weeks and a padded leading day must show its real status. Only `daily_activity` widens; the counts and every other range-scoped field keep the exact window. Like every other list on this response it is `null`, never `[]`, when the window holds nothing.

med-904.1 added the load aggregates on the same response: `totals{volume_kg, hard_sets, easy_sets, reps, pr_count}` over the range, `weekly_volume[{week, volume_kg, hard_sets, reps}]` sharing `weekly_activity`'s ISO-Monday buckets and wider ≥12-week span, and `exercise_totals[{exercise_name, session_count, sets, hard_sets, reps, total_volume_kg, max_weight_kg}]` covering **every** exercise trained in the range (not the top-8 slice — that's what lets Balance fold a complete body-part split). Sets marked `set_type: "warmup"` are excluded from all three. `pr_count` counts in-range logs whose heaviest working set beat every earlier log of the same exercise, including out-of-range history.

med-djsa.2 named those records: `prs[{exercise_name, date, weight_kg, previous_kg}]`, one entry per counted PR, **newest first**. `date` is the session's **local** calendar day (the `YYYY-MM-DD` prefix, same rule as `daily_activity`); `previous_kg` is the record that was broken, `0` for a first-ever weighted lift. Warm-up sets are excluded by the same `max_weight_kg` fold, so a warm-up-only log — and a zero-weight bodyweight one — can never set a weight PR. **Weight PRs only**: est-1RM and rep records stay in `web/domain/workout-analysis.js` and the per-exercise detail view rather than being re-derived here. Like every other list on this response it is `null`, never `[]`. The Load view renders it as a "Records · this range" list under the tiles and omits the section entirely when it is `null`.

med-904.3 added `hard_set_band{current, baseline, low, high, status}` — the user's **own** volume baseline (JEFIT's Stimulus Volume Engine / Strava's Relative Effort), so the Stats headline can say "in range / below / above" instead of an absolute nobody can calibrate. `current` is the hard sets of the last 7 days; `baseline` averages the three 7-day windows before it; `low`/`high` are ±20% around it, floored and ceiled **outward** so a small baseline still leaves a band instead of collapsing to a point; `status` is `below` | `in_range` | `above`. **Rolling 7-day windows, not the ISO weeks `weekly_volume` buckets by** — a calendar week is partial until Sunday, so an ISO-week comparison would report "below" every Monday through Thursday for someone training exactly as much as always. It is `null` (never a zero band) until the vault holds at least four windows of history and the baseline is non-zero: a two-week-old account has no "usual" yet, and averaging a partial history would call every honest session "above". Like `current_streak_weeks` it is **range-independent**. It is computed in `web/domain/workout.js`.

**A hard set is effort, not a set count (med-vov).** A working set counts toward `hard_sets` only when it was taken near failure — RIR ≤ `NEAR_FAILURE_RIR` (4), i.e. the logged per-set `rpe` ≥ 6. Per-set RPE is optional and rating only the top set is normal practice, so an **unrated working set still counts as hard** ("no opinion", never "too easy") — the same rule `workSetStats` applies to unrated sets (effort is read from the rated top set) — and a flat-scalar log, which carries no effort at all, keeps counting every set. `totals.easy_sets` reports the rated-but-easy working sets that were excluded, so the Load view labels the tile "Hard sets · 3 easy" instead of silently shrinking a number the user already saw. Volume and reps are unaffected: an easy set is still work done. One flat threshold for every exercise — goal-differentiated proximity is noted as an upgrade path in `web/domain/workout-goals.js`, not implemented.

**Effort and coverage are separate fields; read the one you mean.** `exercise_totals[].sets` is **coverage** — every working set, ungated, unchanged by med-vov — and `exercise_totals[].hard_sets` is the effort-gated twin alongside it. The Balance view folds coverage, because it prints the body parts with zero sets under **"Not Trained"**: gating that count on effort would tell a user who squatted three honest RPE-5 sets that they never trained legs, while a user who logs no RPE at all keeps getting the truth. Rating honestly must never produce falser data than not rating at all. `totals.hard_sets`, `totals.easy_sets` and `weekly_volume[].hard_sets` are the effort side, and the Load view is where effort belongs.

`top_exercises` is the top-8 slice of `exercise_totals` (med-7pq), so both views report the same volume for the same exercise. Before that it carried the pre-per-set derived-scalar product (stored set count × **max** reps × **max** weight, warm-ups included), which over-counted a realistic ramp roughly 3× — 40 kg×10 warm-up + 80 kg×5 + 85 kg×5 reported 2550 kg against a true 825 kg.

## User Trackers

Vault shape: `data.trackers` in [vault-format.md](vault-format.md#trackers).

- **Streaks** (`med-q2bq`, `med-yd2u`): a limit of 0 with `target.days` is a "hold for N days" challenge. In the editor, "Limit · at most 0" swaps the period for a days field (7 / 30 / 90 or custom; empty keeps the open-ended clean streak). The tile reads "N / 7 days clean" over a bar; reaching N is one-shot — the tile shows "goal reached" with Extend (editor on the days field) and Archive, no auto-restart. The brief reads "day N of 7" / "7-day goal reached".
- **Doctor brief**: opt-in `trackers` section — one line per active tracker with its current day/week/month progress; limits end "— within limit" / "— over", check limits count slips; no block when there are none.
- **Reminders** (`med-1vy5.5`): a tracker with `reminder.time` gets a `tracker` horizon entry at that local time only while its `atLeast` target for the period is unmet (`atMost` limits never remind); every tracker write recomputes the horizon. ## MCP Server

### Claude connector (cloud mode)

Settings → Devices & connectors → Claude connector offers two deliberate modes:

- **Remote connector (Claude Code, Claude app, ChatGPT) — primary.** Connect an AI app → consent states that the server can read requests/answers while relaying, stores none, and retains the connector key until Disconnect. The per-app instructions share the same connector URL (`https://<account-subdomain>/mcp/<token>`). Claude Code gets a prompt and terminal command; Claude app/ChatGPT get URL instructions.
- **Private mode for Claude Code — secondary.** Choose the destination computer (macOS/Linux/Windows), then Create. Copy one complete prompt or the same terminal command, using the published checksum-verifying `mcpshim-v0.1.0` installer. No Go/Node/source checkout or GitHub login is needed. The browser-generated pairing key never goes to the hosted endpoint; the server relays encrypted frames. Claude/model providers can receive requested records. Prompt/config/history can retain the pairing key; see [the helper reference](mcpshim.md). Clipboard success is not installation or live connection proof. Stored pairings show “Private pairing saved”; a lost one-time code requires explicit reconnect.

Keep an app open and unlocked for either mode. Switching modes or reconnecting confirms replacement before any mutating request, with Cancel initially focused. Cancellation preserves the old connection; a confirmed replacement can revoke it before a later setup failure. Disconnect revokes access without erasing previous data/transcripts or uninstalling the helper. Private pairings retain the existing 24-hour/redeploy expiry; generic device-offline errors do not establish expiry. The modes remain mutually exclusive per account.
