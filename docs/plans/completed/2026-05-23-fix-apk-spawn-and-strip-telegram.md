# Fix APK: Spawn Embedded Backend + Strip Telegram + Document Emulator Workflow

## Overview

The CI-built APK at `medtracker-a1616c67-debug.apk` ships `libmedtracker.so` but never spawns it. The Kotlin overlay sources (`MainActivity.kt`, `GoServerService.kt`, `NativeBridge.kt`) are not compiled into the APK — verified by inspecting `classes*.dex` strings: no `GoServerService`, no `MedtrackerActivity`, no `awaitListening` symbols. A Java `MainActivity.java` stub (auto-generated by `npx cap add android`) compiles instead, behaving as a bare `BridgeActivity` that just loads the bundled `assets/public/index.html`. Combined with the Telegram script tag loading unconditionally, this manifests as a blank/broken WebView where every `/static/*` asset 404s and the only network call that succeeds is `https://telegram.org/js/telegram-web-app.js`.

This plan does three things:

1. **Fix the build pipeline** so the overlay's Kotlin sources actually compile and the binary-spawn path comes alive (`MainActivity.kt` → `GoServerService` → `LISTENING <port>` → WebView at `http://127.0.0.1:<port>`).
2. **Strip Telegram from the mobile WebView entirely** by moving the `telegram-web-app.js` script load out of `index.html` and into `messenger-adapter.js`, gated on running outside Capacitor. The frontend's existing `TelegramAdapter`/`BrowserAdapter` runtime selection naturally falls back to `BrowserAdapter` when `window.Telegram` is absent.
3. **Document the local Android emulator workflow** at `docs/android-emulator.md` so future iterations don't need to re-derive it.

## Technical Details

### Why the Kotlin plugin isn't already enabled

Capacitor 6's project-level `build.gradle` (generated by `npx cap add android`) includes the Android Gradle Plugin classpath. It does NOT include the Kotlin Gradle Plugin classpath by default — Capacitor itself ships its Java sources as Java, not Kotlin. The Kotlin plugin must be added to either:
- the project-level `build.gradle` buildscript classpath, AND
- the app-module `build.gradle` (`apply plugin: 'org.jetbrains.kotlin.android'`)

Capacitor 6 does pull `kotlin-stdlib` transitively (via some plugin deps), so `kotlin-stdlib` is already on the runtime classpath. The plugin itself is the missing piece.

If the project-level classpath doesn't include the Kotlin plugin (most likely), we have two options:
- **Option A**: `apply-overlay.sh` sed-inserts the classpath line into `capacitor/android/build.gradle`. Idempotent (check-then-insert).
- **Option B**: Add a project-level `build.gradle` overlay file that gets symlinked or copied. More invasive.

Task 1 picks Option A (smaller surface area, fits the existing apply-overlay model).

### Why deleting MainActivity.java is the right answer

The Capacitor `cap add android` generator does `MainActivity.java` as a 4-line stub. With Kotlin enabled and `MainActivity.kt` present, AGP rejects with "Duplicate class com.korjavin.medtracker.MainActivity". The clean fix is to delete the stub. `apply-overlay.sh` is the right place because it owns the post-`cap add android` reconciliation.

### Telegram SDK dynamic-load: why it works

`messenger-adapter.js` already does runtime detection: if `window.Telegram?.WebApp` is absent, it picks `BrowserAdapter` regardless of platform. So removing the script tag from `index.html` is *safe by itself* — on mobile, `BrowserAdapter` activates and the app continues. The dynamic-load shim is purely to preserve the web build's existing behavior (where the script tag was already loading at HTML parse time).

For the web build, the adapter selection now runs *after* an async script load. This adds ~50–200ms to first paint on slow networks. Acceptable tradeoff — Telegram's CDN is fast, and the alternative (build-time strip) couples the build pipeline to the frontend's HTML structure.

### Architecture-test for index.html

The new architecture test (`tests/architecture.no-telegram-in-html.test.js`) is a string-match assertion against the bundled `index.html`. This catches future regressions where someone re-adds the script tag manually. It does NOT prevent the runtime dynamic-load — that's the whole point.

### APK structural verification

The `scripts/verify-apk.sh` script is a defense-in-depth check that complements the unit tests. Unit tests verify the *intent* (kotlin plugin is wired, Telegram script is removed); the APK script verifies the *result* (overlay symbols are actually in the dex, no `telegram.org` in the bundled HTML). Both layers catch different failure modes.
