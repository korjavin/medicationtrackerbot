Add a device · approve on the device you already have

Epic med-r1j2. Screens AD1–AD11, referenced by beads as Spec: screens-add-device.html ADn. Built from kit v2.1 plus one v2.2 component, the matching code. Both devices show it before Approve; approval happens only on the device that showed the QR.

Review of the brief

Confusing for a non-technical user

  • Two codes on the same screen. AD2 shows a typed fallback code, and seconds later AD3 shows a 6-digit matching code. If both are digits, people will type the wrong one. The fallback is letters in groups ("KXR · 7PM · QDW") labelled "Code for a computer"; only the matching code is digits.
  • Passkey vs. "enrol another passkey". The word passkey stays, since that is what the app uses on every platform, and the buttons never promise a biometric (the OS decides: face, fingerprint, PIN, security key or a password manager). What changes is the framing: each screen says which device the passkey is for ("a passkey for this phone", "your existing passkeys keep working"), so it can't read as adding a second passkey to the same device.
  • "<Android app> wants to join". "Join" is protocol language. The user is letting a device open their account: "An Android phone wants to open your account".
  • "<sub>.<base>" in AD9 and AD10. Nobody knows their account address. AD10 needs a "where do I find it" hint, and the address needs a home: a copyable row in AD11.
  • "Someone else tried to use this code" alone is alarming. It needs "nothing was shared" and what to do differently.

Missing states

  • Origin app in the background when the request arrives: needs a notification ("Approve the new device?") that opens AD3. Not drawn.
  • User cancels the system passkey sheet in AD6: return to AD6, approval held until the code expires (in the AD6 caption).
  • Joining device already syncs to another account (not local mode): AD9 erases records, but here it would also sign out of an account. Needs its own D1 "Switch account?" variant. Same open item as onboarding v3.
  • AD9 with zero records: skip the dialog.
  • AD10 finds no synced passkey: "No passkey for this account on this iPhone" → offer Add a device. Not drawn.
  • Missed toast: AD11 notice should persist in Devices for a few days; a security notice must not rely on a 4-second toast.
  • Camera permission denied on the new device's scanner → fall back to the typed code. Not drawn.

Decisions taken here

  • AD4 · misuse keeps the brief's single "Cancel". "Close" may read better after the fact; owner call.
  • AD9 has no typed ERASE. The D1 rule asks for one on large irreversible actions, but this erase already sits behind a two-device approval. Flip it if the owner wants D1 applied strictly.
  • App name: copy avoids naming the app; the mark carries the brand. Host stays the placeholder medtracker.example. The second devices screenshot (test-vault/71-…) isn't in the project; reviewed against 38-settings-devices only.
