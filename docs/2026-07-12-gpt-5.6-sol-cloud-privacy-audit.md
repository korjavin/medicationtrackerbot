# GPT-5.6 SOL — Cloud privacy architecture audit

**Date:** 2026-07-12  
**Scope:** the current cloud product (`cmd/cloud`, `internal/cloudserver`,
`internal/cloudstore`, `web/cloud`, relevant shared frontend code), Beads design
history, `docs/cloud-mode.md`, `docs/cloud-crypto.md`, and completed cloud plans.  
**Out of scope:** a formal cryptographic proof, infrastructure penetration test,
live production configuration review, and the legacy bot/mobile products except
where current documentation still presents them as part of the cloud strategy.

## Executive conclusion

The cloud vault has a strong and coherent zero-knowledge core. Health records
are encrypted in the browser, passkey PRF outputs and the DEK remain client-side,
recovery material has high entropy, server synchronization stores ciphertext,
and the codebase contains unusually useful architecture and drift tests.

The product around the vault is not uniformly zero-knowledge. Trial AI,
Telegram, hosted MCP, the operator-default food database, voice providers, and
operational metadata have different privacy boundaries. The largest present
problem is therefore boundary accuracy: top-level documentation and onboarding
make unconditional claims which are true for the encrypted vault but false for
the entire product.

Recommended product language:

> Your vault and synced health records are end-to-end encrypted. Optional
> integrations have separately disclosed privacy boundaries.

“Zero-knowledge vault” is supportable. “The operator is cryptographically unable
to read any of it” is not supportable while plaintext opt-in relays exist.

Overall assessment:

| Area | Assessment |
|---|---|
| Vault cryptography and key separation | Strong |
| Authentication and recovery design | Strong, pending external review |
| Server-side deletion coverage | Strong at the logical-row level |
| Browser/XSS containment | Improved, but remains the dominant technical risk |
| Local-device deletion | Incomplete/unreliable |
| Integration and metadata disclosure | Incomplete |
| Operational retention documentation | Missing |
| Architecture documentation | Rich history, weak current source of truth |
| Small trusted beta | Reasonable after P0/P1 fixes below |
| Broad “zero-knowledge health platform” claim | Not ready |

## Threat-model boundary used in this audit

The audit separates four promises which must not be conflated:

1. **Vault confidentiality:** can the cloud read stored or synchronized health
   records?
2. **Feature confidentiality:** can the cloud or a provider read data used by an
   optional feature?
3. **Metadata privacy:** what can be inferred from timing, identifiers, sizes,
   endpoints, and provider choices?
4. **Client integrity:** can the origin serve code which reads an unlocked vault?

The implementation performs best on the first promise. Most findings concern
the other three.

## Findings

### P0 — Top-level privacy claims exceed the implemented boundary

`docs/cloud-mode.md` currently says that the operator is cryptographically
unable to read “any of it,” that the cloud provides “exactly three things,” that
a full breach yields ciphertext and timing metadata “nothing else,” and that
server-side AI proxying is a non-goal.

Implemented exceptions include:

- trial OpenAI-compatible request bodies crossing the cloud in plaintext;
- inbound and outbound Telegram text crossing the relay in plaintext;
- hosted MCP query content visible in transit;
- operator-default food queries crossing the same-origin proxy;
- Telegram bot credentials recoverable by a server holding `SESSION_SECRET`;
- hosted MCP tokens and pairing keys stored in `mcp_remote`;
- push endpoints, chat IDs, egress provider hosts, usage counters, timestamps,
  sizes, and other operational metadata.

This is primarily a product/trust-model defect, not a failure of vault
encryption. Correct the executive claims, landing page, onboarding copy, privacy
page, and architecture diagram so they describe an E2EE vault with explicit
integration carve-outs.

### P0 — The documented trial-provider consent ceremony is not implemented as stated

The design promises a separate explicit consent screen for trial provider keys.
The current first-run flow explains the shared trial and offers “Skip — use the
trial key,” while the runtime automatically selects the trial path when no BYO
key exists and the trial flag is enabled. No dedicated durable consent record
or first-use consent gate was found.

For health-related prompts, photos, summaries, audio, and transcripts, “the user
did not enter a key” should not be treated as consent. Before the first trial AI
or voice request, name the data categories, the operator relay, and the provider
account; require a positive choice; persist the choice in the encrypted vault;
and allow revocation in Settings.

### P1 — User-facing privacy coverage omits implemented egress

The Settings privacy page describes AI mostly as meal parsing. It does not fully
cover:

- ElevenLabs audio, transcripts, tool names, and tool results;
- trial voice under the operator's ElevenLabs account;
- gamification summaries sent for AI narration;
- Telegram free text sent to the unlocked-tab agent/provider;
- non-food uses of the OpenAI-compatible client;
- the distinction between direct BYO food lookup and the operator-default
  same-origin food proxy.

The existing drift test checks only entries with a non-null `docSignal`.
Important exceptions deliberately use `docSignal: null`, so the guard can stay
green while material disclosures are missing.

Replace the hand-maintained dual list with one structured privacy/egress
manifest. Each feature should declare data categories, destination, operator
visibility, persistence/retention, activation/consent mechanism, and BYO/trial
behavior. Generate both the documentation table and the in-app view from it.

### P1 — Local account deletion does not reliably erase the browser vault

Server deletion has an effective schema coverage guard and removes all current
`account_id` rows in one transaction. The browser cleanup is weaker:

- `indexedDB.deleteDatabase('medtracker-cloud')` is not awaited;
- success, failure, and `blocked` are ignored;
- open database handles may prevent deletion;
- the service worker is not explicitly unregistered;
- the push subscription is not explicitly unsubscribed;
- deletion is not verified before navigating away.

The server can therefore report successful account deletion while plaintext
records or warm-unlock material remain in the browser profile. Close local
handles, unsubscribe/unregister, await and verify database deletion, surface a
failure, and add an integration test for a blocked/open IndexedDB connection.

### P1 — Retention and erasure semantics are undocumented

Deleting SQLite rows is not physical erasure. Old values may remain in WAL/free
pages, volume snapshots, database backups, reverse-proxy logs, or system logs.
Data already transmitted to Telegram, AI providers, food databases, RxNav, push
services, or ElevenLabs is governed by those parties.

Add an operator security/retention document covering:

- application and access-log fields and retention;
- database backup schedule and expiry;
- deletion propagation to backups;
- SQLite WAL/checkpoint and secure-delete policy;
- treatment of capability URLs in proxy logs;
- subprocessors/third parties and transmitted data categories;
- incident response and user notification expectations.

User-facing deletion copy must distinguish immediate logical deletion from
backup expiry and third-party retention.

### P1 — Sensitive endpoints and capability paths can enter logs

Push failure paths log complete subscription endpoints. These are durable
per-device identifiers and should be replaced with a keyed hash or short
fingerprint.

Hosted MCP capability tokens travel in URL paths. The application avoids
logging them, but common reverse proxies log request paths by default. The
deployment guide should require redaction or disabled access logging for
`/mcp/*` capability paths, and tests/configuration should make the safe default
obvious.

### P2 — Browser-delivered code remains the dominant confidentiality risk

The documentation correctly recognizes that the cloud origin can serve modified
JavaScript which exfiltrates data after unlock. That caveat is central to the
threat model, not a minor limitation.

The CSP is substantially better than the former wildcard egress posture, but:

- the DEK-bearing document permits `script-src 'self' blob: data:` for voice
  worklets;
- an executing XSS can update the egress-host allowlist and force a reload;
- same-origin trial/proxy endpoints are allowed egress paths;
- the operator controls all same-origin JavaScript in any case.

Review whether worklet-specific directives can remove `data:` and/or `blob:`
from general `script-src` on supported browsers. More importantly, add release
integrity measures appropriate to a PWA: reproducible artifacts, a signed build
manifest, published hashes, and an independent browser-crypto/WebAuthn review.
Do not present the frozen mobile build as the current mitigation.

### P2 — Device removal is not compromise recovery

Removing a device deletes its credential and envelope and invalidates its
server session, but does not rotate the DEK/NK. A stolen unlocked device retains
previously synchronized plaintext and key material. The crypto document records
this honestly; the main security overview and device-removal UI should state it
with equal prominence.

Supportable language today is “retire a device.” Fully evicting a compromised
unlocked device requires a designed DEK/NK rotation and re-snapshot/re-wrap
ceremony.

### P2 — Metadata can carry health signal

Reminder timing, blob sizes, sync cadence, inbox arrival times, Telegram use,
and provider hostnames are not plaintext health records, but may still reveal
behavioral or treatment patterns. The current copy often frames them as ordinary
metadata with “no health content,” which understates inference risk.

Call this “potentially sensitive metadata.” Padding, batching, reminder-time
bucketing, or dummy traffic may be future options; at minimum, make the accepted
leakage explicit.

### P2 — Session timestamps lack a future-time bound

Session verification rejects tokens older than the TTL but does not reject a
timestamp materially in the future. Tokens are server-authenticated, so this is
not an external forgery path; clock rollback or an accidentally future-minted
token can nevertheless extend a session. Enforce a small forward-skew allowance.

### P2 — Beads workspace permissions are broader than recommended

The local `.beads` directory is mode `0775`; Beads recommends `0700`. The issue
database contains security findings, operational incidents, identities, and
implementation context. Unless shared Unix-group access is intentional, reduce
the directory permission to `0700`.

## Documentation quality

The project has valuable design history but no dependable current cloud
architecture source of truth:

- `docs/cloud-mode.md` calls itself a proposal while describing shipped code;
- it mixes normative behavior, obsolete design, implementation notes,
  aspirations, open questions, and historical debates;
- it says subdomains are server-assigned near the top and client-generated
  later;
- it says bot/server mode is not being replaced despite the current direction;
- it presents the frozen mobile build as a current stronger-security route;
- `docs/architecture.md` primarily documents the legacy bot/server system;
- completed plans are useful history but should not be normative references.

Recommended structure:

- `docs/cloud/architecture.md` — current components and data flows only;
- `docs/cloud/threat-model.md` — actors, assets, assumptions, and residual risk;
- `docs/cloud/privacy-boundaries.md` — generated integration disclosure;
- `docs/cloud/crypto.md` — normative formats and ceremonies;
- `docs/cloud/operations-security.md` — secrets, logs, backups, retention, IR;
- `docs/cloud/onboarding.md` — current onboarding and recovery behavior;
- `docs/cloud/deletion.md` — server/device/backup/third-party semantics;
- legacy bot/mobile material clearly marked or moved under `docs/legacy/`;
- `docs/plans/completed/` explicitly treated as historical/non-normative.

## Strengths to preserve

- High-entropy recovery rather than a human password.
- Client-only passkey PRF output and DEK.
- Domain-separated HKDF/AES-GCM constructions with identity-bound AAD.
- Atomic first credential + envelope registration.
- Recovery rate limiting and forced recovery-code rotation.
- Credential-existence checks which make server sessions revocable.
- Public-key sealed inbox which refuses plaintext storage before key setup.
- Application-layer reminder encryption in addition to Web Push encryption.
- Fixed client-authored server-warning notification text.
- Schema-driven account-deletion coverage test.
- Encrypted provider-key vault records.
- No intentional third-party JavaScript on the DEK-bearing page.
- Clear Telegram disclosure relative to typical bot products.
- Download/print-gated Emergency Kit UX.

## Recommended execution order

1. Correct privacy claims and add explicit trial consent.
2. Fix and verify local deletion.
3. Establish the privacy manifest and complete integration disclosures.
4. Stop sensitive endpoint/capability logging and document retention.
5. Split current cloud architecture from legacy/history documentation.
6. Harden session skew and local Beads permissions.
7. Commission an external browser-crypto/WebAuthn review.
8. Design compromised-device key rotation as a separate high-risk project.

## Validation performed

This was a read-only architectural review. It inspected implementation and test
coverage but did not modify or execute production flows. No formal claim is made
about live reverse-proxy configuration, production secrets, provider retention,
or real-device WebAuthn behavior. Those require separate operational and
external review.
