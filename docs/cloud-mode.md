## The install story

> Open the claim link → get `https://amber-falcon-8k3q9x.app.<cloud-domain>` → sign in with Face ID / fingerprint (a passkey) → Add to Home Screen, with the Emergency Kit offered when sync is turned on from Settings and reminded by Settings otherwise. Done. Reminders fire, data syncs across devices, camera/AI/voice features unlock as the user adds their own provider keys. The operator is *cryptographically unable* to read the vault: the DEK never leaves the browser, and sync and reminder content are stored only as ciphertext.

The vault path is the whole default product: **hosting** (a trusted HTTPS origin per user), **storage** (encrypted blobs), and a **push relay** (a blind alarm clock). All domain logic and all BYO-key provider calls run in the browser. Separate from that path, a handful of **opt-in integrations deliberately leave the vault boundary** — they are enumerated in [Privacy boundary — the vault promise and its carve-outs](#privacy-boundary--the-vault-promise-and-its-carve-outs) and must never be described as end-to-end encrypted.

## Goals / non-goals

Goals:

- Zero install effort: no server, no DNS, no certs, no app store. One URL, one passkey — no passphrase to memorize.
- Zero-knowledge vault: a full server breach, subpoena, or malicious operator yields ciphertext plus the operational metadata in [Metadata leakage summary](#metadata-leakage-summary) — never a health record. Opt-in integrations are outside this guarantee and are enumerated separately.
- Full PWA capabilities on iOS ≥ 16.4 and Android: installed home-screen app, offline, camera, barcode, web-push reminders.
- Multi-device with durable backup — the cloud copy is the source of truth; browser storage is a cache.
- BYO keys: OpenAI(-compatible), vision, ElevenLabs (food DB values stored by older builds still apply) — stored inside the encrypted vault, used directly from the browser.
- Optional Telegram channel when the user brings their own bot token.

Non-goals:

- Server-side plaintext on the *vault* path. (This is **not** "no server-side proxying at all": the operator-trial AI/voice proxies, the operator-default food proxy, the Telegram relay, hosted MCP, and the Mi Band backup parser all handle plaintext by design. They do not share one activation story — see [Privacy boundary](#privacy-boundary--the-vault-promise-and-its-carve-outs).)
- Server-side domain logic. The server cannot compute a schedule, merge a conflict, or answer a query, because it cannot read the data. Anything that needs to read the vault runs in an unlocked browser tab or does not exist.
- Multi-user accounts / sharing (future work, needs asymmetric sharing crypto).

## Architecture

```
┌────────────────────────────── user's devices ─────────────────────────────┐
│  Installed PWA (per-user origin)                                          │
│  ├─ web/static UI — talks only to /api/*, which never leaves the tab      │
│  ├─ /api/* shim → in-browser domain layer (JS port) → Dexie/IndexedDB     │
│  ├─ WebCrypto vault (DEK; unlocked via passkey PRF envelopes)             │
│  └─ direct calls: api.openai.com, ElevenLabs, food DB (user's own keys)   │
└──────────────┬─────────────────────────────────────────────────────────────┘
               │ TLS; bodies are ciphertext
┌──────────────▼──────────────── the cloud ──────────────────────────────────┐
│  static host  *.app.<domain>  (one PWA bundle, wildcard cert)              │
│  blob sync API      — encrypted oplog + snapshots, per-account cursors     │
│  push relay         — (fire_at, ciphertext) queue → Web Push (RFC 8291)    │
│  telegram sender    — optional, BYO token; sealed inbound mailbox          │
│  mcp relay          — optional, blind WebSocket pipe (see MCP section)     │
└──────────────┬──────────────────────────────────────────────────────────────┘
               │
        FCM / APNs / api.telegram.org
```

## Privacy boundary — the vault promise and its carve-outs

This is the canonical statement of what the product promises. Every other
surface (README, landing page, signup wizard, Settings → *What can the operator
see?*) restates **this** promise and never a broader one.

> **The promise.** Your vault — every health record you store and sync — is
> end-to-end encrypted. The keys never leave your devices, and the server holds
> only ciphertext it cannot open. Optional integrations you turn on reach
> outside that vault and have separately disclosed boundaries.

The first sentence is unconditional and true: `web/cloud/js/crypto.js` generates
the DEK in the browser, wraps it under passkey-PRF envelopes, and nothing but
ciphertext is ever `POST`ed to the sync API. The second sentence is the part
that top-level copy used to omit.

**Any absolute phrasing that extends the vault guarantee to the whole product is
false** — it contradicts the rows below. The specific banned phrasings, and the
copy surfaces they are enforced across, live in the `BANNED` list of
`web/cloud/js/tests/architecture.privacy-claims.test.js`; that test fails CI if
one comes back. Equally, do not "fix" a claim by hedging the vault away: the
same test asserts the vault half of the promise is still stated.

### The boundary table

Every row below is an implemented data flow. **They do not share one activation
story, and flattening them into "all opt-in" is the regression this table exists
to prevent.** Three activation classes for the rows that leave the device:

1. **Off until the user turns them on** — Telegram, trial AI, trial voice,
   hosted MCP (tier 2).
2. **No toggle; active whenever the feature is used** — the operator-default
   food DB (a BYO endpoint removes the operator from the path) and RxNav drug
   lookups (always proxied; no BYO alternative exists).
3. **Always on, inherent to running the service** — operational metadata,
   including the plaintext record-type tag on every synced op.

Two further row kinds appear in the table: paths marked *not a carve-out*, which
are named so their strong wording is auditable rather than assumed, and rows
marked *stays on your device*, which never leave the device but are readable by
anyone holding it. The rows titled *iOS local mode* describe the iPhone app's
"Only on this device" mode (no account, no server; `web/cloud/js/local-policy.js`). The `How it is turned on` column states each row's class.
Third-party retention for each destination is in
[cloud-operations-security.md §5](cloud-operations-security.md#5-subprocessors--who-sees-what);
the metadata-only signals are also in
[Metadata leakage summary](#metadata-leakage-summary).

**This table is generated.** Its source is the privacy/egress manifest at
`web/cloud/js/privacy-manifest.js`, which is also what
`web/cloud/js/privacy.js` renders into Settings → Account & privacy → *What the operator can see*
(every row except the local-mode ones, `mode: 'local'`, which are not a cloud
account's).
Edit the manifest and run `pnpm privacy:docs`; editing the table by hand fails
CI. `web/cloud/js/tests/architecture.privacy-claims.test.js` additionally
derives the set of things that MUST be disclosed from the code — every
outbound-HTTP / server-side-plaintext file under `internal/cloudserver/` and
every literal third-party host in the Go and browser sources — so a new proxy,
upstream host, or plaintext path fails CI until a manifest entry claims it.

## Trust model — what the server can and cannot see

Model the cloud as honest-but-curious **and** breachable. Design so that even a hostile operator learns nothing beyond metadata.

| Server **never** sees | Server **necessarily** sees (metadata) |
|---|---|
| Health data (meds, BP, weight, food, sleep, diary, workouts) | Account exists; subdomain name; creation date |
| Provider API keys (OpenAI, ElevenLabs, food DB) | Blob counts/sizes, sync timestamps, client IPs |
| DEK, passkey PRF outputs, recovery code | Reminder **timing** (when pushes fire, not what) |
| Reminder content (two-layer encrypted) | Push subscription endpoints (reveals browser vendor) |
| Any plaintext record, ever | Optional: email (URL recovery only), TG bot token + chat id (opt-in) |
| **Inbound** Telegram message content, at rest — sealed to the inbox key on arrival | **Outbound** Telegram reminder text *and* command confirmations, at the user's chosen verbosity (client-composed, forwarded verbatim) |
| What an inbound message *means* — the relay never parses it and never calls AI on it | **Inbound** Telegram message content, **transiently in memory** — Telegram delivers bot updates in the clear; the relay cannot un-see them before sealing |
| Meal photo pixels, at rest — only the Telegram `file_id` (plus the caption, sealed like any inbound text) is stored | That an inbound message arrived, its size, and its timestamp |

The last three rows are the **inbound** posture, decided in `med-eas.29.1` and specified under [Inbound plaintext — what the relay may do](#inbound-plaintext--what-the-relay-may-do). The distinction that carries the whole design: *transiently in memory* is not the same exposure as *at rest*, *logged*, or *sent to a third party*. Telegram already sees every inbound message; the relay's job is to add nothing to that.

**The honest caveat — code serving.** E2EE fully protects data at rest and in transit against the server. It cannot protect against the origin serving *poisoned JavaScript* that exfiltrates the key on next unlock — the fundamental limit of web-delivered cryptography (why Signal ships signed binaries). Mitigations, in increasing strength: subresource integrity + versioned immutable assets; service-worker-pinned bundles with update prompts (an installed PWA runs cached code — a hostile update requires the SW to accept it, which narrows the attack to update time); reproducible builds published to a transparency log; and ultimately, users who need stronger guarantees would need a store-distributed native shell against the same cloud (the cloud then serving only blobs + push, never code) — not something this repo ships. The proposal accepts this residual risk for the PWA tier and documents it in user-facing security notes. The same limit bounds the add-a-device hand-off ([cloud-crypto.md → Path B](cloud-crypto.md), protocol v2): poisoned client code or a hostile landing page defeats it; after Approve, Cancel cannot recall the released ciphertext (the server deletes it on `DELETE`/redeem and an honest new device discards it past expiry); and revoking a device cannot un-copy records it already synced.

**Code coherence per deploy (`med-5h1t.6`).** The service worker (`web/cloud/sw.js`, `warmShell`) precaches each deploy's JS module graph all-or-nothing at install: if any crawled module fails to fetch, the install rejects, the partial cache it created is deleted, and the previous deploy's complete cache keeps serving until a later install succeeds — an install never leaves a precached crypto/unlock/sync graph assembled from two deploys. (Runtime writes are outside this guarantee: the active worker's cache-miss fill and its `/` document revalidation still write current-server responses into its own cache.)

## Accounts, subdomains, hosting

- Per-user origin: `https://<petname>-<random>.app.<cloud-domain>` (e.g. `amber-falcon-8k3q9x`). **The subdomain and the `account_id` are server-assigned at provisioning time**, not client-generated — `randomSubdomain()` and `randomToken(16)` in `internal/cloudserver/provision.go:83,87,159-173`, persisted by `CreateAccount`. Only *key* material (DEK, KEKs, passkey PRF outputs, recovery code) is client-generated; the client reads its server-assigned account id out of the WebAuthn creation options (`web/cloud/js/signup.js:141-144`).
- **Why per-user subdomains** (not one origin + accounts):
  - Browser storage, service workers, and push subscriptions are *per-origin* — each user's install is fully isolated by the platform, no multi-account state to manage.
  - The unguessable name is a capability-style outer moat (defense in depth — real auth still applies; see key hierarchy).
  - The home-screen icon is inherently "your instance"; no login-switching UX inside one origin.
- **Wildcard everything so individual names never leak**: wildcard DNS record (`*.app.<domain>` — names absent from the zone) and wildcard TLS cert via DNS-01 (names absent from Certificate Transparency logs). Residual leak: DNS queries and TLS SNI expose the subdomain to network observers (mitigated over time by DoH and ECH). This is why the subdomain is a moat, not the auth.
- One static bundle served for every subdomain; the API resolves the account from the `Host` header.
- Rate limits + storage quotas per account. Registration is **invite-only, always**: accounts exist only when the operator mints one (see Onboarding). No public signup surface exists — which also deletes the signup-abuse problem outright.
- **Local dev without DNS or certs**: `*.localhost` subdomains resolve without any `/etc/hosts` entry and are treated as a secure context by browsers, so `CLOUD_BASE_DOMAIN=localhost` gives a full local dev loop — including WebAuthn/passkeys — against `http://<sub>.localhost:<port>`.

## Onboarding — invite → wizard → installed PWA

**The invitation IS the claim link.** Minting an invite (`cloud admin invite`) pre-provisions the account (subdomain + one-time claim token) and yields an invite link — delivered by email, link, or QR. There is no public signup page; the base host serves only a static landing/education page with an "invitations only" note. Unclaimed accounts expire and can be re-issued.

**Two link forms, both valid** (bd med-ta2n.9). The token always rides the fragment, so it never reaches the server:

- **Claim form** — `https://<sub>.<base>/#claim=<token>`, minted until med-ta2n.16 and still valid forever. `cloud-boot.js` routes it to `/unlock#claim`; it is what the landing page hands off to and what the native shells store in their pending-invite slot.
- **Landing form** — `https://<base>/i/<sub>#<token>`, what `ClaimURL` returns since med-ta2n.16 and what every mint path hands out (admin CLI `invite` / `reset-claim`, `POST /api/invite` → Settings invite link/QR, managebot DM / email). Pre-v3 native shells (before iOS med-ta2n.11 / Android .12) reject it on their paste/scan screen ("That isn't an account link"); opened as a link it lands on the landing page in the browser, whose "Continue in the browser" still claims. The base domain serves the invite landing page there (`web/cloud/invite.html`, no-store, strict CSP) (`js/invite-landing.js`, med-ta2n.10, design L1–L3). It renders by state and platform: iPhone L1 → L3 ("Installed? Tap to continue", sticky per tab; "Open in the app" = `medtracker://i/<sub>#<token>`), Android L1 (Play link with the invite as install referrer — the "Play install referrer" row of the privacy boundary table), desktop L2 (a QR of the page URL), and an expired screen for `expired`/`claimed`. "Get the app" copies the landing URL to the clipboard before opening the store (the app's paste fallback), and "Continue in the browser" goes to the claim form. Store buttons come from the `medtracker-ios-app-store-id` / `medtracker-android-package` metas (`IOS_APP_STORE_ID` / `ANDROID_PACKAGE`); a missing one hides that button. The AASA file claims `/i/*` (`applinks`) and `assetlinks.json` covers it for Android, so with a v3 shell installed the link opens the app directly. The status read the page uses is `GET https://<base>/api/i/<sub>` (base domain only, per-IP rate-limited, no token, no session) → `200 {"state":"pending"|"expired"|"claimed","expires_at"?}`; `expires_at` comes only with `pending`, and an unknown or malformed subdomain answers `{"state":"expired"}`, so it is indistinguishable from a swept invite.

The claim link lands on a minimal, picture-first education wizard:

1. **Sign in** (bd `med-ta2n.8`, design W5) — "Sign in with Face ID / your fingerprint / this device", which creates the passkey without ever naming it; the trust model is one sentence ("The server stores your log but can't read it"), the full egress list lives in Settings → Account & privacy. (When trials are enabled, the trial-keys caveat gets its own explicit consent screen — see Trial provider keys.)
2. **Protect against device loss** — we *cannot* recover data, so offer, in order: confirm the passkey is synced (iCloud / Google Password Manager), add a second device now (QR flow), save the Emergency Kit. Since bd `med-ta2n.8` signup shows the kit only as an offer when entered from Settings (`#claim=<token>&kit=1`; Done is the acknowledgment, no gate; without the flag no kit page and no code at signup — the wizard files `how: 'none'` and the Settings Kit chip reminds), see [docs/onboarding-wizard.md](onboarding-wizard.md). On `/recover` and the regenerate flow it stays one page (bd `med-ckm5.2`): "I saved my Emergency Kit" is the acknowledgment (it POSTs `/api/loss-ack`) and unlocks Continue even without a download or print here, at the user's own risk — a warn note says so, and the synced `emergencykit` vault record (`{savedAt, how: download|print|ack|none}` — `none` = no saved kit for the current code: a new code issued and not yet confirmed, or a signup without the offer (no code yet); the newer `savedAt` wins; filed by `web/cloud/js/kit-state.js` on the next unlocked open, not exported in vault backups) lets Settings keep reminding until a kit is produced. Never ask for two passkeys on the *same* device — a second same-device platform passkey may silently replace the first (same RP + user handle) and dies with the device anyway.
3. **Install + notifications, platform-aware** — detect iOS/Android and show matching add-to-homescreen steps. Ordering is load-bearing on iOS: **install first, then enable push** — web push only works inside the installed app and the permission prompt needs a user gesture there. Shown only when it can change the outcome (bd `med-eas.63`): a **mobile** browser that is not already `display-mode: standalone`. Desktop is never nudged — it delivers push to a plain tab — and the copy is platform-honest in both directions: iOS is told a Safari tab gets *no* push at all, Android is told push works either way and install is a convenience. There is **no auto-redirect into the installed app**: iOS has no API for it and Android's `beforeinstallprompt` only prompts an install, so guiding ("install, then reopen from your Home Screen and unlock with the same passkey") is the whole of what the platform allows. The escape hatch — "Continue in browser anyway" — never blocks.
4. **Telegram (optional, ships with C3)** — one tap on a Managed-Bots deep link creates the user's personal bot with a pre-filled dialog (see the Telegram section); explicitly skippable, with the channel-credential consent screen.

**The wizard ends by entering the app, not on a confirmation screen** (`enterApp` in `web/cloud/js/signup.js`, bd `med-8eh`). It establishes the LDK warm cache from the ceremony's DEK and navigates to `/`; the real `web/static` app boots, `/api/bootstrap` reports `needs_first_run: true`, and the first-run overlay mounts on top of it (see [docs/onboarding-wizard.md](onboarding-wizard.md)). The warm cache is written at that moment rather than right after passkey registration, so a user who abandons at the Emergency Kit offer (`&kit=1`) does not reload into an unlocked app with an unsaved recovery code; without the flag there is no code at signup and the Settings Kit chip carries the reminder. If the cache cannot be written (storage-blocked browser) the failure is swallowed and we navigate anyway: `cloud-boot`'s `warmUnlock` fails and routes to `/unlock`, where the just-created passkey signs in. Degraded, never dead-ended.

**A claim link that was already claimed routes to unlock, never to passkey creation.** `POST /api/webauthn/register/begin` returns `409 {"error":"already_claimed"}` when the account's claim token has been consumed *and* at least one credential is registered; expired, swept, or mismatched tokens on an account that is **not** claimed still get the plain-text `403 invalid or expired claim`. Once a claim is consumed its token hash is `NULL`, so there is nothing left to compare a presented token against — *any* non-empty `claim_token` on a claimed account answers `409`. Nothing leaks: reaching the subdomain at all already reveals the account exists, and the wizard's own probe replays the same token. The wizard probes that endpoint on load (before rendering anything) and shows an "already claimed" screen — unlock with your existing passkey, or open the app on your former device and share access from there. Edge case: an account whose claim was consumed but whose credentials were *all* later deleted (possible once recovery material exists) has no credentials to discriminate on, so it falls back to the `403` expired-link copy.

**The wizard is stateless — no stored step counter.** iOS Safari tabs and installed PWAs have separate storage, so locally-persisted progress dies at the install boundary. Every step is instead derived from observable facts: passkey exists (server credential list), loss-protection acknowledged (server-side flag), running installed (`display-mode: standalone`), push subscription exists (server). Opening the app in any context computes the first unmet step and resumes there; passkeys carry across the boundary via the platform keychain, so re-unlock works even though local caches don't transfer.

### User-mintable invites

Invites are not admin-only: any signed-in account can mint one for a friend from its own subdomain via `POST /api/invite` (session-authed, same host-routed `/api/*` mux as devices/sync/push). It runs the same `Provision()` path as `cloud admin invite` — server-assigned subdomain, one-time claim token, per-account VAPID keypair — and returns `{"subdomain", "claim_url", "expires_at"}`. The token exists only in that response body and travels in the claim URL's fragment; the store keeps only its hash. Settings → "Invite a friend" shows the claim URL with a copy button and a client-rendered QR code.

**Quota: 100 invites per account per rolling 30 days**, counted in SQL, not memory — `accounts.created_by_account_id` (migration `010`, NULL for admin-CLI invites) records the minter, and the endpoint counts that account's rows with `created_at_unix` inside the window. Over quota: `429 {"error":"invite limit reached","limit":100,"window_days":30}`. Counting rows rather than mints means `SweepExpiredClaims` reaping an unclaimed invite gives the quota back — deliberate, since the limit is about *users* created, not links clicked. `ponytail:` a patient abuser can therefore recycle expired invites; swap in an append-only mint log if that ever happens. Note that `created_by_account_id` also holds `tg:<uid>` rows minted by the managebot — not every value is an account id, see [Managebot onboarding](#managebot-onboarding--invites-over-chat).

## Operating the cloud — admin surface

Deliberately PII-free: no names, no emails in listings (the optional URL-recovery email is the single stored exception). ## Key hierarchy

**Passkey-only — no passphrases anywhere.** Full specification (exact formats, HKDF domains, ceremonies, security analysis): [docs/cloud-crypto.md](cloud-crypto.md).

```
passkey₁ ──WebAuthn PRF──► KEK₁ ──► envelope₁ ┐
passkey₂ ──WebAuthn PRF──► KEK₂ ──► envelope₂ ├──► DEK (random 256-bit) — encrypts all data
recovery code (160-bit, Emergency Kit) ──► KEK_rec ──► envelope_rec ┘
account inbox keypair (ECDH) — public half on server, private half in vault
```

- **DEK** is random, generated at signup; all records are AES-256-GCM under keys derived from it. Enrolling/removing a passkey = add/delete one envelope; data is never re-encrypted except on deliberate rotation.
- **Each device enrolls its own passkey** (device-local, non-synced passkeys fully supported) and gets its own DEK envelope via the WebAuthn PRF extension — biometric-gated, high-entropy, phishing-resistant. Synced passkeys (iCloud/Google) make one envelope serve a whole device fleet, but are never required.
- **Auth** to the API is standard WebAuthn assertion verification → per-device session tokens. PRF outputs are client-side only and never transmitted.
- **Recovery code** (printed in the Emergency Kit) wraps the DEK as the last-resort envelope; a domain-separated verifier lets the server rate-limit recovery attempts without learning anything that decrypts.
- **No low-entropy secret exists anywhere** — nothing server-side is offline-crackable, an upgrade over any passphrase design.
- **Inbox keypair**: lets the server (or the Telegram path) append events *sealed to the user* that only the client can read — see Telegram and MCP sections.

## Sync protocol

- **Encrypted oplog**: each write produces `{account_seq, device_id, record_type_tag, nonce, ciphertext}`. Server assigns the monotonic `account_seq`; clients push local ops and pull `since=<cursor>`. This mirrors a change-events + download-cursor design, with ciphertext bodies.
- **Conflict resolution is client-side** (server can't merge what it can't read): last-writer-wins per record on `clientTs`.

  `clientTs` is a **merge token, not a wall clock** (bd med-d5t.6). It used to be the writing device's raw `Date.now()`, which made LWW obey whichever device's clock ran fastest: a phone ten minutes fast would win against a correctly-clocked laptop's *later* edit, and the laptop's fix was dropped silently. On a medication tracker that is the worst failure mode there is — quiet, plausible, and about dosage. Two local guards, neither touching the envelope format nor the server:

  1. **Server-referenced time.** Every sync response already carries a `Date` header — the server's own clock, for free. `noteServerDate` measures the offset into `sync_meta.clockSkewMs` and writes subtract it, so every device stamps on one scale.
  2. **A per-record monotonic guard.** A write to a record this device can already see is stamped `max(correctedNow, existing.clientTs + 1)`, so editing what you can see always beats what you are overwriting, whatever either clock says. This is what fixes the phone-then-laptop case outright.

  3. **A floor for materialized rows** (bd med-d4w, bd med-9a87). A row that a *read path* lazily derives into a **deterministic recordId** is stamped `clientTs: 0`, never `correctedNow`. Such a row is re-derivable on every device, so a client whose mirror is stale re-creates that same recordId in its *initial* state — `PENDING` dose, `pending` session. Stamped with a real timestamp that stale re-creation is the newest write, and LWW erases the real state underneath it. A floor makes materialization lose the merge against a real write, which is exactly its standing: **it only ever needs to win against nothing at all.** Guard 2 does not cover this — it only fires when the writing device can already *see* the record, and the whole failure mode is a device that cannot.

     **The floor rides on an atomic put-if-absent** (bd med-qhpu), because a floor alone is not enough. `writeRecord` applies guard 2 unconditionally and `getRecord` reads the *raw* store, tombstones included, so a floored row used to be promoted to `existing.clientTs + 1` whenever any raw row already occupied that recordId — the exact promotion the floor exists to prevent. `recordsPort.putIfAbsent` (`writeRecord`'s `ifAbsent` mode) is the derived-write primitive instead: under `withRecordsLock` it writes only into an **empty raw slot**, treats a tombstone as occupied, stamps the floored `clientTs` verbatim (no skew correction — derived bodies must stay byte-identical across devices, bd med-8j12), and resolves to the **stored winner** rather than overwriting it. `applyIncoming` takes the same lock, so an incoming op cannot land between the absence check and the put. A caller that loses decides what that means: `getNext` drops the day and surfaces the next occurrence.

     A slot the *derived* path finds tombstoned therefore stays empty, which makes **who tombstones a slot** load-bearing. For workout sessions only a deliberate `deleteSession` does — `nextVariant` is now an explicit **replacement** of the slot (cascade the logs, advance the rotation, write the new variant as a real wall-clock write) rather than a delete that leant on the next `getNext` re-materializing over the tombstone. Any new derived write must ask the same question: *is there a delete path whose recovery depends on re-materialization?* If yes, make that path write what it wants instead of deleting it.

     A session tombstone therefore means "no workout that day" to **every** reader, not just `getNext` (bd med-w0fe):
     - `findOrCreateScheduledSession` probes the raw slot (`listRaw`, a READ — the body it mints is a real wall-clock write and must keep guard 1's skew correction, which `putIfAbsent`'s verbatim stamp would drop) and returns null on a tombstone: a Telegram Snooze/Skip tap on the already-sent reminder no-ops instead of minting a fresh body that guard 2 would promote above the tombstone, and `startSession`'s med-gmyf re-key mints an ad-hoc session (same as for a day already finished).
     - The reminder horizon reads the **raw** session rows (`recordsPort.listRaw`, the one reader that needs them) and treats a tombstone at `session-<groupId>-<date>` as that day suppressed. Before, `sessionStatusByKey` saw only live rows, so a deleted day read as "not materialized yet": the card skipped it while Telegram kept asking about it, and tapping Snooze/Skip re-materialized the slot.

     Deleting is therefore a **one-way door for that day**, including a day already completed and deleted from history: nothing re-materializes the slot, so the card, the horizon and the Telegram buttons all stay silent for it until the next occurrence. A vault export carries tombstones at these slot ids (`TOMBSTONED_SLOT_TYPES` in `web/domain/vault.js`), so the day stays deleted across an export/import round trip.

     Materializers: `web/domain/workout.js`'s `getNext` (the day's session) and `web/domain/medintake.js`'s `ensureLedgerCut` (the `ledgercut` singleton, bd med-wi09.12) use `putIfAbsent`, as does `web/domain/stock.js`'s `ensureSeed` (bd med-wi09.13): before the first stock-moving write on a tracked med that has no `stock` audit yet, it writes a seed audit at `stock-<medId>-<ms>-seed<count>`, `clientTs: 0`, whose count is back-projected from the legacy `inventory_count` mirror (`inventory_count + TAKEN − refills`) and which has no window start, so every past movement still counts. Two devices that seed concurrently write different ids. That's harmless: the earliest seed starts the window and later ones are ignored once any real audit exists. `materializeDueDoses` (dose targets) was retired by med-wi09.12 — doses are now derived (see Ledger cut below); the history in this paragraph describes it before that. Two paths tombstone an intake slot and both now stick, where the sweep used to promote a floored placeholder over them and hand the dose back (bd med-j2ku): `deleteFutureIntakes` (future `PENDING` only) and `medications.js`'s `cancelPendingIntakesForMedication`, which archiving a med runs over **any** `PENDING` dose, today's already-due slot included — so un-archiving the same day no longer restores that dose (the next day's slots have their own ids and materialize normally). Same second consequence as sessions, fixed for the **push path** (bd med-x7x2): the reminder horizon reads the **raw** intake rows too (`recordsPort.listRaw`, `web/cloud/js/reminders.js`) and drops any forecast target whose deterministic `intake-<medId>-<slotUnix>` id is tombstoned. Before, it suppressed a slot only on a `TAKEN`/`SKIPPED` intake and skipped tombstones outright, so a deleted future dose was still pushed as "Time to take" and tapping Confirm on it recorded nothing. That tap is now only reachable for a push already in flight when the dose was deleted; the drain's exact-id lookup reads the raw slot, sees the tombstone and treats that med as a silent no-op (since bd med-wi09.4 there is no band fallback at all), so it creates nothing and reports no confirmation (a tap whose every named slot is tombstoned answers "Nothing was due", bd med-944k). **A deleted dose is now a one-way door in the app too:** `upcomingDoses`, `nextIntake` and `triggerNextIntake` all read `medintake.js`'s one projection over the **raw** intake rows (bd med-wi09.1, med-wi09.18), where a tombstone hides its slot, so none of them lists the deleted dose and `triggerNextIntake` (which confirms exactly the cluster `nextIntake` shows, at each row's own id) never mints a row over it. See [Incident: a stale tab erased a finished workout](#incident-a-stale-tab-erased-a-finished-workout-bd-med-9a87).

     The reminder delivery pref takes the floor as a default, not a materialized row (bd med-5vy0): account reminders always named what was due until the lock-screen pref governed them too, and an absent `reminderdeliverypref` reads Generic. All three writers go through `web/domain/reminders.js` `floorDeliveryPref(verbosity)`, which writes a fixed body via `putIfAbsent` only when no pref is stored. There are two bodies:
     - **Detailed:** `{clientTs: 0, delivery: 'webpush', lockscreen_default: 'detailed'}`, with `verbosity` **absent**. Clients from before med-5vy0 read `verbosity` as the Telegram opt-in, and to them absent means Generic, so an older writer never carries a floored Detailed into Telegram plaintext. New clients resolve the lock-screen text (web push body, shell rows) as explicit `verbosity` → `lockscreen_default` → Generic. Telegram reads `verbosity` only.
     - **Generic:** `{clientTs: 1, delivery: 'webpush', verbosity: 'generic'}`. This is **the one exception to the floor-0 rule**. Two devices that derived different defaults would otherwise hold two bodies at the same `clientTs`, and strict-`>` LWW would never converge them. At 1, Generic wins the tie on every device, because between two defaults privacy wins. Any real write (`now()`) still beats both. So "floor" for this record means `clientTs` 0 or 1, and `replaceAllRecords`' pending overlay (`web/cloud/js/sync.js`, `FLOOR_MAX_CLIENT_TS`) discards a pending floored row (`clientTs <= 1`) whenever the snapshot holds the same record with a higher `clientTs`, dropping its op too. A queued Generic default therefore yields to a newer explicit pref compacted into a snapshot, and still stands over the Detailed floor.

     The writers:
     - the account recompute (`web/cloud/js/reminders.js` `recomputeAndPush`) floors `'detailed'` when the vault has a medication, so existing accounts keep the names they always saw;
     - the first-run picker (`PUT /api/settings/reminder-delivery {floor: 'auto'}`; the shim picks `'detailed'` if a live medication exists, else `'generic'`) gives a new account Generic before its first medication, so the recompute floor finds a record and stays out;
     - the RD1/RD2 sheets closed without a change (`{floor: 'generic'}`, account mode) store Generic only if nothing is stored, so skipping never overwrites another device's pick. A changed pick is a real `now()` write.

     Any real choice on any device wins; a stored value (a Telegram user's Generic included) is never touched. Local mode never writes a floor (its absent pref stays Generic). `setDeliveryPref` writes an explicit `verbosity`, which replaces `lockscreen_default`. A channel switch that resends the shown lock-screen value unchanged keeps the Telegram verbosity, so a floored account that moves to Telegram or Both stores Generic, and its lock screen follows from then on (one field, one visible setting).

     The account zone takes the floor as a default too (bd med-wi09.19). With no pinned `settings.timezone`, every device used to resolve its own zone, so two devices projected different dose instants, occIds and reminders. Now `web/domain/settings.js` `ensureTimeZoneFloor(zone)`, called by the boot (`cloud-boot.js` → the router's `floorTimeZone`, after the boot pull and each drain until it has run; never from a request, so a read such as `GET /api/brief` touches only what it serves) once a pull in **this page load** has reached the tail (`sync.js` `pulledThisSession`, plus the shim's `caughtUp` so a pending local → cloud move pickup blocks it too: the router's `canFloor`; an offline boot of a synced device never floors against its stale mirror, and the inbox applier's agent router passes `canFloor: () => false`), writes `tzfloor` `{timezone, at: now()}` at `clientTs: 0` through `putIfAbsent` when neither a pin nor a floor is stored. `zone` is `web/domain/medintake.js` `evidenceZone()`: the zone the projection already reads today's dose evidence in (the last `evidenceTransitions` zone, from the same `evidenceFor` call and cut), else the device zone when nothing tz-stamped was ever logged. A device that floors therefore agrees with the past days every device already projects, so switching to the floor moves no slot that already passed (breakage F1: flooring the device zone made today's evidence-zone slot vanish while a forecast slot in the other zone fired). Settings never reads intakes. It is its own record, not a field on `settings`: that singleton is whole-record LWW, so a floored copy could not carry one field without losing (or winning) the merge for all of them. `getGeneral` reads pin → floor → device zone and reports which one as `timezone_source`; a stored zone this engine's `Intl` rejects (tzdata older than the writer's, e.g. `Europe/Kyiv` on an old WebView) is skipped for the next candidate but still names the source, so no floor is written over an unreadable pin, so an explicit pick (`setTimezone`, a real `now()` write on `settings`) wins whatever the floor holds. Travel still changes the zone through the tz plan, never through the device zone. **User-visible:** an unpinned account no longer follows the device on travel. A device whose zone differs from the account's gets the launch prompt (`bootstrap.js` `maybeUpdateTimezone` → `tzplan.js` `shouldPromptSuggestion`), which before this change never fired for an unpinned account; accepting pins the zone for the whole account, dismissing keeps home-zone times. A dismissal sticks account-wide for every dismissed detected zone (med-wi09.26): `dismissed_tz_suggestions` lists them (deduped, newest 10) beside the legacy `dismissed_tz_suggestion` string, which stays the newest one so older bundles keep comparing it to their detected zone; the list counts only while it holds the string (an older bundle's zone change clears the string but carries the list), and an actual zone change clears both. Two devices off-zone at once in different zones no longer overwrite each other, except when both dismiss before either pulls the other's write (whole-record LWW: one re-asks once). The Settings → Account row shows the zone, read-only until med-wi09.25. Two devices that floor before seeing each other hold two bodies at the same `clientTs`, which strict-`>` LWW never converges, so `tzfloor` is a `MERGE_POLICY` type (`mergeTzFloor`: earliest `at`, then the smaller zone name) and a `REPAIR_TYPES` one (the winner is re-stamped above both copies, so older bundles and compaction agree). Older bundles never read `tzfloor`; they keep resolving to their device zone until a pin exists. Local-only mode never floors: one device, nothing to keep in step, and it keeps following the device zone. Not in the vault (re-derivable; an import leaves it in place).

     `medications.js` backfills a med's `medsched-<medId>-<createdSec>-base` row (the schedule it had before history existed, bd med-wi09.9) the same way — `putIfAbsent` at `clientTs: 0` on the first schedule edit — so a device that created the med (a real write at that id) always outranks it.

     Imports keyed by a source id take the same floor: `web/domain/healthimport.js` (Apple Health, bd med-w6gx.6) writes `bp-hk-<uuid>` / `weight-hk-<uuid>` through `bp.js` / `weight.js` `create(…, { derived: true })` — `putIfAbsent` at `clientTs: 0` — so a second iPhone or a reset anchor re-reading the same HealthKit sample never overwrites an edit to it or resurrects a delete. Workouts and sleep days (bd med-w6gx.7) take the same floor directly (`miband-hk-<uuid>`, `sleep-hk-<day>`), with bodies built only from the HealthKit samples.

     **One deliberate exception: the legacy sleep conversion** (bd med-0xad.4, `web/domain/vitals.js` `unifyLegacy` over `healthsource.js` `unifySleep`) writes `sleep-hk-<day>` with a plain `put` at `now()`. It runs at boot and at the end of every `importAll`, triggered only by the presence of legacy rows (any live sleep row not at a `sleep-hk-<day>` id) or live `stresssample` rows, never by a flag; with none it writes nothing. In cloud mode it runs only on a mirror a pull in **this page load** brought to the tail (`sync.js` `pulledThisSession`; an offline boot, or one held by a pending forced snapshot, retries after each drain), because a stale mirror would fold a partial night at a later `now()` and outrank the full conversion another device made; a merge import is gated the same way, a replace import (the store is the file) is not. Local mode has nothing to pull and runs after the leave pickup. **The legacy rows are the ledger and the day row is its projection; no code deletes the ledger** (bd med-0xad.9). Per sleep day it folds ALL live legacy rows of the day into one body (the fold is over the ledger alone, never the day row plus the ledger, so a session is never counted twice) and puts it when it has more asleep minutes than the live day row, or equal minutes and a different body (so a tie against a Health day goes to the band, an equal-minutes correction reaches the projection, and an identical earlier projection writes nothing). A tombstone at `sleep-hk-<day>` holds: the day is never re-projected, and `visibleSleep` hides that day's live ledger too. Ledger rows are assumed append-only (no route edits or deletes a session; `importSamples`' guard only grows one). It is not floored because it has to win over a Health day it beats. A late session or a divergent ledger on another device folds on the next boot, once the union has synced. **Sync merges `sleep` by `healthsource.js` `mergeSleep`** (`sync.js` `MERGE_POLICY`, on local writes, pulled ops and pending-vs-snapshot): a ledger row is clientTs LWW (tombstones included), a day-row tombstone wins either side, else a day row goes to the FULLER (asleep minutes), then the newer clientTs, then the body (a total order, so the fold does not depend on arrival order), so a newer day row folded from a partial ledger cannot bury a fuller one. When that winner is not the clientTs winner, the merging device re-stamps it above both copies and queues it (`REPAIR_TYPES`), so older bundles and the compaction floor, which still merge by clientTs, agree; an incoming copy with the same body is never repaired, so repairs stop. A snapshot bootstrap (not a full-vault import, which replaces by intent) reduces acknowledged live local `sleep-hk-<day>` rows against the snapshot the same way, so an older bundle's compaction cannot bury a fuller day row. A peer's import usually arrives as such a snapshot with its bump op compacted away, so the importing device keeps its bump tombstone in the store (it rides in that snapshot and every later one): a snapshot carrying a bump this store does not hold is an unseen import and replaces without reduction. A Health day it beats is **discarded on purpose**: the Health importer meets the day as present and never re-imports it. The other direction is symmetric, so the pick does not depend on arrival order: when `healthimport.js` `importSleep` finds a Mi Band day (`source` not `apple_health`) with fewer asleep minutes than the settled Health day, it puts the Health body over it at `now()` (the same exception); a tie stays with the band. It also deletes every live `stresssample` row (stress is dropped). Cost: about one op per night of history, once. The `.nxk` drain (`vitals.js` `importSamples`, until bd med-0xad.6) stores its incoming sessions as ledger rows `sleep-<startMs>` again (put at `now()`, never downgrading a longer stored session, never over a tombstone), then folds, so a cumulative re-upload writes nothing and only a new or fuller night is written. Its stress stream is ignored. Days converted by #1413 (med-0xad.4, which tombstoned the ledger) keep their day row; a later session for such a day is hidden behind it, not lost (it stays in the vault and the export).

     **`total_minutes` is asleep-only on every sleep row** (bd med-0xad.4). Health days always used that definition. A converted Mi Band day takes `asleepMinutes` (light + deep + REM, else total − awake), where the Zepp figure included awake time. So historical band nights drop by their awake minutes everywhere that reads it: the Vitals chart and averages, the doctor brief, the analyses and the gamification sleep score. Naps fold into their sleep day too.

     **The floor also covers read/timer-side *transitions*** (bd med-y4ue). A record that already exists everywhere is not materialized, but a read or timer that flips its state is the same hazard one layer up: it rebuilds the record out of a mirror that may be stale, so `now()` lets it push state it never observed over newer state it never saw. These keep plain `put`, not `putIfAbsent` — the slot is occupied *by design* and the transition has to land in it — so here guard 2's promotion is the feature rather than the leak: a floored write becomes `existing.clientTs + 1`, i.e. **it beats exactly the version this device read, and nothing newer**; when it loses, the transition is simply re-derived from the winning record on the next read. Current floored transitions: `gamification.js` (`writeJournal({...}, { derived: true })` — `resolveElapsedChapter`, `getTraits`, `appendKeystone`, and `markDiscoverySeen`, which `journey.js` fires as a card *renders*, not from a gesture — plus `resolveElapsed`'s frozen verdict) and `tzplan.js`'s `refreshPlanStatus`. Deliberate user actions keep `now()` — editing on a stale device is ordinary LWW; the rule is *who triggered the write*, not which module it lives in.

     **Concurrent derivations of one singleton merge on apply** (bd med-ooeh). Two synced devices deriving *different* fields of the journal singleton both stamp `existing.clientTs + 1`; strict-`>` LWW kept neither op, and the next real write replaced the blob from one device's copy, dropping the field only the other derived. `applyIncoming` (`web/cloud/js/sync.js`, `APPLY_MERGE`) therefore folds the LWW loser's **grow-only** journal fields into the winner via `mergeGamificationJournal` (`web/domain/gamification.js`): `keystones` (by id), `seen_discoveries`, `traits` (by key) — nothing ever removes an entry, so a union is safe in any apply order and also covers a newer blob that never saw the field. `chapter`/`closed_chapters` stay plain LWW (they move as a pair, and a stale close is re-derived). `replaceAllRecords` applies the same fold when a pending journal row meets a compacted snapshot row (the overlay keeps the pending row's scalars; a floored pending row still loses to the snapshot but its grow-only fields survive). The merged row keeps the winner's `clientTs` and is not re-queued: peers fold the same ops, and the next write of the journal carries the union to any device that missed one (e.g. one that bootstrapped from a snapshot published before the fold). Old clients still apply strict LWW, so a mixed fleet can briefly diverge until an upgraded device next writes the journal — no worse than before. Tombstones are never merged. Any other singleton with grow-only fields needs its own `APPLY_MERGE` entry; without one it keeps this residual.

  4. **Intake rows merge semantically, not by `clientTs`** (bd med-wi09.11). `MERGE_POLICY` in `web/cloud/js/sync.js` runs `mergeIntake` (`web/domain/medintake.js`) on every path an intake row meets another copy of itself — local writes (`stampAndPut`), incoming ops (`applyIncoming`) and pending-vs-snapshot (`replaceAllRecords`, where a pending row the reducer rules stale leaves the queue). Order: a tombstone is terminal both ways; higher `rev` wins (explicit actions write seen+1; so does the Telegram reminder callback, `confirm()`, but only on an OPEN dose — `PENDING` or `UNTAKEN` — and only when the tap's `at_unix` is later than the row's `acted_at` (no `acted_at` = a rev-0 row, applies); an older tap is not the newest intent and writes nothing, `stale_callback` — bd med-944k, which replaced the earlier "rev 0 → 1 only" proxy that refused a tap made after an undo); equal rev → `via` app = mcp > telegram = native > legacy; then later `acted_at`, then `clientTs`, then the body — a total order, so every device converges. Two explicit (app/mcp) rows tied on rev with different **statuses** keep the winner and flag it with the loser in `conflict` (with the same status, e.g. two devices both taking the dose, the later act wins unflagged). `snoozed_until` rides its own `snoozed_at` branch and never changes status. Undo writes status `UNTAKEN` (reads as due; the wire shape still says `PENDING`; the reverted `taken_at` goes into `note`). A row without `rev` is **legacy** — PENDING is rev 0, anything else rev 1, ranked lowest — and the reducer never writes rev into it, so an old client's queued payload re-posted after reload can never beat a v2 correction. `clientTs` is still stamped, so older clients keep merging these rows by plain LWW; an older client's edit spreads the row it read (rev included), so it ties at that rev and loses to anything newer. Intake is a `REPAIR_TYPES` entry like `sleep` (bd med-wi09.23): when the reducer's winner is not the clientTs winner the merging device re-stamps it above both copies and queues it, and a snapshot bootstrap reduces every acknowledged live local intake row against its snapshot copy (a local tombstone is not reduced: against a live snapshot copy it can only be an old tab's restore), so an older bundle's compacted PENDING cannot bury an acknowledged TAKEN. Projection rows carry `via` (`legacy` for a rev-less row) and `conflict`.

  Neither orders two *blind concurrent* writes made on skewed devices; that needs a hybrid logical clock (deferred with the envelope's `format_version`, bd med-jb7.5). But a device whose clock is more than two minutes out now says so in the sync status line rather than losing edits quietly.
- **Snapshots + compaction**: the server cannot compact ciphertext, so clients periodically upload a full encrypted snapshot (`maybeSnapshot` in `web/cloud/js/sync.js`: once the tail passes `SNAPSHOT_THRESHOLD` ops, at most once per `MIN_SNAPSHOT_INTERVAL_MS` per device unless the tail reaches `SNAPSHOT_FORCE_OPS`; a full-vault import forces one); the server then drops ops below that seq. Bounds both restore time on a new device and storage growth. The snapshot plaintext is **gzip-then-encrypt** (`gzip(utf8(JSON))` before AES-GCM), shrinking a large vault's POST body ~10x; the decrypt path sniffs the `0x1f 0x8b` gzip magic so legacy uncompressed snapshots still read. Server cap is a **64 MiB decoded ciphertext** (the request body is capped at 96 MiB to hold its base64 expansion). See [docs/cloud-crypto.md](cloud-crypto.md).
- **Ledger cut + writer gate** (bd med-wi09.8, epic `med-wi09` Phase 2): `accounts.ledger_cut_seq` / `ledger_cut_at` (migration 036) record the dose-ledger cut as a server fact. The first `POST /api/sync/ops` op whose plaintext `record_type_tag` type (the part before `:`) is `ledgercut` sets both — that op's assigned seq and server time (RFC3339 UTC) — in the same transaction as the insert; later `ledgercut` ops never move it. Every `GET /api/sync/ops` page returns `ledger_cut_seq` / `ledger_cut_at` (null until set). Once the cut is set, a writer that does not send `X-Ledger: 2` gets **426** `{"error":"update_required"}` on (a) any op batch containing a type in `medication|settings|tzplan|stock|medsched|tztransition` — the whole batch is refused, nothing inserted, its `intake` ops included (Archie 4100: each op's AES-GCM AAD binds the seq the client predicted in batch order, so storing only part of a batch would shift the kept ops to seqs no device can decrypt) — and (b) any `POST /api/sync/snapshot`. `PUT /api/push/schedule` is not gated yet: `push.js` sends `sync.js`'s `WRITE_HEADERS` (so `X-Ledger: 2`) on it since bd med-wi09.20, and the server only logs `push schedule: header-less PUT on cut account` for a header-less PUT on an account with a cut, then replaces the schedule as before. The 426 for it is bd med-wi09.22, shipped once prod logs show zero such PUTs over 48 consecutive hours (the bundle before med-wi09.20 sets the cut but sends no header there). `intake` is deliberately **not** gated (HIGH-1, bd med-wi09.12): an old bundle's dose writes keep landing after the cut, and the client's intake reducer (`mergeIntake`) ranks them legacy — a `PENDING` placeholder is rev 0 (it never promotes and never undoes a taken dose; at a regenerated slot's id it simply dedupes with it), an old `TAKEN`/`SKIPPED` is rev 1 and beats a regenerated due (real evidence must not be lost to a 426). Pulls, `GET /api/sync/snapshot`, exports, untagged op types and every other route are unchanged; the check reads only the plaintext tag, never ciphertext. Gate and cut are checked inside the append/snapshot transaction, so a concurrent cut cannot let a pre-v2 batch slip in after it. **Activation (bd med-wi09.12):** `sync.js` sends `X-Ledger: 2` on every write POST (op flush, snapshot, import bump), and `push.js` on the schedule PUT. The apishim install runs `intake.ensureLedgerCut()` once: a floored (`clientTs: 0`) `putIfAbsent` of `{recordId: 'ledgercut', at: <now ISO>}`; its first push sets the server cut, and `pullTail` adopts the server's `ledger_cut_at` into the local row (a local-only `putRecords`, never queued) so every device derives from the same instant. Local mode writes the same row and never syncs it. The row is not vault-managed: an import keeps it, an export omits it. So a local → account transfer does not carry the local cut — deliberately: the account's cut is a server fact the first device set and it never moves, so a local cut could not be honoured anyway. The cost: a moved local vault's never-acted doses dated before the account's cut stop showing as due (no regeneration before the cut); its taken/skipped evidence moves intact. Only shells that bundle the v2 local app can produce such a vault. From the cut on, doses are **derived**: the 60 s dose sweep and every `PENDING` placeholder write are gone. `medintake.js` `project()` regenerates occurrences from the cut day's local midnight, in the zone in force at the cut (before that day stored rows are the whole truth; on the cut day before the cut instant, a slot is covered by any stored row — tombstones included — with the same medication and the same instant, and the stored row wins). A device whose `ledgercut` row has not arrived yet uses a provisional cut fixed at its first read, so the cut never slides with now. Generated via `lineage.js` `regenerateWindow` → `regenerate` (segments at `tztransition.switch_at` and `medsched.from`, with the approved tz plan's steps). With no `tztransition` history, each past local day is planned in its **evidence zone**, never the device clock: the `tz` stamped on that day's acted rows (newest wins), else the zone of the nearest earlier evidence row, else the pinned/device zone — synthesized in memory as pseudo-transitions at local midnight, never written; a day whose evidence carries no `tz` (an old client's row) is no longer special: from the cut day on, history always regenerates and a stored row wins at its own id/instant (so an old tab's TAKEN 08:00 leaves the forgotten 20:00 due and tappable). **Edit-day pairing:** when a schedule edit changes slot times, the olds and news on the edit's local day are paired by order per med: a taken old keeps its row and its partner is not generated; an untaken old is cancelled and its partner is due even if already past; extra news are due, extra untaken olds cancelled; the MT7 preview labels show exactly this pairing. **Projection cache:** settled UTC days before today are kept per records port and zone; every read first asks the port's write journal (`sync.js` `changesSince`, which every `putRecord` feeds and every store replace/reset/connection drop resets) which intakes changed and drops their days, and any change to the other inputs (meds minus stock, history, tz plan, cut, evidence zones) drops every day; today on is always computed fresh. A port without a journal rebuilds on every read. `sync.js` also memoizes `listRaw` next to `list`, invalidated at the same funnels. Tabs and windows of one origin share the IndexedDB store but not these memos, so every write funnel also announces itself on the `medtracker-records` BroadcastChannel; the other tabs journal the record and drop their memo for its type (a store replace or reset drops everything). Writers that never announce (an old bundle's tab left open after a deploy, a message lost while the page sat in bfcache, Safari < 15.4 without BroadcastChannel) are caught twice over: the memos drop on `focus`, `visibilitychange` → visible and a persisted `pageshow`, and the projection rebuilds its index whenever the raw intake list's row count or `clientTs` sum stops matching it (a stamp only rises, so any write moves the sum). A `syncWedged` / `writeError: 426` in the shared `sync_meta` comes from a pre-v2 tab (this build never counts a 426): v2 ignores it, flushes the shared queue with `X-Ledger: 2`, and if that is still refused shows "Update required", never the reset hint. A known one-day gap (LOW-5): on the cut day an old client's drifted row from before the cut instant does not cover the regenerated slot (exact instant only), so both show due that day. Readers always pass a window (gamification reads its 365-day scoring window, never the whole log). It treats stored rows as evidence — a post-cut `PENDING` row whose slot history does not yield is an old client's prediction and is hidden. Actions (`act`, confirm, skip, snooze, Telegram/inbox applies via `withDueRows`) on a derived dose write at its exact id (confirm-or-create); a batch resolves against one projection. `withDueRows` is the projection's own not-yet-ahead rows (no future dose, nothing the projection hides); a Telegram tap's band fallback only considers doses at or before the tap, the inbox drain projects and stamps in the pinned zone (the tracked zone if none is pinned), never the device zone, and the chat "took my meds" (`intake.dueToday`) confirms only today's due doses. The reminder horizon reads the same cut and has no ±band of its own: the projection is the only rule. `tzplan.getCurrentPlan` now completes a finished plan on read (floored), since the sweep that used to do it is gone. Gate cost (accepted in the epic): a pre-Phase-1 tab that writes a gated type after activation wedges with the "reset local sync" hint (following it discards its queued writes); a Phase-1+ tab shows "Update required — reload" (asking the SW for the current build — `registration.update()` — as the banner goes up), keeps and exports its queue (bd med-wi09.5). Shells' bundled local-mode app does not sync and never hits the gate.
- **Cross-device wake** (bd med-eas.9): pulls run on unlock (`pullOnOpen`), on `visibilitychange`→visible / `online` (`startReconnectAutoDrain`), and on a content-free `sync-ready` SSE event. `SyncAPI.PostOps` and `PostSnapshot` (`internal/cloudserver/sync.go`) call `InboxBroker.NotifySync` after a durable write; the event rides the existing `GET /api/inbox/events` stream with its own coalescing slot, separate from `inbox-ready` (`internal/cloudserver/inbox_events.go`). The tab hands it to `requestDrain` (`web/cloud/js/sync.js`), the same single-slot drain guard as the visibility/online path and `reauthenticate`, and also runs one on stream `open` to catch wakes missed across a reconnect. Pulled records repaint via `notifyRecordsChanged(…, ORIGIN_EXTERNAL)` → the cloud-write tab refresh, or the "new data" banner while editing. The writing tab is woken too, because a credential id is not a device id; that echo costs one empty `GET /api/sync/ops`. Because a wake can land between an importer's bump op and its forced snapshot, `pullTail` records a pulled bump's seq (`sync_meta.importBumpSeq`) and re-bootstraps from the first snapshot at or above it that this device hasn't loaded, even when the cursor has already reached that seq, then repaints every tag. Wake-triggered drains (and a rerun coalesced only from wakes) never retry a stranded import (`requestDrain(ctx, { wake: true })`): that retry posts a bump whose own echo would start the next retry; and a device that pulled a bump holds its own threshold compaction until the import snapshot lands, so it cannot bury the import under its pre-import vault. Nothing new leaves the vault: the stream is same-origin, the event carries no data, and the server already sees oplog append times.
- Local layer stays Dexie/IndexedDB (already vendored); plaintext lives only in memory and IndexedDB on the user's device, cloud copy is authoritative.
- **Account deletion is a verified local wipe** (med-d5t.8 / med-yor.3): the client's `clearLocalVault()` awaits `deleteDatabase` on **both** `medtracker-cloud` (encrypted mirror + LDK material) and Dexie's `MedTrackerDB` (the shared frontend's plaintext caches), resolving only on `onsuccess`, and the flow runs it **twice**: once *before* `DELETE /api/account` — a blocked delete (another open tab) fails while the account is still intact, so plaintext can never be stranded no matter what the user does next (the cloud copy is authoritative; an erased mirror re-syncs if they abort at the passkey prompt) — and once *after*, the load-bearing erase that catches anything background sync re-created during the ceremony. Navigation happens only once the post-delete wipe is confirmed; a blocked wipe surfaces a recoverable "close other tabs" error instead of a false success, and a post-delete retry skips the (now-impossible) re-auth ceremony, re-runs only the wipe, and must happen in the same tab — the deleted account's subdomain serves 404s, so no page on that origin can ever run again. Push unsubscribe (browser-side only — the server rows are already cascaded) and SW unregister are best-effort. The delete dialog's "Export a backup first" link cancels it and opens Settings → Backup & import (the passphrase-encrypted export; its unencrypted option warns before writing plaintext provider keys); the flow itself writes no file (bd med-ckm5.9). Related invariant: every open of `medtracker-cloud` auto-closes on `versionchange` — page code via `localdb.js`'s `openDb()`, and the service worker's per-push `readNK` open directly — so a live handle never blocks the deletion (or a future schema bump); any new open of that DB must do the same.

### Importers and derived writers — checklist

Lessons from the Apple Health imports (PRs #1053, #1055); the reference code is
`web/domain/healthimport.js`, `web/domain/vault.js` and `web/domain/healthsource.js`.
Any new importer or derived writer answers each of these:

- **Tombstones survive export, restore and rescan.** A deleted slot must stay
  deleted after a vault round trip and a full re-read of the source — add the
  type and id shape to `TOMBSTONED_SLOT_TYPES` / `SLOT_ID_SHAPE` (`vault.js`).
- **Dedupe on `source_id`, not only on the recordId.** An older client restores
  rows under fresh ids but keeps `source_id`; the import must count those as
  present (`healthimport.js`).
- **Bodies are device-independent at `clientTs: 0`.** Two devices deriving the
  same slot must write byte-identical bodies — no device time zone, clock or
  local-only derived field (imported weights store no `weight_trend`).
- **Ordering is deterministic, with explicit tie-breaks** (longest span, then
  smaller UUID; sources by name), so every device picks the same winner.
- **Deleting an alias tombstones the canonical id** (`healthsource.js`), or a
  rescan re-creates the row the user just deleted.
- **Precedence between two sources is picked on read, not by deleting or
  skipping on import.** Store both, and let one reader choose
  (`healthsource.js` `visibleSleep`, bd med-w6gx.31). A tombstone is
  permanent and travels in the vault, so any overlap heuristic eventually
  deletes a real night; an import-side skip depends on arrival order. (The
  legacy sleep conversion, bd med-0xad.4/.9, never deletes the legacy rows:
  they are the ledger, the day row is their fold, and the read shows the day
  row when it is at least as full.)
- **The `putIfAbsent` floor beats content-derived stamps.** Write once at
  `clientTs: 0` (rule 12) so edits and deletes always outrank it; a stamp
  derived from the content is no floor and reopens the LWW race.

### Incident: a stale tab erased a finished workout (bd med-9a87)

**2026-08-31, production.** A completed strength session vanished from history hours after it was logged. Worth keeping because nothing misbehaved — every component did exactly what it was written to do, and the data was still destroyed.

| time (Europe/Berlin) | event |
|---|---|
| 08-30 21:18 | `getNext` materializes `session-7-2026-08-31` (LEGS, `pending`), stamped `clientTs = now()` |
| 08-31 18:24:09 | user finishes the workout — status `completed`, 4 exercise logs written, rotation cursor advances 16 → 14 |
| 08-31 18:24:09 | `getNext` re-runs, skips today (terminal) and materializes the *next* occurrence, 09-02 |
| **08-31 21:40:43** | **a second browser, mirror stale since ~08-28, is opened.** Its `getNext` sees no slot for 08-31, re-derives one as `pending`, stamps `clientTs = now()`, pushes it |
| — | LWW: `21:40 > 18:24` ⇒ the placeholder wins. The completed session is gone |

Three symptoms, one cause: the workout disappeared from history (the list renders only `completed`/`skipped`), its four exercise logs orphaned onto a `session_id` no record carried any more, and the Telegram reminder un-suppressed because the horizon reads that slot's status.

**What made it findable.** The `/api/*` views hide all of it — they project live records and drop `clientTs`, tombstones, and orphans. Three things cracked it, all worth reaching for again:

- **Numeric ids decode to wall-clock.** `mintNumericId` is `nowMs * 1000 + rand`, so `id / 1000` is the mint instant. That alone built the timeline above and showed the intruder was minted *after* the completion.
- **Read the raw mirror.** `indexedDB.open('medtracker-cloud')` → `records` store is plaintext and carries `clientTs`, `deleted` tombstones, and rows no API surfaces.
- **Cross-check derived cursors.** The intruding record carried `variant_id: 15` while `rotation-7` sat at `14`. Variant 15 was the cursor value from *before* a skip three days earlier — which dated the offending device's mirror precisely.

**Why it is a class, not a one-off.** This is the second time: bd med-d4w was the same shape in `medintake.js`, where a stale device re-materialized a dose target and a *confirmed* dose silently reverted to `PENDING`. Both are the same three ingredients — a read path that writes, a deterministic recordId, and a `now()` stamp. Any two of those are fine; all three lose data.

**The rule that prevents it** is guard 3 above: materialized rows are stamped `clientTs: 0` **and go in via `putIfAbsent`**, so they can neither outrank a real write nor be promoted over one. Regression coverage lives in `web/static/js/tests/cloud.shim-contract.workout-convergence.test.js` (domain layer, replaying a stale device against a completed session through a local replica of `applyIncoming`'s comparison) and in `web/cloud/js/tests/sync.test.js` (the port itself: put-if-absent over a tombstone, over a live row, and the promotion that used to happen).

**Since fixed**: scheduled sessions used to mint a *non-deterministic* numeric id, so two devices held divergent bodies at equal `clientTs` until the first real write and logs written against the losing one orphaned — `derivedNumericId(recordId)` now hashes the slot instead (bd med-8j12). The same stale-device shape also reached read/timer-side read-modify-writes on singleton records in `gamification.js` and `tzplan.js`, which the med-9a87 sweep wrongly waved through as "last-write-wins is intended" — the floor now covers those transitions too (bd med-y4ue, guard 3 above), with the divergence residual named there.

**If you are adding a lazily-materialized record**, the check is one question: *could a device that has not synced recently create this same recordId?* If yes, it is derived state and takes the floor.

## Push relay & reminder lifecycle

The server is a **blind alarm clock**. It cannot compute "when is the next dose" — the client pre-computes and uploads the schedule:

1. Client (which has the domain logic + data) computes all reminders for the next horizon (default 30 days, configurable; ~KBs even at many-meds scale) and uploads `(fire_at, app_ciphertext)` rows, replace-all per sync — replace-all pre-schedule semantics.
2. At `fire_at`, the server wraps `app_ciphertext` in standard Web Push encryption (RFC 8291) per registered subscription and sends. Two layers: the push services (FCM/APNs) can't read RFC 8291 payloads, and our server can't read the app layer.
3. The service worker decrypts the app layer if the vault key is available and shows a rich notification ("BP pill — 10 mg"); if the vault is locked, it shows a generic "Medication reminder". Notification tap deep-links via the existing `handleDeepLinks()` surface (bd med-9d1a): the sealed payload carries `url` from `reminderDeeplink(entry)` (`web/cloud/js/reminder-deeplink.js`) — `/?action=medication_confirm&ids=<csv>&scheduled=<iso>` for a dose (no names; `handlePushAction` resolves them, checks each against the dose projection (`GET /api/doses` at that exact instant), drops doses already logged for the slot, and opens an *additive* sheet on the doses that resolve — `POST /api/doses/act` touches only their exact ids; when none resolves it lands on the MT6 out-of-date note on Meds → Timeline at that med with the original time, never the nearest due row (bd med-wi09.4); a since-deleted med lands on Meds with a toast), `/?tab=<section>` otherwise. The SW allowlists that shape (root path, keys `tab`/`action`/`ids`/`scheduled`) and either `openWindow(url)` on a cold start or `postMessage({type:'reminder-open', url})` to an open tab, which `cloud-boot.js` routes once unlocked. Known limit: a locked app loses the target (a warm locked tab has no listener yet; a cold start loses the query through `/unlock`) and opens the default tab.
4. Every app open refreshes the horizon; multiple devices each hold a subscription; the relay prunes subscriptions on `410 Gone`.

**Relay fencing (bd med-wi09.14, epic `med-wi09` Phase 3; Archie 5800)**: replace-all horizons from two devices used to settle on whichever PUT landed last, so a device holding stale records could overwrite a fresher horizon. `PUT /api/push/schedule` now takes `{entries, based_on_seq, generation}`. `based_on_seq` is the device's pulled cursor (`sync_meta.localLastSeq`), read in one IndexedDB transaction with the pending-queue count **before** the async build (`sync.js` `recordsPort().horizonBasis()`), so a pull during the build cannot inflate it. `generation` is the dose-ledger generation the horizon was built under — the `X-Ledger` number (`sync.js` `LEDGER_GENERATION`, 2 today), bumped only with a future engine change. `reminders.js` `recomputeAndPush` PUTs only when the pending queue is empty and the device is bootstrapped (every local write then has a server seq at or below the cursor); otherwise, and on a **409**, it pulls once (`requestFreshDrain`, which also flushes the queue), rebuilds and PUTs once more (the deferred case is awaited, so a caller such as Settings sees that PUT's outcome; the 409 case runs in the background). That post-drain PUT goes out even if writes are still pending (a queue that cannot drain — quota 413, sync wedged, 426, a stranded import — must not stop the relay horizon; Archie 5808): it is fenced with the cursor captured before the build, which never claims more than the device pulled, so a stale stuck device still gets 409 while a single-device account keeps its reminders; that device's horizon then also carries its own unflushed writes. A 409 on the post-drain pass, or a cursor still null, stops there, and the next write, unlock or drain-triggered recompute builds again. Server: `sync_state.schedule_seq` / `schedule_generation` (migration 038, default 0/0) hold the last fenced PUT's pair; `cloudstore.ReplaceScheduleFenced` compares and stores it in the same upsert that stamps `last_schedule_unix`, before any row is deleted: a generation different from the stored one is accepted in **either** direction and overwrites both values (the stored generation is only the epoch the seq compare runs in — stored state never refuses with a 426, so a server rollback cannot leave a higher stored generation fencing every device out; the only 426 on this route is the compiled header gate, bd med-wi09.22); the stored seq is capped at the account's `last_seq` (`MIN(based_on_seq, last_seq)`; after a DB restore an ahead device cannot pin the fence above what a freshly pulled device reaches), and the body's raw `based_on_seq` is compared against that capped value: under the same generation `based_on_seq <` stored → **409** `{"error":"stale_schedule"}`, nothing changed; equal → accepted (renewal: same inputs, same rows); higher → accepted. Half a fence (one field without the other), a negative seq or generation < 1 → 400. **Legacy clients** (bundles before med-wi09.14, and the `/unlock` shell's demo scheduler, send neither field) are accepted exactly as before and move neither stored value. Bundles that already send `X-Ledger: 2` on the schedule PUT (med-wi09.20) but predate med-wi09.14 send an unfenced body with the header, so the header gate (med-wi09.22) does not close them: they keep last-writer-wins until they reload. Only the older header-less bundles fall to that gate. The account seq never resets short of account deletion, so `based_on_seq` is monotonic. The relay's own cancel-refire on confirm still covers the in-flight chain (a confirmation is a write, so it advances the seq and a same-seq refresh cannot revive the job). **Native shells**: unchanged — the device-local horizon (iOS/Android local notifications) is built on every recompute, deferral or not, per device and eventually consistent; no native code PUTs the schedule (the web app inside a shell PUTs it, fenced, like any browser).

**Native channel (bd med-erq1)**: the Android app (iOS pending, med-erq1.4) can also register an FCM/APNs token (`internal/cloudserver/nativepush.go`). The relay uses it for three content-free wakes only: a Telegram inbox message ("Open the app to record what you sent"), a dry reminder queue ("Open the app to keep reminders running"), and an add-device claim (`transfer_claimed`, "Approve the new device?", bd med-r1j2.9); the app then drains/refills locally. Neither shell handles `transfer_claimed` yet: on Android the system shows the server's notification text while the app is in the background, and a tap resumes the app as it was (in the foreground the shell drops the unknown kind; the page's own 2 s poll still sees the claim); iOS does not register tokens yet. The native deep link to Add a device (`?tab=settings&page=add-device`) comes with the shells' twin beads. It is not a reminder channel: reminders stay local notifications, and no vault data reaches Apple or Google. Boundary row: `native-push`.

**Add-device claim push (bd med-r1j2.9)**: `TransferAPI.ClaimTransfer` calls `Relay.NotifyTransferClaimed` on the pending→claimed transition, which the store allows once per slot, so it is at most one push per slot and none on reveal/approve/enroll/delete. Web Push gets the bare `{"kind":"transfer_claimed"}` (no slot id, platform or expiry); `web/cloud/sw.js` shows a fixed "Approve the new device?" text with a generic body (no "<platform> · N min": the SW holds no slot state, and the payload carries none), and the tap opens `?tab=settings&page=add-device`. The flow's secrets live only in the page that made the code, so the SW probes every window (content-free `transfer-live-probe`, 250 ms budget, first ack wins — a click grants focus only briefly) and routes the tap to the one holding the live code; that page polls at once and lands on Approve with the match code (`transfer.js resumeLiveTransfer`). With no ack the first window opens Add a device on the "This request isn't open here" end state.

**Settings entry point**: the main app's Settings screen (`web/static`, not just the `/unlock` shell) surfaces a cloud-only Notifications block (`features/settings.js`, gated on `window.__MEDTRACKER_CLOUD__`) with Enable/Disable and "Send test push" controls. It calls the same DOM-free `web/cloud/js/push.js` (`subscribe`/`unsubscribe`) helpers the shell uses, reached via `window.MedTrackerCloud.ctx` (published by `cloud-boot.js` once the vault is unlocked). The `/unlock` shell's own push screen remains for the pre-app flow (before the vault has ever been unlocked in the main app).

**Test push is a separate, immediate, this-device-only send** — distinct from the scheduled-reminder path above, which always fans out to every subscribed device. `sendTestPush(ctx)` (`web/cloud/js/reminders.js`) reads the current device's own subscription, encrypts a fixed test payload with the account NK, and `POST`s `{ endpoint, ct }` to `/api/push/test`. The handler (`internal/cloudserver/push.go`) resolves that endpoint to a subscription on the caller's account (404 if none/foreign), loads the account's VAPID keys, and calls `WebPushSender.Send` immediately — no relay tick, no schedule mutation, so it can never clobber the real replace-all reminder schedule. Same blind shape as the relay: the server sees only the endpoint (already-stored routing metadata) and the client-encrypted `ct`, never content.

**Notification actions (Snooze / Don't-bug)** — implemented, bd med-9b8.3. BP and weight reminders carry Snooze and Don't-bug action buttons. The `kind` that selects them (`bp` / `weight` / `medication`) rides *inside* the NK ciphertext, so the relay never learns what sort of reminder it is forwarding.

**A service worker cannot apply the tap itself.** `/api/bp/reminder/snooze` and friends are served by the apishim, which lives in the page and needs the DEK, and a service worker never holds the DEK. So a tap is handed to an unlocked page instead — `postMessage({type:'reminder-action', route})` to a focused tab, or `openWindow('/?reminder_action=<action>')` on a cold start, which `cloud-boot.js` drains *after* the vault opens (and strips from the URL, so a refresh can't replay the mute). `cloud-boot.js` allowlists the four routes it will replay, so a stale or hostile same-origin worker message can't drive arbitrary shim writes.

Snooze (2h) and don't-bug (24h) are **mute-until instants on the `bpreminderpref` / `weightreminderpref` vault records**, not flags — `enabled` stays true and the schedule resumes on its own, Because the horizon is *precomputed and already queued server-side*, muting only takes effect once a horizon omitting the muted targets is re-uploaded; the shim fires that recompute undebounced but does not await it, so a snooze tapped on a flaky connection still succeeds (the next unlock re-uploads anyway). The "send a test reminder" affordance is `sendTestPush(ctx)`, the this-device-only encrypted push described above.

**Dry-queue safety net**: if the user doesn't open the app within the horizon, reminders stop — and the server can't extend them. The server can still *see the queue emptying* (inherent metadata: `scheduled_pushes.fire_at_unix`), so it sends a generic warning push ("Open the app to keep reminders running") once a day per account. This is the E2EE analogue of the adherence safety net.

The signal is **queue exhaustion, not sync recency** (bd med-2lx, `Repo.AccountsNeedingStaleSyncWarning`). Two facts made the original last-sync gate a net that never caught anything: every inbox drain flushes ops through the sync API and touches `sync_state.last_sync_unix`, so an account alive enough to tap Confirm in Telegram always looks freshly synced while its horizon rots; and the query INNER JOINed a subquery over *unsent* rows, so an account whose queue had already gone fully dry produced no row at all and could never be warned. A production account missed five days of morning doses through both. The query now takes `COALESCE(MAX(fire_at_unix), 0)` from a correlated subquery — an empty queue collapses to 0 and always trips the warn horizon — and, because that would otherwise sweep in every account that never wanted reminders, it warns only accounts with a live (non-disabled) push subscription **and** a most-recent scheduled push (sent or not) no further than `dryQueueWithin` *behind* now. That backward window is deliberate: a user who switches reminders off leaves the same trace as a horizon that rotted (`ReplaceSchedule` deletes the unsent rows, the sent history stays), and no query outside the vault can tell those apart — so the warning is bounded to a few daily nags after the last reminder rather than made permanent. Since med-ei2 that window is the legacy branch for rows whose `sync_state` upload signal is still NULL; every schedule PUT stamps when it happened plus whether the batch was empty, and stamped accounts use that directly — an empty last PUT is 'reminders deliberately off' however old (silent, even if the app was then abandoned), a non-empty last PUT older than `dryQueueWithin` with a dry queue is a rotted horizon (warned even outside the old window, as long as the account ever scheduled anything).

**Subscription eviction (implemented, bd med-d5t.3)**: Safari drops the push subscription of a PWA left unopened for a few days, and iOS gives no signal when it does. The stale-sync warning is *not* the countermeasure — it is itself a server-composed web push, so once the subscription is evicted it cannot arrive either. That reasoning was circular, and reminders stopped forever with nothing to show for it.

The countermeasure is a two-layer reconcile. The load-bearing half is `ensurePushSubscription()` (`web/cloud/js/push.js`), called on every app boot from `cloud-boot.js`: if notification permission is still granted, it demands a live `pushManager.getSubscription()` and re-subscribes when it finds none — no user gesture is needed once permission exists. Re-uploading the endpoint also *heals the server row*, because `POST /api/push/subscriptions` upserts with `disabled = 0`. The belt is a `pushsubscriptionchange` handler in `web/cloud/sw.js`, which re-subscribes with the same (never-rotated, per-account) `applicationServerKey` and re-uploads; Safari's support for that event is unreliable, which is exactly why it cannot be the only layer. When neither can restore the subscription, Settings says "Reminders are not armed on this device" rather than showing a bare Enable button that reads like a fresh device.

Server side needs nothing new: the relay already disables a subscription on a 410/404 from the push service (`Relay.send` → `Repo.Disable`), and `Repo.List` skips disabled rows, so a dead endpoint is never retried forever.

Remaining platform caveat: iOS web push requires the installed (home-screen) PWA and has occasional delivery quirks.

**Troubleshooting: a desktop push that "never arrives".** When the server reports
a successful send, `Notification.permission === 'granted'`, and
`navigator.serviceWorker.ready.then(r => r.showNotification('x'))` hangs and never
resolves, the OS is blocking the browser's notifications (macOS System Settings →
Notifications → the browser, or a Focus mode). It is not a code bug; fix the OS
setting. If `serviceWorker.ready` itself never resolves, look at the SW
registration instead. The cloud SW (`web/cloud/sw.js`) falls back to a generic
notification on any decrypt failure, so getting nothing at all also points to the
OS.

**Per-account VAPID keys** (implemented, see `docs/plans/completed/2026-07-05-cloud-c2-push-vapid-per-account.md`): each account gets its own VAPID keypair, generated server-side at invite provisioning. Push services bind a subscription to the `applicationServerKey` used at `subscribe()` time and reject sends signed with a different key — so a relay bug that misrouted account A's payload to account B's endpoint gets rejected by Apple/Google themselves, a third enforcement layer on top of RFC 8291 per-subscription encryption and NK app-layer encryption. The VAPID *subject* stays service-wide (it identifies the relay operator per RFC 8292, never the user — a per-user subject would leak identity to Google/Apple): `VAPID_SUBJECT` env, defaulting to `mailto:noreply@<CLOUD_BASE_DOMAIN>`, with `https://<CLOUD_BASE_DOMAIN>` substituted for Apple endpoints. Key rotation is unsupported by design — push services bind subscriptions to the subscribe-time key, so rotating would orphan every subscription for that account.

## Lost device / recovery — the reliability matrix

Zero knowledge means **no account reset**; recovery must be designed in, not bolted on. There is no passphrase to forget — recovery paths are other passkeys, other devices, and the recovery code.

**Emergency Kit** (generated client-side, never stored server-side): a printable page/PDF with the instance URL, account id, recovery code, and a QR code encoding all three. Since bd `med-ta2n.8` signup offers it only when entered from Settings (`&kit=1`, no gate); otherwise the Settings Kit chip reminds until one is made via `/devices?flow=emergency-kit`. `/recover`'s forced rotation and the regenerate flow keep the explicit "I saved it" confirmation (1Password/Ente pattern). The server can optionally hold an email address for **URL re-delivery only** — never key material.

| Lost | Still has | Outcome |
|---|---|---|
| Phone | synced passkey (iCloud/Google) | New device asserts with the restored passkey; PRF unwraps the DEK. Non-event. |
| Phone (device-local passkey) | a second enrolled device | **Implemented (C0b)**: enroll replacement via QR hand-off / typed fallback ([cloud-crypto.md](cloud-crypto.md) Path B — Path A cross-device ceremony stays deferred); revoke the lost device from the surviving one. Key rotation on theft is a documented gap, not yet implemented. |
| Phone (device-local passkey) | Emergency Kit | **Implemented (C0b)**: recovery code unwraps DEK → enroll a new passkey → code force-rotated. Full restore. |
| Phone + forgot URL | email on file | Server emails the URL; then any row above applies. |
| All devices + all passkeys + Kit | nothing | **Data unrecoverable — by design.** Stated plainly in onboarding. |

Two cheap habits the onboarding pushes hard, because they collapse the loss matrix: (a) enroll a second device (a desktop browser tab counts — it gets its own passkey and envelope), (b) keep the Emergency Kit. A synced passkey does both jobs at once for users who accept iCloud/Google in the loop.

Ongoing safety: the client periodically (and after every schema migration) verifies it can decrypt the latest snapshot end-to-end — a backup that was never restore-tested is not a backup.

## Telegram (optional, BYO bot token)

**Status: C3a implemented; C3b outbound implemented** — managed-bot provisioning + BYO fallback + chat linking + consent screen + wizard step + test notification all ship in `cmd/cloud` (endpoints under `/api/telegram/*` and webhooks under `/tg/*`; token sealed at rest via HKDF-from-`SESSION_SECRET` + AES-GCM). **Outbound reminder delivery now ships too** (med-76c.1): `scheduled_pushes` carries a per-entry `delivery` flag (`webpush|telegram|both`) and, for Telegram entries, a `tg_text` the client composes at its chosen verbosity; the relay branches on the flag and sends via the sealed bot token. **Inbound now ships too** (med-76c.2): medication reminders carry inline Confirm/Snooze buttons whose `callback_data` is `s:<slotUnix>:<action>` (`tgclient.CallbackSlotPrefix`), a tap is sealed to the account's inbox key by `ChildWebhook` and queued, and an unlocked client applies it through the intake domain at drain time. The stem is **slot-scoped, not intake-scoped**, because one cloud dose reminder bundles every medication due at the same instant into a single message — so one Confirm means "I took the 08:00 meds", and the client expands the slot to its intakes. The relay learns nothing new from the stem: the slot instant is already the row's `fire_at_unix`. Real-Telegram empirics (managed-bot count limits, edited-username binding, user-revocation semantics) remain open and are gated to Post-Completion validation — the fake-API integration tests cover the contract but not Telegram's live behavior.

Zero-knowledge server vs. a chat bot is a real tension: the bot must exchange plaintext with Telegram, but the server can't read the vault. Resolution — the bot is a **channel**, not a brain:

- **One-tap provisioning via Managed Bots (Bot API 9.6, April 2026)** — no BotFather chat, no token pasting. One-time operator setup: create a manager bot and enable "Bot Management Mode" in BotFather's MiniApp. The onboarding step then shows a deep link `https://t.me/newbot/{manager_bot}/{suggested_username}?name=…`; the user taps it, confirms a pre-filled creation dialog, and owns a **personal** bot; the manager bot receives a `managed_bot` update and the cloud fetches the child bot's token via `getManagedBotToken` (`replaceManagedBotToken` for rotation). Account binding: the suggested username carries a random per-invite suffix the server remembers (or a `/start` pairing code fallback). Verified against the [official changelog](https://core.telegram.org/bots/api-changelog) + [features docs](https://core.telegram.org/bots/features); open items: undocumented managed-bot count limits and user-revocation semantics — test empirically at C3. Manual **BYO token stays as the fallback** for users who want a bot outside the manager's control (and it's the same server-side code path — a token is a token). Because Telegram never re-sends a lost `managed_bot_created` update, the pending page always exposes the BYO form and a "Start over" control (`POST /api/telegram/reset`, clears the `tg_pending` row → status `none`) — a lost bind update never strands the account waiting out the 1h pending TTL.
- **Opt-in with eyes open**: either way the bot token (and chat id) is a *channel credential*, not health data — server-visible by necessity, stored encrypted at rest with a server-side key, and clearly flagged in the UI as the one server-visible secret. Anyone holding it can send messages as that bot — the consent screen says exactly that.
- **Outbound = the same blind queue.** The pre-computed reminder queue grows a per-entry delivery flag (`webpush` / `telegram` / both) and, for Telegram entries, client-chosen plaintext at the user's chosen verbosity: generic ("Medication time") or detailed ("BP pill 10 mg") — the user decides what transits Telegram. Inline `Confirm` / `Snooze` buttons ride along.
- **Inbound = sealed mailbox.** Button callbacks and simple commands arrive at the server, which cannot apply them (it can't write ciphertext it can't produce). Instead it seals each event to the account's X25519 inbox public key with a server-side timestamp and appends it to a pending queue. On next open, the client drains the mailbox, decrypts, and applies through the normal domain layer — a `Confirm` tapped at 09:00 is recorded as taken at 09:00 even if the app opens at noon. (Push can nudge the SW to drain sooner when a device is reachable.)
- **Inbound foundation (implemented, med-76c.2 part 1).** The sealed-box format is `mt/v1/inbox`: anonymous ephemeral-static **X25519**, `ephPub(32) ‖ nonce(12) ‖ AES-256-GCM(K, plaintext, aad)` with `K = HKDF-SHA256(ikm=X25519(ephPriv, inboxPub), salt=ephPub‖inboxPub, info="mt/v1/inbox")` and `aad = encodeFields("mt/v1/inbox", accountId)`. Salting with both public keys binds a ciphertext to its (ephemeral, recipient) pair; the AAD binds it to the account, so a mailbox row copied between accounts fails to open rather than decrypting into the wrong vault.

  Both sides use their platform's native X25519 — Go's stdlib `crypto/ecdh`, WebCrypto's `X25519` — so **neither language takes a new crypto dependency**. `internal/cloudserver/testdata/inbox_sealed_vector.json` pins the wire format: the Go suite regenerates it from fixed randomness and the Vitest suite decrypts that exact file, so the two implementations cannot drift apart silently. (WebCrypto X25519 needs Chrome 133+ / Firefox 132+ / Safari 17.4+; `inboxCryptoSupported()` probes for it and the client refuses to half-provision a mailbox it could never open.)

  The account's inbox **public** key lives on `accounts.inbox_public_key`; there is deliberately no private column. The private key is an ordinary vault record (`inboxkey`), so it syncs to every device and any unlocked client can drain. `ensureInboxKey` writes it to the vault *before* publishing the public half — publishing first would let the server seal to a key a crash could stop us from persisting, stranding those events forever. Until a key is published, `SealAndQueue` returns `ErrNoInboxKey` and the event is **dropped, never stored in the clear**. Endpoints: `PUT /api/inbox/key`, `GET /api/inbox`, `DELETE /api/inbox/{id}` (per-event, account-scoped, idempotent).

  The ack barrier the protocol below demands now exists: `flushPending` (and its `flushConfirmed` wrapper in `web/cloud/js/sync.js`) returns **true only when every pending op is confirmed persisted server-side**, and false when writes were left pending — offline, un-bootstrapped, or a concurrent-writer collision. Before this it returned identically in both cases, so a drain could not have told "applied" from "deferred".

- **Drain protocol (binding requirements for C3b).** The failure to design out: an event acked as processed that never landed in the vault. Rules:
  1. **Ack strictly after flush**: per event — decrypt → apply through the domain layer → wait for the resulting ops to be *confirmed flushed* to the sync log → only then delete from the mailbox. A client crashing mid-drain leaves the event queued for the next drain. Never batch-ack ahead of the flush barrier.
  2. **At-least-once + idempotent apply**: re-draining an already-applied event must converge, not duplicate — guaranteed by deterministic record ids (e.g. a `Confirm` targets `intake-<medId>-<slotUnix>`) + LWW. Free-text events (`/food two eggs`) get a deterministic id derived from the mailbox event id, so a re-parse after a crash overwrites its own earlier result instead of double-logging.
  3. **Concurrent drainers are expected, not an error**: several unlocked clients may drain at once — including physical devices sharing one synced passkey (iCloud/Google-synced credentials look like a single device to the server; sync correctness never keys on credential identity — cursors and pending queues are per-client-local). Mailbox delete is per-event; the first ack wins, a second delete of the same event is a no-op, and duplicate applies converge per rule 2.
  4. **Apply in sealed-timestamp order** within a drain, and backdate records from the sealed `at_unix` (not drain time) — that's what makes the 09:00 tap record 09:00. See rule 4 under the implementation notes for what `at_unix` means per event kind.
- **Drain wedge recovery (`med-eas.51`).** The ack-after-flush barrier has a failure mode: an event whose ops can never flush is never acked, so the drain re-fetches the whole un-acked backlog on every 5s poll — forever. The concrete trigger seen in the wild is a stale sealed Telegram `.nxk` **Mi Band vitals import** (`vitals_import`, `sealNXKDocument` in `internal/cloudserver/telegram.go`, applied by `web/cloud/js/inbox-apply.js` → `web/domain/vitals.js importSamples`). `importSamples` day-batches hr/spo2/stress into **one record per day holding all that day's samples**, so a densely-sampling device day serializes past `maxOpCTLen = 64<<10` (64 KiB) — `POST /api/sync/ops` then returns `400 "op field too large or missing"` (`PostOps`, `internal/cloudserver/sync.go`). Three consecutive permanent 4xx trip `WRITE_ERROR_BUDGET` and set `syncWedged`; `flushConfirmed` returns false immediately, the event never acks, and the un-byte-capped `GET /api/inbox` re-fetches the entire ~160 MB backlog every poll. That is a self-inflicted DoS that bricks the account. Three coupled guards stop it:
  1. **Pause the drain when wedged.** `drainInbox` checks `isSyncWedged()` (`web/cloud/js/sync.js`) *before* fetching and returns without a single `GET /api/inbox`. `startInboxPolling` backs off the visible-tab poll on consecutive no-progress ticks and resumes on progress. Clearing `syncWedged` (via reset) un-pauses the next tick — no new persisted flag. **One drain outcome is deliberately excluded from that backoff (`med-3q8.3`):** an event this device cannot *open* — sealed to an inbox public key a concurrent device's last-write-wins `PUT /api/inbox/key` superseded. It is reported per event (`unopenable` in the drain report), left queued so a device holding the matching private key can still drain it, and stepped over rather than thrown — a throw used to abort the whole page, so every Telegram command behind it stayed `⏳ Queued` for as long as the app stayed open. Because such an event is skipped client-side after a fetch guard 2 already byte-caps, it costs exactly what an empty poll costs and must not throttle the mailbox.
  2. **Byte-cap the page.** `ListInbox` (`internal/cloudserver/inbox.go`) trims each response to `maxInboxDrainBytes = 1<<20` (≈1 MiB, mirroring sync's `FLUSH_MAX_BODY_BYTES`) alongside the existing `maxInboxDrainBatch=200` count cap, always including at least the first event so a single over-budget event still makes progress. So one response is never 160 MB.
  3. **Reset clears the poison backlog.** `DELETE /api/inbox` (session-scoped, `ClearInbox` → `cloudstore.ClearInboxEvents`) drops every un-acked event for the account. `resetLocalSync` (`web/cloud/js/cloud-boot.js`) calls it best-effort after the local un-wedge, so the one "Reset local sync" action also discards the un-appliable sealed events. **This discards any un-applied sealed events** — same "discards un-synced local writes" semantics reset already carries; it is the recovery escape hatch, and acceptable as such.
  The deeper fix — not sealing a large Mi Band `.nxk` as one giant >64 KiB event into the per-message mailbox (chunk the vitals import into sub-`maxOpCTLen` records, or route bulk imports around the per-message inbox) — is a **follow-up** (bd med-0cf), deliberately out of scope for the loop fix.
- **Free-text logging works through the same mailbox**: `/bp 120/80`, `/food two eggs`, `/weight 81.5` are sealed as raw text and parsed *client-side at drain time* by the same JS domain layer the app uses — including AI food parsing, since provider keys live in the vault and the drain runs on an unlocked client. The bot's immediate reply is necessarily generic ("saved — recorded next time you open the app"): the server can't confirm what it can't parse. Richer confirmation can arrive after drain, composed by the client (user-chosen verbosity). This is now ratified policy, not just a sketch — see [Inbound plaintext — what the relay may do](#inbound-plaintext--what-the-relay-may-do) for what the relay is and is not permitted to do, and why relay-side parsing was rejected.

  **Implemented for commands (`med-eas.29.2`), photos (`med-vcv.1`), and free text (`med-vcv.2`).** `ChildWebhook` answers `/start` and `/help` locally, seals every other `/command` verbatim, seals a photo's `file_id`, and now seals free text too — each replying `⏳ Queued`, which the client later edits into a confirmation. Free text is handed to a drain-time OpenAI tool-calling agent (`web/cloud/js/tg-agent.js`) that runs on the unlocked tab with the user's own key over the MCP catalog, so the model can log or answer. The relay still parses nothing and calls no AI.
- **Not supported in cloud mode**: conversational queries ("what's my BP trend?") — answering requires reading data, which only clients can do; a live reply would need an online unlocked client anyway, at which point the user has the app open.

### Inbound plaintext — what the relay may do

**Status: decided (`med-eas.29.1`), gates `med-eas.29.2` / `med-vcv` / `med-eas.30`.** The bullets above describe the mechanism; this section is the *policy*, and the constraint every downstream bead must implement against.

**The tension.** Outbound is already settled: the client composes the reminder text at a verbosity it chose, and the relay forwards it verbatim (`SendReminder`, `internal/cloudserver/telegram.go` — "Nothing here derives text from account data"). Inbound is different in kind. Telegram delivers bot updates as **plaintext over a webhook**; there is no bot API that is end-to-end encrypted. The moment full chat management exists, food descriptions, BP numbers and diary text land in the relay's memory. The question was never *can we avoid the relay seeing it* — we cannot — but **what the relay is permitted to do with it once it has.**

**Decision: seal-only. The relay never parses inbound content and never sends it to an AI provider.**

Per inbound message the relay may:

1. Read the leading command token, only to distinguish what it answers locally (`/start`, `/help`) from what it seals. It does **not** inspect arguments.
2. `SealAndQueue` the **raw message text, verbatim** to the account's X25519 inbox public key, and append the ciphertext to `inbox_events`.
3. Reply with a **fixed server constant** — "Queued — recorded when you next open the app." The reply is necessarily generic: the relay cannot confirm what it cannot parse. That is the feature, not a limitation.
4. Forget the plaintext. It is never written to disk, never logged, never re-read.

Everything else happens on an unlocked client: `drainInbox` decrypts, the existing JS domain layer parses (including AI food parsing, since provider keys live in the vault), and writes land through the normal domain path with an ack-after-flush barrier.

**What this costs, stated plainly.** The sealed mailbox is drained only after a **tab unlocks** — the service worker never holds the DEK, so `web/cloud/sw.js` cannot drain (it has no fetch handler and never touches the vault). The push→drain nudge described above is *aspirational, not implemented*. So a `/bp 120 80` sent on the bus is recorded when the app is next opened, and the bot cannot echo the value back in the meantime. This matches the availability constraint MCP already lives with: **no live tab, no processing.** Accepted deliberately.

**Alternatives rejected.**

- **(a) Relay-side AI parse** (relay calls OpenAI with the operator trial key so the bot can reply "Logged 2 eggs, 12 g protein"). Rejected. It gives the relay the plaintext *and* the intent *and* a provider key, converting an honest-but-curious operator from someone who sees ciphertext and metadata into someone who reads every meal, reading, and diary line. The relay today holds **no** per-account key capable of decrypting anything (`accounts` stores only a VAPID keypair and the inbox **public** key — `012_inbox.sql` has no private column, deliberately). Option (a) would be the first thing in the system to break that, in exchange for a nicer bot reply. Not a trade worth making. The one existing carve-out — the trial AI proxy — stays what it is: an explicit, consent-gated, *outbound-initiated* choice the user makes in the app, not a silent property of receiving a text message.
- **(c) Hybrid** (seal, reply "queued", relay later relays a client-composed answer back). **Adopted in `med-eas.29.2`** — see [Closing the loop](#closing-the-loop--queued--recorded) below. It needs no new trust: the answer is composed by the client and forwarded verbatim, exactly like `tg_text`. The original objection ("only pays off once a push→drain nudge exists") turned out to be wrong — a visible tab polling the mailbox is enough, and needs no notification permission.
- **Structured-commands-only** (relay regex-parses `/bp 120 80` itself to reply exactly). Rejected: it buys a better reply by making the relay read the values, which is precisely the exposure the seal-only rule exists to prevent — and it cannot generalize to food or diary text anyway.

**Photos — proxy, never store. Implemented (bd med-vcv.1).** A photo is worse: the relay must download it, because only the relay holds the bot token. The rule:

- Seal only the Telegram **`file_id`** (plus `mime`/`size`, and the **caption** verbatim — unparsed, like any inbound text; it is the only place a portion the pixels cannot show ("300g") can come from, and the client passes it to the vision model as a hint) into the mailbox as a `tg_photo` event (`sealPhoto` in `internal/cloudserver/telegram.go` — the largest rendition's `file_id`, structurally identical to `sealCommand`). Never seal the bytes: multi-MB blobs in `inbox_events` would bloat every `GET /api/inbox` drain, and the mailbox is a control channel, not a blob store.
- On drain, the client requests the image through a **session-gated, account-scoped relay endpoint** (`GET /api/telegram/photo?file_id=…`, `GetPhoto`) that resolves the `file_id` via `getFile` — through **this account's own bot token**, resolved from the session via `BotByAccount` — and **streams the bytes through** to the browser. Nothing is written to disk; nothing is logged but the status code. The vision parse then runs browser-side (`applyTGPhoto` → `foodAI.parseMealFromPhoto`) with the user's own or the trial key. **The account-scoping IS the whole boundary:** the relay cannot cross-check the requested `file_id` against the sealed mailbox (it is zero-knowledge ciphertext), but a `getFile` with bot A's token can only ever resolve files sent to bot A, so a session can only fetch its own bot's images.
- This is durable, contrary to first appearances: a Telegram **`file_id` is stable and re-usable** — it is the `file_path` returned by `getFile` that expires (~1h). The relay re-resolves on demand at drain time, so a photo sent on Monday and drained on Friday still fetches, as long as the file exists on Telegram's servers and the bot token is unchanged. A `getFile`/download failure is surfaced to the client as a normal error and the event is acked, not retried forever (a re-drain would re-pull bytes and re-bill the provider for a result that will not improve). Idempotent on success via per-item `tg-<mailboxEventId>-<index>` ids, like `/food`.

#### Closing the loop — "Queued" → "Recorded"

Seal-only forces the immediate reply to be generic: the relay cannot confirm what it cannot parse. But it does not force the reply to *stay* generic.

1. The relay sends `⏳ Queued — recorded when you next open the app.` and keeps the `message_id` Telegram returns, sealing it into the event alongside the raw text (`tgCommandEvent.reply_message_id`).
2. An unlocked client drains, parses, writes through the domain layer, and waits for the flush barrier.
3. It then composes the confirmation *itself* — `✅ Recorded BP 128/84.` — and POSTs it to `POST /api/telegram/reply-edit`, which calls `editMessageText` on that exact message.

**This adds no trust.** The relay forwards a string it never derived, from vault data it cannot read — the identical contract it already has for outbound `tg_text` (`SendReminder`: *"Nothing here derives text from account data"*). The chat is taken from the stored bot row, never from the request, so a session can only edit messages in its own chat. The confirmation honours the same `generic`/`detailed` verbosity as reminders: a user on `generic` gets `✅ Recorded.` with no health value crossing Telegram.

**Latency.** Originally nothing in cloud mode polled, so a drain only happened on page load. Today an open unlocked tab drains within ~1s of a seal via the content-free `inbox-ready` event on `GET /api/inbox/events` (bd med-j0tc, `internal/cloudserver/inbox_events.go`; the same stream carries `sync-ready`, see [Sync protocol](#sync-protocol)), and the poll below is the fallback when the stream is down. `startInboxPolling` now drains every 5s **whether or not the tab is visible**, and immediately on `visibilitychange`. Hidden tabs poll too (med-d15): the user is in Telegram exactly while this tab is backgrounded, so skipping the timer there made the mailbox silent for the whole window that matters — the ✅ only ever landed the instant they switched back. Browsers already clamp background timers to roughly one fire per minute, so the cost is about one empty `GET /api/inbox` per minute per backgrounded tab. With the app open, "Queued" becomes "Recorded" in a few seconds; backgrounded, within about a minute; with it closed, on next unlock.

**The wake (`med-5fo`).** The poll is the floor, not the only signal. A hidden tab's timer is throttled to ~1/min and a frozen page does not poll at all, but the server knows the *instant* a seal lands — so every seal path calls `TelegramAPI.sealAndQueue`, which fires `Relay.WakeInbox` (`internal/cloudserver/relay.go`). That fans a content-free `{"kind":"inbox-wake"}` out to the account's push subscriptions on the same non-NK channel as the stale-sync warning, coalesced to **at most one push per account per 10s** (a drain is per-account, not per-message, so the tab woken by the first message of a burst drains the rest). `web/cloud/sw.js` postMessages every open window — which `cloud-boot.js` turns into an immediate `drainInbox`, bypassing the poller's backoff gate — and suppresses the notification only when a window **acknowledges** the nudge on the transferred `MessageChannel` port within 1.5s. Existence is deliberately not the signal: `clients.matchAll` also returns a window that is frozen, still loading, or *locked*, and the ack listener is installed in cloud-boot's post-unlock path, so a locked window never handles the wake — exactly the case where the notification is the only thing that gets the event recorded. The page acks on receipt, not after its drain, so a slow drain cannot earn a duplicate notification. With no ack (or no window) the SW shows a FIXED client-side string, never server-supplied text. A failed seal wakes nothing.

**Known tax.** The subscription is `userVisibleOnly: true` (no browser offers silent push otherwise), so Chrome tolerates only a bounded number of notification-less pushes before it forces its own generic "this site was updated in the background" one. On a phone, a chatty Telegram day can therefore surface a notification per burst once that budget is spent. The wake is additive: no notification permission (or no subscription) means no wake, and the poll still applies.

**Commands implemented** (`web/domain/tgcommand.js` parses; the relay never does): `/bp 120 80 [pulse]`, `/weight 81.2`, `/food 200g chicken breast` (natural-language meal — the relay seals the raw text and the AI parse runs client-side at drain with the user's own or the trial key, bd med-eas.29.4), `/note …`, `/intake` (confirms every dose already due), `/workout [name]` (logs a completed ad-hoc workout for today through the shared workout domain — the "I did a workout" log, mirroring how `/bp` logs a reading; the name is an optional label, bd med-eas.29.5). An unknown command is answered too — and note that the *client* composes that refusal, because the relay is forbidden from telling `/bp` from `/bogus`.

**Free text (no command)** is sealed as a `tg_text` event and, at drain, handed to a browser-side OpenAI tool-calling agent (`web/cloud/js/tg-agent.js`, bd med-vcv.2): a two-tool discover-then-call loop (`mcp_help` + `mcp_call`) over the 110-op cloud MCP catalog, running with the user's own key, so the model can log something or read data to answer — one code path with the cloud UI and MCP connector (`createApiRouter` → `createDispatcher`). Every failure (no key, provider error) is answered and **acked, never retried** — the agent may already have written through a tool, and a re-drain would re-run a non-deterministic loop. A run that was *interrupted* instead (iOS suspended the page, a reload, a closed tab) leaves its `tgagentrun` marker (`tgtext-<eventId>`, put before the run) without a `reply`; the next drain evaluates it in order (bd med-ramv): (0) **legacy** — a marker without `startedAt` (an older bundle's) never tracked `wrote`, so it is not retried: "I could not finish handling that message."; (1) **lease** — `marker.startedAt` (the run's start on this device's clock; not `clientTs`, which the sync port skew-corrects to server time) within `TG_AGENT_LEASE_MS` (2 min) of now, either side, may be a run still going in another tab, so the apply throws and the event stays queued (a `startedAt` more than the lease in the future — the clock jumped back — is stale); (2) **wrote** — the agent router's records port puts `wrote: true` on the marker before its first `put`/`del` and awaits it, so the flag is durable in the local store before the tool write and any later local read sees it; such a run is answered `✅ Done.` without a second run; (3) **retry once** — no `wrote` and `attempts` < 1: the marker is re-put with `attempts: 1` and a fresh `startedAt`, and the agent runs exactly as a first run; (4) **exhausted** — the user gets "I could not finish handling that message; nothing was saved." `putIfAbsent` (read-path materialization, idempotent) does not set `wrote`. Under `generic` verbosity the answer is suppressed to a content-free ack, since a free-text reply can contain readings the user asked to keep off Telegram.

**Idempotency.** Writes use a deterministic `recordId` of `tg-<mailboxEventId>`, so a crash between flush and ack re-applies the event onto the same row instead of logging a second reading (drain rule 2). `/food` yields many rows from one message, so each item is keyed `tg-<mailboxEventId>-<index>`; a re-drain overwrites its own rows rather than appending. `/intake` needs no id — the domain's `PENDING` check is its own guard.

**Retention and logging invariants** (test these, don't trust them):

- **Never `slog` message content.** Not the text, not a typo'd command, not a caption, not the sealed ciphertext. Permitted fields: `ref`/account id, `update_id`, byte length, status codes. This extends the existing trial-proxy invariant (`slog.Info("trial chat proxy", …, "status", N)` logs a status, never a body) and the child-webhook rule already in the code: *"Do not log the raw Telegram payload, as it can contain PII."*
- **No inbox key → drop, never store clear.** `SealAndQueue` returns `ErrNoInboxKey` when `accounts.inbox_public_key` is NULL; the caller must discard the event and reply "Open the app once to finish setting up." Already implemented for callback taps; free-text must follow it.
- **No plaintext column, ever.** `inbox_events` holds `ct` and an ordering timestamp. Any bead proposing a `text` column has misread this section.
- **The relay keeps no copy after the response is written.** Message text lives in the request goroutine and dies with it.

**Consent copy implications** (feeds `med-eas.30`, which is blocked on this). Today's consent screen (`web/cloud/js/telegram.js` → `renderConsent`) covers *outbound* only: "it reads your reminder text." It says nothing about inbound, because inbound was two buttons. Once chat management ships, the copy must add, in the same plain register:

- that messages you send the bot are **read by Telegram and pass through this server in the clear** — because Telegram bots cannot be end-to-end encrypted;
- that the server **seals them immediately and never reads what they mean** — no parsing, no AI, no logs;
- that this is why the bot answers "queued" instead of telling you what it recorded, and that the record appears **when you next open the app**;
- for photos: that the image is **fetched through the server but never stored there**.

The honest one-liner for the consent screen: *"Telegram sees your messages. This server passes them along sealed, and never reads them."*

### Managebot onboarding — invites over chat

The manager bot is also the front door: an ordinary private message to it starts an onboarding conversation (`handleManagerMessage`, `internal/cloudserver/telegram.go`), reached from `ManagerWebhook`'s "not a `managed_bot_created` update" branch. Group chats and messages from bots are ignored — a group adding the managebot must not trigger onboarding — and the handler always answers 200, logging and swallowing every reply/mint failure, because a non-200 makes Telegram retry the update.

Flow, keyed on the sender's Telegram user id:

```
already claimed an account?  yes -> "you already have an account, unlock it with your passkey"   [no mint]
                             no  -> "yes"/"ok"/…      -> invite requests off ? "Invites are closed right now."
                                                         : tg request (one pending per user) + admin ping -> "I've asked the admin"
                                    /start|hi|help    -> explain + offer
                                    anything else     -> one-line nudge
admin taps Approve           -> mintMu | sweep | live invites >= 3 ? request declined + wait DM : Provision -> claim URL DM
admin taps Decline           -> "Sorry, invites are closed for now."
```

**Admin approval (bd med-ta2n.14).** "Yes" no longer mints: it files an `invite_requests` row (`channel='tg'`, migration `032`) and pings `FEEDBACK_ADMIN_CHAT_ID` with Approve / Decline buttons (`callback_data` `ir:<id>:a|d`). The same table and buttons serve the in-app email form (`POST /api/invite-requests` on the base host, `channel='email'`; in local mode the app shell sends it — bridge op `base.post`, `local-policy.js` `shellPost`, contract in bd med-ta2n.24 — so the route has no CORS and the local CSP never lists the base for it; the Settings button shows only when the shell has the op; on Approve the server emails the claim link over SMTP, `internal/cloudserver/mailer.go`). A tap counts only when `callback_query.from.id` is the admin chat and the message is that request's ping; the decision is a conditional `pending → approved|declined` UPDATE, so a second tap, a replayed callback or a Telegram retry answers "Already decided." and does nothing. `approved` means the mint and delivery are in flight; the run settles it `done` only once the requester or the admin holds the link (delivered, or the fallback edit carrying it went through), and only while it still owns the row (the settle matches the approval's own stamp). A run that never settles (a crash, a failed rollback, a lost fallback edit) is re-run by an Approve tap once 2 minutes (twice the 60 s work budget) have passed, under a new stamp, so the outlived run can no longer settle the row — a re-run may mint a second invite, and the unclaimed one simply expires. A mint failure reopens the request (buttons kept); a failed DM or email puts the claim link and a failure class in the admin message so the admin can pass it on by hand. Telegram requests need only the manager bot and `FEEDBACK_ADMIN_CHAT_ID`; the email form also needs the SMTP settings (startup log `invite requests email=<bool> telegram=<bool>`); with no admin chat the bot says invites are closed and never falls back to an unapproved mint. One Telegram user files at most one request per 7 days, whatever was decided. Email requests: bare address only (`net/mail`, no display name, no CR/LF, stored lowercased), note ≤ 500 chars, 5/hour per IP (in memory; no IP is stored), 50/day instance-wide (persisted, checked before the dedupe so a full day answers every address alike), one per address per 7 days (a repeat answers 202 and sends nothing), rows swept after 90 days.

**Provenance: `created_by_account_id` is overloaded.** A managebot mint stores `"tg:<telegram_user_id>"` in that column — do not read every value there as an account id. The column is `TEXT` with **no foreign key** (migration `010`), so three value shapes coexist: a real account id (user-mintable invites), `NULL` (admin-CLI invites), and `tg:<uid>` (managebot). They cannot collide — account ids are opaque and never carry a `tg:` prefix — so the 100/30d per-account quota above and the managebot's own counter are provably invisible to each other (asserted by `TestInviteQuotaIgnoresManagebotProvenance`). One column then serves provenance, the rate limit, and the already-connected check, with no migration and no new table. `ponytail:` promote to a `tg_invite_mints` table only if a second non-account minter ever needs provenance.

**Quota: 3 *live* invites per Telegram user**, hardcoded (`managerInviteQuota`), checked when the admin approves and refused with a plain-language wait message. It mirrors `POST /api/invite`: take `mintMu`, `SweepExpiredClaims`, *then* count — sweeping first because a user sitting at the cap never reaches `Provision`, so their own expired unclaimed invites would otherwise hold slots forever. An invite that expires unclaimed frees a slot.

The counting window is **the claim TTL, not a rolling day**: post-sweep, every surviving row attributed to that user is still claimable, and anything older was minted with an already-passed expiry. A per-day window would only cap the mint *rate*, not the number of claim links a user holds — since claiming happens out-of-band (passkey registration on the subdomain, nothing the bot sees), an abuser could say "yes" three times a day for the whole TTL and bank `3 × TTL/day` claimable links against the one-account-per-person promise. Pinned by `TestManagerOnboarding/day-old_unclaimed_invites_still_occupy_the_quota`.

**Already-connected check is a separate query, not the counter.** The sweep deletes expired *unclaimed* accounts, so a count cannot tell "claimed an account" from "has a pending invite". A claimed account has `claim_token_hash IS NULL` and survives the sweep — `HasClaimedAccountCreatedBy` tests exactly that. Without it, a returning user saying "yes" again would silently collect a second, empty account. A pending invite's link cannot be re-sent (the token is hash-only at rest), so a user with a live unclaimed invite who asks again gets a fresh one — up to the cap of 3 — and the old ones expire on their own.

**No `update_id` dedupe** exists anywhere in this codebase, and since med-ta2n.14 none is needed here: a retried `"yes"` finds the user's pending request and files nothing new, and a retried Approve finds the row already decided. Minting happens only on an admin Approve, still behind the two gates above.

### Feedback channel over the manager bot (med-dni.5)

A user can send feedback (text, voice, or a screenshot) through the **manager bot** as an alternative to the in-app UI. The manager bot's greeting/help reply carries an inline **"📮 Send feedback to developer"** button (`callback_data:"fb"`); tapping it (`handleManagerCallback`) prompts "send your message, voice, or screenshot now" and sets an in-memory capture flag. The sender's next message is turned into the same **v1 plaintext feedback doc** as the web path (`{v, created_at, text, attachments[]}`), **age-encrypted server-side to `FEEDBACK_AGE_RECIPIENT`** (`encryptFeedbackDoc`), and stored via `AppendFeedback` into the same blind `feedback_queue` with `kind:"telegram"`. The dev CLI (`cmd/feedbackpull`, med-dni.4) drains web and Telegram feedback uniformly.

**Server encrypts but stays blind.** This is the one place the cloud *server* encrypts to the recipient (the web path did it in the browser). The manager bot holds only the recipient **public** key, so it encrypts and cannot decrypt — the queue row is always ciphertext, nothing plaintext at rest. Telegram plaintext *in transit* is the user's own choice (they typed it into Telegram); the persisted row never is.

**Attribution: claimed senders only.** `feedback_queue.account_id` is `NOT NULL` and carries an account id (or `attest:<bucket id>` for local-mode feedback; migration 031 dropped the FK to `accounts(id)`, bd med-ta2n.19), and there is no tg-user→account mapping — only the overloaded `created_by_account_id = "tg:<uid>"` provenance. So the button is offered **only to senders with a claimed account** (`ClaimedAccountIDForCreator` resolves `tg:<uid>` → their `claim_token_hash IS NULL` account); the feedback attributes to that account. Unlinked senders never see the button, and a stale tap is answered "finish setting up your account first." Truly-anonymous TG feedback would need a reserved account id of its own — deliberately deferred.

**Disabled when unset.** The whole feature is gated on `FEEDBACK_AGE_RECIPIENT != ""` — unset means no button is ever attached and no capture happens, mirroring the web feedback API's disabled state. Capture state is an in-memory `map[chatID]expiry` with a ~5 min TTL on `TelegramAPI`; a restart drops a pending prompt (the user re-taps). `ponytail:` a one-column table only if cloud ever runs multi-replica.

### Admin relay: knowing feedback arrived (med-orj)

Both channels drop into the same blind queue whose only reader is `cmd/feedbackpull`, run by hand — so feedback nobody drains is feedback nobody sees. Setting **`FEEDBACK_ADMIN_CHAT_ID`** (numeric Telegram chat id, requires `MANAGER_BOT_TOKEN`) makes the manager bot DM the developer when an item lands. The two channels relay deliberately different amounts:

- **Web feedback → metadata ping only.** `FeedbackAPI` calls an optional `notify(kind, appVersion)` hook (`TelegramAPI.NotifyFeedback`) that DMs `📮 New feedback (web) · kind … · app … · <time> — read it here (link expires in 30 min): https://<base>/feedback#t=<token>`. **No content, no ciphertext, no account id** — the server holds a blob it cannot read and the E2EE promise stays literally true. The client-side encryption (`web/cloud/js/feedback-submit.js`) and the queue are untouched; reading still requires the age private key.
- **Telegram feedback → full content.** `relayFeedbackToAdmin` sends a one-line header plus a **`copyMessage`** of the user's own message, so a voice memo or screenshot rides along by `file_id` with no re-upload. This downgrades nothing: the manager bot already held that plaintext in memory to build the doc it then encrypted. `copyMessage` rather than `forwardMessage` keeps the sender unattributed (no "forwarded from" header), matching the web channel's anonymity; the queue row still carries the account id for `feedbackpull`. A refused copy falls back to sending the text.

**Never on the request path.** Both relays run on their own goroutine with a detached, timeout-bounded context — the web ping fires with `go a.notify(...)` *after* the 204 (whose request context dies with the response), and the Telegram relay is detached from the webhook so two more Bot API calls can't push it toward a redelivery (a redelivered feedback message finds the armed flag already cleared and would get a confusing onboarding reply). Every failure — a 403 because the admin never pressed `/start`, a refused `copyMessage` that falls back to sending the text — is a `slog.Warn`, never an error to the user: a broken notification must not turn a stored feedback item into a 500.

**One queued item, one DM.** `AppendFeedback` returns `queued bool` and the web ping only fires when it inserted, so the reliable-retry client re-POSTing the same `client_id` over a flaky connection doesn't announce "new feedback" again. `FEEDBACK_ADMIN_CHAT_ID` unset (or unparseable — logged and treated as unset) means no relay at all.

The base domain serves [privacy-policy.md](privacy-policy.md) rendered to static HTML at `https://<base>/privacy` (prod: the deployment's own base, the URL the store listings, the native shells and the web first-run footnote link). ### Web feedback reader: `/feedback` (med-rbl)

The metadata ping told the developer *when* to run `feedbackpull` — a chore needing the server's SQLite file, the age private key (which must not be on that server), and a Go toolchain, so in practice nobody ran it. The reader page moves the read to the phone the DM already arrived on, **without moving the key to the server**.

- **Page.** `web/cloud/feedback.html` + `web/cloud/js/feedback-reader.js`, served on the **base domain** (`router.go`'s base-domain branch returns before the subdomain ceremony-page switch, so both halves are handled there). Web feedback is anonymous — there is no account to scope it to. It is a plain shell page: `connect-src 'self'`, no app-document egress widening, and the only `web/static` asset the base domain serves is the vendored `age.min.js` the page decrypts with (an exact-path case, not a `/static/` prefix — copying the 150 KB bundle into `web/cloud/vendor` would be a second copy to drift).
- **Capability, not an account.** `cmd/cloud` has no admin HTTP surface at all (admin ops are a CLI subcommand), so rather than invent admin accounts the short-lived token **is** the capability, delivered over an already-authenticated channel: the developer's own Telegram DM. `feedback_reader_tokens` (migration 021) stores **SHA-256 of the token only**, with a 30-minute TTL, expired rows swept on the next mint (no background job — mirrors `SweepExpiredClaims`). It is **multi-use within the TTL**: the developer reloads the page, and a one-shot token would look like a bug. Validation walks the unexpired rows with `subtle.ConstantTimeCompare` rather than `WHERE token_hash = ?`.
- **Fragment, then header.** The DM link puts the token in the **URL fragment** (`/feedback#t=…`). Browsers never send a fragment to the server, so it stays out of access logs — and Telegram *prefetches* links to build previews, which would fetch a query-param token before the developer ever tapped it. The page reads it out of the fragment, immediately `history.replaceState`s it away, and sends it in the **`X-Feedback-Reader-Token` header** on `GET /api/feedback/queue`. A query-param token is not accepted.
- **Response.** `{items:[{id, kind, app_version, created_at, ciphertext_b64}]}`, **newest-first** (`ListRecentFeedback`), capped at 100. The direction is load-bearing: the per-account cap does not bound the queue *globally*, so past 100 undrained rows `feedbackpull`'s oldest-first drain order would push the very item the DM announced off the end of the window — and the page had no pagination and, before med-rbl.3, no way to drain. **No `account_id`, no `client_id`** — web feedback is anonymous by design and this endpoint must not be the thing that de-anonymizes it. Missing / unknown / expired tokens all get an identical 401 body.
- **Decryption is in the browser.** The pasted age identity goes into the vendored typage `Decrypter` (`addIdentity`, the sibling of the `addPassphrase` path `web/static/js/core/backup-crypto.js` already uses for `.json.age` import). Per-item failure is isolated — one unreadable row renders an inline error and the rest still show, mirroring `cmd/feedbackpull`'s fail-open drain. A malformed key is detected once, before the loop.
- **Ack: delete after reading (med-rbl.3).** `DELETE /api/feedback/queue` with `{"ids":[…]}` deletes exactly those rows and answers `{"acked":n}` — a count, never the rows, so the delete path cannot become the thing that attributes anonymous feedback. It is the **same capability token in the same header** as the read (one `authorized()` gate serves both verbs, so they cannot drift), and the id list is mandatory: an empty list, a missing field, or more than 100 ids is a 400. There is deliberately **no "drain everything" and no "delete older than"** — those are exactly the shapes that would ack rows nobody has looked at. Acking an id that is already gone is a 200 (`DeleteFeedback` is a no-op), so a second tab or a retried tap is not an error. A body on `DELETE` rather than a query string: the ids are the selector and a query string would print them into every access log for nothing.
- **Ordering rule: rendered, *then* acked.** `cmd/feedbackpull`'s `run()` renders each item into a buffer and writes it **before** deleting, so a failed write cannot destroy the only copy of the plaintext. The page holds the same property, and it *has* to hold it client-side: the server never sees plaintext, so it cannot verify anything was read. `renderResults` attaches the per-item **Delete** control only inside the success branch — an item that failed to decrypt gets no control at all, so "never delete what the developer has not seen" is a property of the markup rather than a rule to remember. The batch **"Delete all N read"** button carries only the ids that decrypted; the unreadable ones stay on screen *and* in the queue for `feedbackpull`. A rejected ack (expired token, network) removes nothing and shows a fixed message.
- **Key handling (required mitigation).** The owner accepted the "paste a private key into a web page" risk *against these mitigations*, so they are part of the deliverable: the key is never written to localStorage / sessionStorage / IndexedDB / a cookie / the URL, never logged, and never interpolated into an error message (every message the module produces is a fixed constant, so no library exception text can carry key material). The field is cleared the moment its value is read and again on `pagehide`. JS strings are immutable, so dropping references is the ceiling — the bytes cannot be zeroed. If web feedback ever becomes high-volume, the upgrade is wrapping the age identity in a WebAuthn-PRF envelope (machinery already in `web/cloud/js/crypto.js`) so nothing is typed at all.
- **Degradation.** A token-mint failure logs a `slog.Warn` and the ping falls back to the old "run feedbackpull to read" text — it never drops the ping and never touches the feedback POST. A deployment that never calls `SetFeedbackReader` 404s the queue endpoint. `cmd/feedbackpull` stays the fallback reader (and remains the only place account attribution is visible).

## BYO provider keys

All provider keys live as ordinary records inside the encrypted vault (synced across devices, invisible to the cloud). Calls go **directly from the browser** to the provider:

- OpenAI(-compatible) chat + vision endpoints support browser CORS; the existing first-run → integrations flow and `***`-masked settings UX carry over as-is.
- ElevenLabs conversational voice runs **browser-direct** on their SDK (WebRTC/WS). **A voice agent without data access is useless** — operating on the user's data is its entire purpose — so tools registered at `startSession` execute in the browser session itself, backed by the in-browser domain layer. No relay hop, and the availability constraint is trivially satisfied because the device is online and unlocked during its own call. Agent and tool provisioning happen from code against the ElevenLabs Agents API; the user sets only an API key. See [Voice (ElevenLabs)](#voice-elevenlabs) for the shipped detail. ElevenLabs' cloud sees tool names, tool **results**, and transcripts — inherent to any cloud voice agent; with the user's own key the audio, tools and transcripts are strictly user↔ElevenLabs. The one exception is the LLM leg: the agent's answers are generated by the user's own AI (or the operator's trial AI) through a blind browser relay on the operator's server — see the "LLM = the user's own AI" bullet in [Voice (ElevenLabs)](#voice-elevenlabs).
- **Food DB is the exception to "bring your own": too niche to ask users about.** The operator hosts an instance and cloud mode points at it silently as the built-in default — no setup step, no wizard mention, no expiring trial, no BYO nagging (it's excluded from the trial-pool CTA mechanics below). Settings → Integrations has no food-DB field since med-bpp9 (self-hosting is vanishingly rare, and the field linked to a repo that goes stale); a custom `integrations.food.url`/`api_key` stored earlier keeps working untouched (read path unchanged, and the save form omits the `food` group so it is never cleared). Honest note: food/barcode lookups necessarily reveal query terms to whoever hosts the DB — same exposure as public Open Food Facts, no health-record content.
- **Gamification AI narration (Phase 6, med-z1n.3) is opt-in prose OVER the deterministic engine, same BYO posture as food AI.** The Journey/Atlas screen's "AI Story" card offers per-tap narration (weekly story, chapter recap, experiment suggestion, workout insight). Tapping sends **only already-computed summaries** — the JSON the `/weekly-review`, `/atlas`, `/experiments`, `/chapter` read-models and the workout stats return (revealed discoveries, week deltas, verdicts, review lines, workout counts — discovery and verdict text for the goal probes/templates includes a weight-trend change in kg) — to the user's own OpenAI-compatible endpoint via the same `web/cloud/js/aiclient.js` path. **No raw vault records ever leave** (no BP/sleep logs, no diary text). The model returns prose only; every number on screen still comes from the deterministic cards, and the narration is a separate, visually-attributed block — a hallucinated figure can never displace a computed one. No key or any provider error → the narrate route returns `{text:null}` and the deterministic cards render unchanged (narration degrades to nothing).
- The existing graceful degradation contract is unchanged: no key → feature shows its "configure to enable" empty state; key added → capability appears immediately.

The pricing/consent story is clean: AI costs are the user's own, on their own keys; the cloud never proxies (and so never sees prompts, photos, or voice). The trial-keys pool below is the one deliberate, consent-gated exception.

## Trial provider keys (pooled, metered)

New users get AI features working immediately from a pooled set of operator keys (DeepSeek/OpenAI-compatible chat + vision, ElevenLabs) for a trial period — then bring their own keys, or the trial features degrade to their existing "configure to enable" empty states with a bring-your-own-key CTA. No hard account gate.

Design rules:

- **Pool keys never reach the device** (one extraction drains the pool). Two mechanisms instead:
  - **OpenAI-compatible chat/vision: a metered relay** that mimics the OpenAI API surface so the client is unaltered — trial mode is just the default base URL pointing at the relay with session auth; BYO is a settings change to the provider's real URL. Per-account quotas (requests/tokens per day), per-feature budgets, a global circuit breaker — the demo-mode rate-limit pattern this repo already has.
  - **ElevenLabs: server-minted signed session URLs** — the server mints the session with the pooled key; audio then flows device↔ElevenLabs directly and never transits our server.
- **The honest carve-out, stated on its own consent screen**: on trial keys, AI request content (food photos, prompts; ElevenLabs conversations under the *operator's* provider account) is visible to the relay in transit and to the provider under the operator's account. Nothing is stored and relay bodies are never logged — but it is a real, explicit downgrade from the BYO posture, and the user chooses it or enters their own keys on day one. The vault stays E2EE regardless; only in-flight AI content is affected.
- **Sequencing**: the relay ships only when the PWA has AI features to call it — alongside C2 (see phasing), not in C0.

Implementation (med-eas.25): trial keys are `TRIAL_*` envs on `cmd/cloud` (see [environment.md](environment.md#cloud-service-cmdcloud)), loaded into `cloudserver.TrialConfig`. Two account-authenticated proxy routes on the account subdomain: `POST /api/trial/openai/chat/completions[?vision=1]` (body forwarded as-is with `model` forced server-side to the trial model; when that model is gpt-6-luna and the body carries tools, the proxy also sets `reasoning_effort: "none"`, which luna requires for function calls) and `GET /api/trial/elevenlabs/signed-url` (server-minted with the operator's shared agent). In-call photos have no route of their own: they ride the voice turn to the chat route's `?vision=1` (bd med-ku8r). Client precedence: vault BYO key (browser-direct, unchanged) → trial proxy route → "set your key" error. Availability is advertised to the client as booleans only (`<meta name="medtracker-trial-ai|medtracker-trial-voice">`); no key, URL, or model ever appears in a response, meta tag, or log. Per-account sliding-window rate limit (`TRIAL_RATE_PER_MIN`, default 10/min) shared across these routes; on limit: `429 {"error":"trial_rate_limit","retry_after_seconds":60}`. Unconfigured routes return `503 {"error":"trial_not_configured"}` and the client degrades to today's pure-BYO behavior. With `TRIAL_AI_PROVIDER=anthropic` (bd med-p07e) the chat route keeps the same OpenAI-shaped contract but translates to the native Anthropic Messages API (`trial_anthropic.go`): `response_format` json_schema → structured outputs, tools/tool_calls → tool_use/tool_result, a `cache_control` breakpoint on the system prompt; tool-calling answers carry an extra `anthropic_content` field the client echoes back so thinking blocks round-trip. The OpenAI-compat endpoint is deliberately not used — it silently ignores `response_format`.

**Trial consent** (bd med-yor.2): every trial request is additionally gated client-side by an explicit, durable consent record — a `trialconsent` encrypted-vault singleton (`web/domain/settings.js`, routed at `PATCH/GET /api/settings/trial-consent` in the apishim) with three independent boolean-or-null scopes: `ai` (meal text/photo parsing), `voice` (trial ElevenLabs calls), and `tg` (the Telegram free-text agent and gamification narrator, whose messages carry vault-derived health data). Only literal `true` passes; `null`/missing means never asked and refuses — skipping key setup in the wizard is NOT consent. The disclosure dialog (`web/static/js/features/trial-consent.js`) is shown before first trial use and names the data categories, that content transits the operator's provider account, and the BYO alternative; consent is grantable and revocable in Settings → Integrations. BYO keys bypass the gate entirely. The record syncs across devices like any vault record but is deliberately excluded from export/import backups — a fresh account asks fresh consent. The server never sees consent state; the trial proxy stays dumb.

### Anonymous trial (local mode) — App Attest / Play Integrity

Two platforms, one protocol: iOS installs enroll with App Attest + DeviceCheck (below), Android installs with Play Integrity (*Android — Play Integrity* at the end of this section). Everything after enrollment — challenges, buckets and passes, quotas, chat/food/voice routes, the clientDataHash binding — is shared; only the enrollment body and the assertion's wire format differ, chosen by the install's `kind` (`attest_installs.kind`, migration `030_attest_install_kind.sql`; every pre-Android row is `ios`).

bd med-o7zq.15 (server; client: med-o7zq.16). iOS local mode has no account, so a request is signed by an **App Attest key** — one per app install — and every budget is counted on that key's **trial bucket** (bd med-o7zq.26): one device's trial, shared by the installs that rejoined it with its trial pass (see *Trial pass and buckets* below). Code: `internal/cloudserver/attest.go`, `internal/appattest`, `internal/cloudstore/attest.go`, migrations `027_attest_installs.sql`, `029_attest_buckets.sql`. Env: [environment.md](environment.md#cloud-service-cmdcloud) (`APP_ATTEST_*`, `DEVICECHECK_*`, `TRIAL_ANON_*`); deployment: [cloud-deployment.md](cloud-deployment.md).

**Routes** — base domain only (an account host 404s them), no session, `Cache-Control: no-store`, CORS (`GET, POST`) for the local-mode origins only (`wgapp://local` on iOS, `https://appassets.androidplatform.net` on Android), a per-IP limit of 60/min across all of them. All binary values are standard base64; the challenge is 32 random bytes and the client hashes the **decoded bytes**, not the base64 text.

- `POST /api/attest/challenge` → `{challenge, expires_in: 300, feedback_recipient}`. Single-use, 5-minute TTL, in memory (a redeploy just makes clients fetch a new one). `feedback_recipient` (bd med-ta2n.19) is the `FEEDBACK_AGE_RECIPIENT` age **public** key local-mode feedback is sealed to, `""` when feedback is off — the local bundle has no meta tag, and this needs no extra unauthenticated route.
- `POST /api/attest/enroll {key_id, attestation, challenge, device_token, pass?}` (body ≤ 32 KiB): consume the challenge (400 `challenge_invalid`) → `appattest.VerifyAttestation` with clientDataHash = SHA256(challenge) (401 `attestation_invalid`, no detail) → key already enrolled: 200 with its bucket's count (idempotent, no DeviceCheck call, no pass) → **with a `pass`**: rejoin — the pass must open a bucket (401 `trial_pass_invalid` otherwise, nothing stored), the key joins it, no DeviceCheck call → `200 {remaining, daily}` with the bucket's remaining count → **without one**: DeviceCheck query: **bit0 and bit1 both set → 403 `trial_already_used`**, DeviceCheck error → 503 `trial_unavailable` (fails closed; BYOK unaffected) → insert the row and a fresh bucket, then set bit0 (bit0 clear before) or bit1 (bit0 set, bit1 clear); the bit write failing deletes the row and its bucket and answers 503 → `200 {remaining, daily, pass}`. Every 200 also carries `granted` (bd med-ta2n.25): `true` on all of these paths, `false` only for a feedback-only key (below) — the client's one signal whether the key holds a trial. With anonymous voice on, every 200 also carries the bucket's `voice_remaining_seconds` / `voice_daily_remaining_seconds` and the limits `voice_lifetime_seconds` / `voice_daily_seconds` / `voice_call_max_seconds` (bd med-o7zq.28; additive — Settings shows the minutes from the grant or rejoin on, and all voice copy derives from them, so a `TRIAL_ANON_VOICE_*` change needs no app release; the pre-grant consent copy names no numbers). Query → insert → bit write runs under one lock, because DeviceCheck tokens differ per call and two keys from one device racing would otherwise both read bit0 unset (single instance; a multi-instance deploy needs a DB lease). A lost enroll response needs no re-enroll — Apple attests a key once — the client just proceeds to the chat route with that key.
- `POST /api/attest/trial/openai/chat/completions[?vision=1]` with `X-Attest-Key-Id`, `X-Attest-Challenge`, `X-Attest-Assertion`. Header checks first, under a 10 s read deadline and before any body byte is read: consume the challenge (400 `challenge_invalid`) → load the key (401 `install_unknown`: enroll a new key). Only then the long upstream deadline and the body cap (`maxTrialBodyBytes`) → `appattest.VerifyAssertion` with **clientDataHash = SHA256(challenge ‖ SHA256(pathAndQuery ‖ "\n" ‖ body))** (401 `assertion_invalid`), where pathAndQuery is the request URI exactly as sent (`/api/attest/trial/openai/chat/completions` or `…?vision=1`). This binds the assertion to the single-use challenge, the route and the vision flag, and the exact body; the client computes the inner SHA256 and the native op hashes challenge ‖ that digest → `stream:true` → 400 `stream_unsupported` → output capped at ≤ 1024 tokens (OpenAI path: `max_tokens`/`max_completion_tokens` in the body; anthropic path: the adapter's `max_tokens`, attest route only) and `n` dropped (one completion; the cap is per choice) → the account trial's per-subject burst limiter → one transaction: counter compare-and-set (a replayed or concurrently-raced counter → 401), the bucket's lifetime quota (429 `trial_budget_exhausted` scope `install`), its daily quota (scope `install-day`; `trial_usage` subject `attest:<bucket id>`), the **global daily budget shared with accounts** (scope `global`) → the same upstream proxy code as the account route (`proxyChat`: forced model, luna effort, sanitize, anthropic switch). A non-200 answer refunds the lifetime request (daily counters are not refunded, as for accounts). No idempotency keys: a retry is a new request.

- `POST /api/attest/feedback {client_id, kind, app_version, ciphertext}` (bd med-ta2n.19; client med-ta2n.20) — local-mode feedback, the attested twin of the session `POST /api/feedback`: same body shape and 5 MB cap, `ciphertext` sealed in the app to `feedback_recipient`. Recipient unset → 503 `feedback_disabled` before any challenge is consumed. Same header-first ceremony as chat, the assertion over SHA256(pathAndQuery ‖ "\n" ‖ body). Then one transaction: counter compare-and-set (401 `assertion_invalid` on replay) and `AppendFeedback`'s dedupe + cap under `feedback_queue.account_id = 'attest:' ‖ <bucket id>` (no accounts row; migration 031 dropped the FK). Keyed by the **bucket**, like every other attest budget, so a pass rejoin or a re-enrolled key shares the cap and the dedupe instead of minting a fresh allowance. 204 on store and on a client_id retry, 429 `feedback_queue_full` at 100 undrained items per bucket, 400 `invalid_request` for a signed but malformed body. `cmd/feedbackpull` and the reader drain these rows unchanged; a new item fires the same metadata-only admin ping (kind + app version, never the install or bucket). It spends no AI/food/voice budget and does not check `granted`: any enrolled key may send, a feedback-only one included (next item). The ciphertext, key id and bucket id are never logged by this route.
- **Feedback-only enroll** (bd med-ta2n.25; client med-ta2n.20): the enroll body (both kinds) takes an optional `"trial": false`. The attestation is verified exactly as above; then **no** DeviceCheck query or bit write, **no** Play recall read or write, no pass minted (a sent `pass` is ignored), and `device_token` may be empty. The key gets its own bucket with `attest_buckets.granted = 0` (migration 033; every older bucket reads 1) and the reply is `200 {remaining: 0, daily, granted: false}` plus `X-Attest-Challenge`, no voice fields; logged as `attest enroll keyed` with kind and `trial=false`. A re-enroll with `trial: false` answers the key as stored. Such a key signs feedback; `chat`, the food routes and `voice/start` answer **403 `trial_not_granted`** right after the header checks, before any body read or budget. **Upgrade**: the same key enrolls again with `trial` absent/true — with a `pass` it moves into that bucket (no DeviceCheck/recall); otherwise the grant gate of a fresh enroll runs on the existing row (DeviceCheck bits on iOS; recall on Android with the flag on, no gate with it off): granted → the bucket gets `granted = 1` and a new pass hash → `200 {granted: true, pass, …}`; both bits set → 403 `trial_already_used` and the row stays, so the install keeps sending feedback; a failed bit write revokes the grant → 503. The same-key upgrade is the Android path (a new integrity token over the same Keystore key); Apple attests a key once, so on iOS the shell's `attest.enroll` mints a new key and the upgrade is an ordinary fresh grant for that key — the feedback-only key's row stays, inert, and the client signs with the new key from then on. So a device refused the trial still sends feedback, and feedback alone never spends the device's DeviceCheck/recall bit. Abuse: every such key still costs a genuine App Attest / Play Integrity attestation; one device can mint many ungranted keys (~200 B each), bounded by the per-IP limit — a per-IP daily enroll cap only if that is ever abused.
- `POST /api/attest/delete` (bd med-egb3) — local mode's *Erase data on this device* deletes this device's trial record. Empty body; the assertion binds the URI like the food routes (`SHA256(challenge ‖ SHA256("/api/attest/delete\n"))`), so only a key of the bucket can delete it; no `trialGranted` gate (a feedback-only key erases too) and no counter compare-and-set (the challenge is single-use). Under `grantMu` it deletes the caller's **whole bucket** (`DeleteAttestBucket(q.install.BucketID)`: every install in it — the stale rows earlier reinstalls left behind included — and the bucket's counters and pass hash) → `204` plus the next challenge. Idempotent: a key already gone answers the usual `401 install_unknown`, after which the client erases silently. Day counters keyed by the dead random bucket id (`trial_usage 'attest:'`/`'attest-food:'`, `attest_voice_usage`) stay as unlinkable counters until swept; queued feedback ciphertext under `attest:<bucket>` stays on the server until the operator drains it (`cmd/feedbackpull`). The trial budget goes with the bucket. Apple's DeviceCheck flags, and Google's device recall if the operator switches it on, are kept by Apple or Google and the operator can't clear them; they limit how many free trials one phone can get after erasing (on iOS a pass-less re-enroll after an erase is the one grace the bit protocol allows, then bit1 caps it; see *DeviceCheck bit protocol* below). A pass restored from an Auto Backup or a second phone restored from this one's backup share the bucket, so they lose the trial too (`trial_pass_invalid` → the page drops the pass and enrolls afresh). **Client**: `local-policy.js` `eraseDevice` runs it first, through `base.post` (old shells answer `invalid path`), before anything is wiped (the assertion needs the shell's key): no attest shell or no attested key → skipped, nothing sent; `204` → erase, then `local.reset {dropAttest: true}` (the shells drop the attest key material, **never the trial pass**: it may name an older bucket this key's delete did not reach, e.g. after a reinstall whose enroll took a new feedback-only bucket — so only the current key's bucket is deleted); `install_unknown` (no server record for this key; possibly an iOS reinstall whose enroll failed while the pass still names a live bucket) → erase silently, no `dropAttest`; any retryable failure (network, 5xx, an old shell's `invalid path`, a server without the route's 404) → *Erase anyway?* (Cancel keeps everything), erase without `dropAttest`. Never retried.
- **Client (bd med-ta2n.20).** `local-boot.js` mounts the cloud's Settings → Send feedback row (`feedback-ui.js`) and the outbox drain wherever `window.Attest` reports support and the shell lists the `base.post` op (an older shell mounts nothing), with `feedback-submit.js`'s transport swapped by `local-policy.js` `mountLocalFeedback`: the recipient comes from the challenge JSON (`local-trial.js` `feedbackRecipient()`, kept in `localStorage` for an offline Send), the drain POSTs this route through the shared attest client (one client for the trial and feedback, so one enrollment), whose challenge, enroll and feedback requests the shell sends (`base.post`, `shellPost` in `local-policy.js`, contract med-ta2n.24 §A/§B); the op's `network` error is a retryable status 0. **Voice** (bd med-o7zq.22; client: med-o7zq.23). The call-agent button in local mode, on the same enrollment, key and trial switch. Audio runs phone ↔ ElevenLabs directly on the **operator's** shared trial agent; its custom LLM is the voice relay (`voice_llm_relay.go`), which for these calls answers each turn **itself** with the trial AI instead of forwarding it to the phone.

- `POST /api/attest/voice/start` — empty body, the same three headers; clientDataHash = SHA256(challenge ‖ SHA256(pathAndQuery ‖ "\n")). Gates in order: `TRIAL_ELEVENLABS_*` and trial AI configured and `TRIAL_ANON_VOICE_LIFETIME_SECONDS` > 0 (**off by default**: unset means 0, so a server with the ElevenLabs and trial-AI env but no `TRIAL_ANON_VOICE_*` keeps anonymous voice off), else 503 `voice_not_configured` (a distinct code: "voice is not available on this server", not "add your key") → header checks and the assertion as for food → a call of this bucket that no device leg ever attached to is ended first (refunded under the Metering rule below; a leg still dialing its token gets 4404), then a remaining live or in-grace call → 409 `call_in_progress` (end it first; a re-attach uses the device route) → one transaction: counter compare-and-set (401 on replay), then **grant = min(lifetime left, today's per-install left, today's global left, `TRIAL_ANON_VOICE_CALL_MAX_SECONDS`)** seconds; grant < 30 s (the floor) → 429 `trial_budget_exhausted` scope `voice` (lifetime), `voice-day` or `global`, with `resets_at` for the two day scopes; otherwise the whole grant is **charged** → the signed URL is minted with the operator key (`mintTrialSignedURL`, shared with the account route) — failure → full refund, 502 `upstream_error` (no signed URL reached the client; the other refund is a never-attached call, see Metering) → the call is pre-registered in the relay under subject `attest:<key id>` → `200 {signed_url, call, granted_seconds, remaining_seconds, daily_remaining_seconds, voice_lifetime_seconds, voice_daily_seconds, voice_call_max_seconds}` plus `X-Trial-Voice-Remaining` (lifetime seconds left; the body carries the same figure, the header is not CORS-exposed).
- `GET /api/attest/voice/device?call=<token>` — the WebSocket device leg (browsers cannot set headers on a WebSocket, so the token the attested start minted is the capability, as it is for ElevenLabs). The upgrade accepts the same two local-mode origins as the CORS above, nothing else cross-origin. Only anonymous calls attach here (an account call's token, or an unknown/expired one, closes 4404; an anonymous token never attaches on the session route). It must attach within 60 s of the start. Same hello/keepalive/30 s grace as the account leg; no request frame ever arrives on it.
- **Turns**: ElevenLabs POSTs `/api/voice-llm/chat/completions` with the call token; for an anonymous call the relay runs the account trial's `proxyChat` (stream on, `n` dropped, output ≤ 1024 tokens, the per-subject *stream* limiter of 60/min, the per-call and global turn ceilings of [Voice relay abuse bounds](#voice-relay-abuse-bounds-bd-med-93u1)) and relays its SSE — **only while the device leg is attached** (the leg gates AI answers, it does not meter time; before it attaches or during the grace after a drop the turn gets the retry sentence and no AI call). Any non-200 (upstream failure, the limiter) speaks the retry sentence + `[DONE]` with HTTP 200, as the forwarded path does. No per-turn App Attest assertion (latency); turns are **not** counted as trial AI requests and never touch `trial_usage` — the minute budget bounds them. Content is never stored or logged (the turn log line carries sizes, duration and outcome under the attest subject).
- **Metering: every start costs its whole grant, charged at mint.** Nothing is refunded for an early hang-up or a dropped leg, whatever the turn count: once the signed URL is out, the ElevenLabs session it opens runs on the operator's account whatever the device leg does, so the leg cannot be the meter. **One exception, bounded (bd med-02b0): a call no device leg ever attached to costs nothing** — when the relay drops it (attach window over, or replaced by the bucket's next start) the grant is refunded (`RefundAttestVoice`, lifetime and that UTC day's counters; log line `attest voice start abandoned` with `refunded`), for at most **3 such starts per bucket per UTC day**, and server-wide while the day's free starts total ≤ half of `TRIAL_ANON_VOICE_GLOBAL_DAILY_SECONDS` (each counted at max(grant, `TRIAL_ANON_VOICE_CALL_MAX_SECONDS`)); past either cap they are charged as above. A start for a bucket whose dropped call is still being refunded waits for that refund before reserving. The counters are in memory (a restart resets them). A budget timer at mint + grant sends `{"type":"budget_exhausted"}` on the device leg and closes it with **4429** (the client then ends the ElevenLabs session); until the call is reaped its turns speak "Your free voice minutes are used up — please hang up." The call is reaped after the grace following the last detach, or after the attach window when no leg ever attached; then the install may start again — on what is left. No live call is persisted (the relay table is in memory by design); a crash needs no settlement because nothing is pending.
- **ElevenLabs-side backstop**: `pnpm trial:agent` sets, on the shared trial agent, `max_duration_seconds` (`TRIAL_VOICE_MAX_CALL_SECONDS`, default 120 — keep it ≤ `TRIAL_ANON_VOICE_CALL_MAX_SECONDS`) and `turn.silence_end_call_timeout` = 30 s, so an abandoned session ends after half a minute of user silence instead of running to the cap ([agents API](https://elevenlabs.io/docs/api-reference/agents/update)). Both also apply to account trial calls (which are therefore capped at 2 minutes by default).
- **Threat model.** **One charged start = one ElevenLabs session**: the anonymous mint asks for `include_conversation_id=true`, which per ElevenLabs makes the signature single-use ([get-signed-url](https://elevenlabs.io/docs/api-reference/conversations/get-signed-url)); a plain signed URL could open further sessions within its validity window (the account route keeps the plain mint). Each session lasts at most `max_duration_seconds` (`TRIAL_VOICE_MAX_CALL_SECONDS` ≤ `TRIAL_ANON_VOICE_CALL_MAX_SECONDS`, both 120) and was charged its grant, which equals the per-call max except for a *short* grant (30 s ≤ grant < max) issued when a scope has less than a call left. So ElevenLabs time per start ≤ max(grant, `max_duration_seconds`): the overrun is (max − grant) on short grants only. With the approved values (600 lifetime / 300 daily / 120 per call) every short grant is 60 s and an install gets at most two of them (each day's cap ends in one, the lifetime ends in one, and 600 s holds at most two 60 s remainders), so ElevenLabs time per install ≤ 720 s — the voice budget plus one call's max. **Globally the bound is per-start, not per-second**: the charged total per day is capped at 7200 s, but an adversarial population whose every start is a short grant (each install's last 60 s, or the global cap's own last < 120 s) runs each such start to the 120 s cap, so worst-case ElevenLabs time per day is ≤ 2 × 7200 s with the approved values (≤ 4× for 30 s grants in other configurations); ordinary use, where most grants are full, sits near 1.2×. Other values change the overrun term (a daily cap that is a multiple of the per-call max has none); the silence end-call timeout usually ends an abandoned session well before the cap. Re-minting while an old session still runs buys nothing extra — each mint is paid in full, except the never-attached refund: a device could open the ElevenLabs session from a signed URL without ever attaching the leg (no AI turns are answered then, but STT/TTS time runs) and get the grant back, which is why that refund is capped at 3 per bucket per UTC day (the extra is ≤ 3 × 120 s per bucket per day) and, because a refund also gives the global SUM back (many buckets, or reinstalls into fresh buckets), server-wide at half of `TRIAL_ANON_VOICE_GLOBAL_DAILY_SECONDS` of free sessions a day (3600 s at the default 7200), each counted at max(grant, per-call max) ≥ what its session can run. So the global worst case becomes ≤ 2.5 × 7200 s of ElevenLabs time per day with the approved values (2 × 7200 for charged starts plus 3600 for free ones). A restart resets the in-memory counters, acceptable at deploy frequency. AI spend is bounded too: turns are answered only while the device leg is attached. One call per bucket in the relay at a time (two installs of one bucket share it); the bucket bound (below) holds for voice too. The bound depends on the agent's `max_duration_seconds` being ≤ the per-call max — an operator who raises `TRIAL_VOICE_MAX_CALL_SECONDS` above it widens it to (starts × that cap).
- **Failure modes.** ElevenLabs mint down → 502 and a full refund. Relay restart → live calls vanish; ElevenLabs' next turn speaks the hang-up sentence; the charge stands. Trial AI upstream down → spoken retry, the call keeps running on its grant.
- **Stored**: `attest_buckets.voice_seconds` (lifetime; `attest_installs.voice_seconds` from migration `028_attest_voice.sql` is no longer read) and `attest_voice_usage (day, key_id, seconds)` (per day, `key_id` holding the bucket id; global = the day's SUM). Seconds only: no audio, transcript, turn text or token (privacy manifest row `local-voice`).

**Trial pass and buckets** (bd med-o7zq.26). A fresh grant founds a bucket (`attest_buckets`: id = the founding key id, the lifetime request and voice counts, `pass_hash`) and returns its **trial pass** once, in that grant response only: `<bucket id>.<secret>`, the secret 32 bytes of `crypto/rand` (raw base64url). The server stores only SHA-256(secret), compares it in constant time, and never logs the pass. The iOS shell keeps it in the Keychain (`attest.setPass`; `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not iCloud-synced), which survives deleting the app, and hands it back in the next install's `attest.enroll` reply; `local-trial.js` sends it on that enroll and the new key joins the bucket. Every counter — lifetime and daily requests, food daily, voice lifetime/daily (global stays the day's SUM), the burst limiter and the one-call-at-a-time relay lock — is the bucket's, read and written in the same transaction as the key's assertion counter compare-and-set (a write first, so `BEGIN IMMEDIATE` serializes two installs of one bucket), so a rejoin resets nothing and concurrent installs never double-spend. Old keys of the bucket keep working and share the counters. A pass the server refuses (`trial_pass_invalid`: wrong secret, unknown or pass-less bucket, malformed) is dropped by the client, which enrolls once more without it. Migration 029 backfills one pass-less bucket per existing install (id = key id) with its counters, so the existing `attest:<key id>` / `attest-food:<key id>` / `attest_voice_usage` rows already belong to it and testers keep their budgets; such an install gets a pass only through a later fresh grant. Rolling the binary back past 029 leaves the old per-install `used` / `voice_seconds` columns stale (the down migration copies each install's bucket counts back onto it).

**DeviceCheck bit protocol**: bit0 = "this device was granted a trial", written at the **first grant** (enrollment), never at exhaustion; bit1 = "and a second, pass-less one" (a wiped phone whose Keychain is gone, or an install from before trial passes), written at that grant. DeviceCheck is touched only at a pass-less enrollment, never per request and never on a rejoin. A reinstall with the pass rejoins its bucket; without one it gets one fresh bucket while bit1 is clear, and `trial_already_used` once both bits are set.

**Threat model.** App Attest proves a genuine build of our app on a real Apple device, per install key. It does **not** prove a hardware identity or that two keys are the same device — DeviceCheck's two bits are the only cross-install signal the device cannot clear, and they hold no counter, so pass-less reinstall farming is bounded by the two bits: at most two buckets per device. The trial pass only ever joins a bucket, never founds one, so presenting (or copying) one can at most share an existing budget; guessing one means a 256-bit secret behind a genuine attestation per try and the per-IP limit. Emulators and jailbroken devices are out of scope (App Attest is Apple's answer; we add nothing). Cost is bounded by lifetime × buckets (≤ 2 per device), the per-bucket daily cap, the global daily budget, and the 1024-token output cap. Accepted gap: a crash between the row insert and the bit0 write leaves a granted key with the bit unset — at worst one extra trial after a reinstall; no status column for it.

**Failure modes.** DeviceCheck outage → enrollment 503, already-enrolled installs keep working. Apple root rotation → update the embedded root in `internal/appattest`. Lost challenge map (redeploy) → clients fetch a new challenge.

**What the server stores**: per install the key id, its public key (PKIX DER), the last assertion counter, its bucket id, the environment and two timestamps; per bucket the lifetime request and voice counts, whether it holds a trial grant (`granted`), and the SHA-256 of its trial pass secret (never the pass); the daily counts in `trial_usage` (AI and food apart) and `attest_voice_usage`, by bucket. Not the device token, not prompt text or photos — those transit memory only, exactly as in the account trial (privacy manifest row `local-trial`). Food search terms and scanned barcodes likewise transit memory to the operator's food DB and are never stored or logged — only the per-install daily food count (row `local-food`). Local-mode feedback (bd med-ta2n.19) is stored as `feedback_queue` rows under `account_id = 'attest:<bucket id>'`: client id, kind, app version, receive time and the age ciphertext the server cannot read, until the developer drains them.

#### Android — Play Integrity

bd med-nt9p.32.8.3 (server; client: med-nt9p.32.8.4). Code: `enrollAndroid` in `internal/cloudserver/attest.go`, `internal/playintegrity`. Env: `PLAY_INTEGRITY_*` ([environment.md](environment.md#cloud-service-cmdcloud)); deployment: [cloud-deployment.md](cloud-deployment.md). The subject is an app-generated **Android Keystore P-256 key**, one per install; its key id is derived, never chosen: base64url-nopad(SHA256(SPKI DER)).

- **Enroll**: `POST /api/attest/enroll {kind:"android", key_id, public_key, integrity_token, challenge, pass?}` (`public_key` std base64 SPKI DER; same 32 KiB cap — a token is ~1–2 KB). A body **without** `kind` is the iOS body, handled exactly as above (every iOS build sends none); an unknown `kind` → 400 `invalid_json`. Android not configured → 503 `trial_not_configured` (and on an Android-only server the iOS body gets the same). Consume the challenge (400 `challenge_invalid`) → `playintegrity.VerifyEnrollment` (401 `attestation_invalid`, reason logged, never the token or verdict): the key is P-256 and `key_id` is its derived id; Google's `decodeIntegrityToken` answers the verdict; `requestPackageName` and `appIntegrity.packageName` = `PLAY_INTEGRITY_PACKAGE_NAME`; **`requestHash` = base64url-nopad(SHA256(challenge ‖ key_id ‖ SPKI DER))** — the standard request's binding of this single-use challenge to this key (the client passes it to `setRequestHash`); `timestampMillis` within 10 minutes; `appRecognitionVerdict` ∈ `PLAY_INTEGRITY_ACCEPT_APP_VERDICTS` (default `PLAY_RECOGNIZED`); `deviceRecognitionVerdict` ∋ `MEETS_DEVICE_INTEGRITY`. Google unreachable / non-400 error → 503 `trial_unavailable` (fails closed, as DeviceCheck); Google 400 (a token it cannot decode — or a wrong package name, then *every* enroll) → 401 plus a distinct warning log line. Then the iOS flow without DeviceCheck: key already enrolled → 200 (idempotent); a `pass` → rejoin; otherwise a fresh bucket and `200 {remaining, daily, pass}` (the same response shape, voice fields included). The row is `kind = android`, `env` = the accepted app verdict, so a sideload-test-window grant reads `UNRECOGNIZED_VERSION`.
- **Assertions** (chat, food, voice start — same headers, same clientDataHash): `X-Attest-Assertion` = std base64 of **counter (uint32 big-endian) ‖ ECDSA ASN.1 DER signature**, where the Keystore signs SHA256withECDSA over clientDataHash ‖ counterBE. The counter must exceed the stored one; the same store compare-and-set (`UPDATE … WHERE counter < new`) commits it, so a replay or a concurrent race → 401 `assertion_invalid`. An install whose kind the operator has switched off answers 503 `trial_not_configured`.
- **Device recall — the DeviceCheck twin** (bd med-nt9p.32.8.6; `enrollAndroidRecall`). **Off unless `PLAY_INTEGRITY_DEVICE_RECALL` is set**, and only meaningful once Device recall (a gated Google beta) is enabled in Play Console. Off: a pass-less Android enroll always founds a bucket — farming is bounded by each enroll needing a fresh genuine Play Integrity verdict (Play-distributed app, device integrity), the per-IP limit, `TRIAL_DAILY_GLOBAL` and the global voice cap; the trial pass keeps an honest reinstall in its bucket. On: the verdict's `deviceIntegrity.deviceRecall.values` carries the same **bit protocol as DeviceCheck** above — `bitFirst` = "this device was granted a trial", `bitSecond` = "and a second, pass-less one", `bitThird` unused (never written). Only a pass-less enroll reads or writes them; a rejoin and an idempotent re-enroll never do. With the flag on, the grant lock is held from the idempotent lookup through the write, so a concurrent enroll of the same key never answers 200 for a row a failed write then rolls back. Both set → 403 `trial_already_used`, nothing stored. Otherwise, under the same grant lock as iOS: insert the row and bucket → `POST playintegrity.googleapis.com/v1/{package}/deviceRecall:write {integrityToken, newValues:{bitFirst:true}}` on a first grant, `{bitFirst:true, bitSecond:true}` when the verdict showed `bitFirst` (the same token, bearer and scope as the decode). **The write only ever sets bits — a `false` is never sent**: the verdict's values are a snapshot (a standard-request client caches them at warm-up), and echoing a stale `false` would clear a bit Google already holds and reopen pass-less farming. The guide leaves unspecified bits unchanged; the REST reference lists all three as required — if Google enforces that, every write fails and the grant rolls back (503, fail closed, never a cleared bit), which the owner device check (bd med-nt9p.32.8.9) catches before the flag is relied on → `200 {remaining, daily, pass}`, logged with `second_grant`. Fail closed: `deviceRecall` absent from the verdict (flag on, Console opt-in off) → 503 `trial_unavailable` plus a warning naming the Console switch; a write error (Google down, or an unevaluated recall `{"values":{}}`, which Google refuses to write) → the row and bucket are deleted → 503. **Threat model**: Google keeps three recall bits per device, shared by every app of the developer account, surviving reinstall and factory reset (retained 3 years after last access); we use two, so pass-less farming is bounded to two buckets per device, as on iOS. Accepted windows, same class as iOS: a crash between the insert and the write, and recall propagation (≤ ~30 s; a standard-request client refreshes the values only at warm-up) — at worst one extra bucket.
- **What goes to Google**: one opaque integrity token per enrollment, from our server to `playintegrity.googleapis.com` (bearer minted at `oauth2.googleapis.com` with the service account); with device recall on, a pass-less grant also sends that token back with the two recall bits. No health data, no account, never per request. **Stored**: the same row as iOS plus `kind`; never the token or the verdict beyond the app-verdict string in `env`.
- **Signing-cert pin** (`playintegrity.Config.CertDigests`) is left off: `PLAY_RECOGNIZED` already implies Play's signing certificate, and the digest encoding is unverified against live Google.

## MCP

"MCP" and "a server that cannot read the data" genuinely conflict: the server cannot answer a single catalogued operation. The resolution is that the server proxies MCP *to the user's own devices* — the only question left is who can read the frames, and that is what separates the two tiers below.

**Tier 1 — blind relay + local shim (preserves zero knowledge). PoC implemented**, see
`docs/plans/completed/2026-07-05-cloud-c4-poc-mcp-blind-relay.md`. For Claude Desktop / Claude Code,
which can run a local stdio MCP server:

```
Claude Desktop ──stdio── cmd/mcpshim ──wss:// ciphertext ──► cloud relay ──► user's device (PWA)
                          (holds a pairing key)  (blind pipe)   (decrypts, runs op, answers)
```

- **The shim is a Go binary** (`cmd/mcpshim`, built from the repo — `go build ./cmd/mcpshim`),
  not an npm package; it uses the already-vendored `modelcontextprotocol/go-sdk` stdio
  transport and the `internal/mcpshim` package for dial/crypto/request-correlation. No
  config file — reads `MEDTRACKER_MCP_CODE` from the environment, reconnects on drop, logs
  to stderr only.
- **Pairing code**: the PWA's Settings → "Connect Claude" screen POSTs `/api/mcp/pairings`
  (session-authed) to mint a `{pairing_id}`, generates 32 random key bytes client-side, and
  shows a one-time code `mtmcp1.<base64url(json{relay_url, pairing_id, key})>` — the key
  never touches the server. The user pastes the code into the shim's `MEDTRACKER_MCP_CODE`
  env var. "Disconnect" issues a DELETE and drops the stored key (kept in a vault record
  `mcppairing` so any unlocked device can answer).
- **Frame format** (both directions): `nonce(12) ‖ AES-GCM(key, payload, aad="mt/v1/mcp"‖pairing_id)`,
  payload = one JSON-RPC MCP message. The relay (`internal/cloudserver/mcp_relay.go`) pipes
  opaque binary frames between the shim leg (`GET /api/mcp/relay/shim?pairing=<id>`,
  authenticated by possession of the single-use pairing id) and the device leg
  (`GET /api/mcp/relay/device`, authenticated by the existing session cookie) — no
  inspection, no buffering beyond one in-flight frame per direction, 5 MiB frame cap,
  closes both ends when either drops. Pairings are in-memory (die with process restart) and
  currently one shim + one device per pairing.
- **The device leg presents its pairing id** (`?pairing=<id>`) and the relay checks it against the
  account's current pairing. A browser `WebSocket` cannot read a handshake HTTP status — a reject and
  a network drop both surface as `onclose` — so both failures accept the upgrade and then close with
  an application code the responder can branch on. The two codes are **not** interchangeable:

  | code | meaning | responder |
  |---|---|---|
  | `4404` `StatusNoPairing` | the account has no pairing at all (relay table is in-memory, 24h TTL, lost on redeploy) | stop, and **purge** the vault record — it is a tombstone pointing at nothing |
  | `4409` `StatusPairingReplaced` | the account has a live pairing, but this leg is not the one serving it | stop, and **do not purge** — release the Web-Lock election so the tab holding the current key takes over |

  The `mcppairing` vault record is CRDT-synced across devices, so a tab that purges on `4409` would
  delete the pairing every other device just adopted. A leg presenting *no* pairing id (an old
  responder from a previous deploy) takes the `4409` path: it cannot prove which pairing it holds.
  Without this check a stale tab reconnects onto the current pairing's device slot, evicts the tab
  holding the right key (`pairingRecord.join` is last-writer-wins), and silently drops every frame it
  cannot decrypt — the connector looks alive and every `mcp_call` times out.

  `4409` is sent from **two** places, and both need it. `DeviceSocket` rejects a leg whose pairing id
  is stale or absent (above), and `pairingRecord.join` closes the leg it evicts when a newer one takes
  the device slot. The eviction case is not the stale-tab case: two *legitimate* devices (phone and
  laptop, both unlocked, both synced to the current pairing) each pass the id check, so they take turns
  evicting each other. An abrupt `CloseNow` there reaches the browser as `1006`, which the responder
  reads as a transient drop and retries — re-evicting its replacement, forever. Closing with `4409`
  makes the loser step aside. (One device leg per pairing is the standing limitation; per-device
  pairings are full-C4 scope.)
- The device answers using the *same operation catalog* as `internal/mcp/registry`, served by
  `web/cloud/js/mcp-responder.js` — `mcp_help` (discover) and `mcp_call` (executed by the
  in-browser domain layer against local data, same construction path as `apishim`).
- **Cloud MCP is a two-tool surface — `mcp_help` + `mcp_call` — by design, not by omission.**
  A third tool, `mcp_execute`, appears in the shared operation vocabulary but is structurally
  impossible here: it would fork a script runner server-side, and the server never sees vault
  plaintext, so that runner would have nothing to read. Making it work would mean shipping
  plaintext to the server, which is the one property this whole design exists to prevent.
  Calling `mcp_execute` against a connector returns an explicit error
  saying so (`web/cloud/js/mcp-responder.js`), rather than an opaque "unknown method" an agent
  would retry; `USAGE_PROTOCOL` also states it up front. Multi-step work is done by chaining
  `mcp_call`, one operation per call.
- **Availability**: every cloud MCP call requires a live, unlocked browser tab. There is no
  server-side fallback — by design, for the same reason. If no device is unlocked and online,
  the call returns an actionable error instead of hanging.
- Running the Python sandbox **in the browser** via Pyodide is the only route that would preserve
  zero-knowledge — the script would run in the unlocked tab against the already-decrypted vault, and
  only its output would cross the relay. The spike (bd med-csu.6) weighed it and **decided not to
  build it.** Three reasons: (1) it ships a ~10 MB WASM runtime into the DEK-bearing page — the most
  security-sensitive surface in the app; (2) instantiating that WASM needs `'wasm-unsafe-eval'` added
  to `script-src`, directly reverting the strict `script-src 'self'` that med-7e7.1 *just restored*
  (pure `runPython` avoids full `'unsafe-eval'`, but the relaxation is still on the DEK page); (3) the
  value is unproven — `mcp_call` chaining already covers multi-step work, and the deleted `python/`
  helper package assumed `api.call` over the signed server bridge, so a browser
  runner would need its whole transport rerouted through the in-process `apishim` router. Revisit only
  if a concrete agent task emerges that provably can't be expressed as chained `mcp_call`s.
- **The catalog is generated, not hand-written.** `web/cloud/js/mcp-catalog.generated.js` is
  emitted from `registry.DefaultOperations()` by `cmd/genmcpcatalog` (logic in
  `internal/mcp/catalogjs`); regenerate with `go run ./cmd/genmcpcatalog`. **9 of the 106**
  registry ops are excluded, each listed individually with a `Reason` in `catalogjs.Excluded`:
  the 8 **gamification** ops (deferred project-wide, clamped out of `apishim.js`'s `PORTED_SET`)
  and **`workouts.miband.gps`** (cloud vaults carry no GPS tracks — `vaultToRecords` drops
  `workouts.miband[].gps` on import, so the op could only ever return an empty track; see
  [docs/vault-format.md](vault-format.md)). That leaves **97 generated ops, every one of them
  dispatchable**. The responder then serves **114**: `web/cloud/js/mcp-responder.js` merges
  `[...GENERATED, ...CLOUD_EXTRA]`, and `mcp-catalog.cloud-extra.js` adds seventeen ops that exist
  only here (the two composite analyses, `health.brief`, `workouts.progression_preview`,
  `medications.doses.list` / `medications.doses.act` (the occurrence projection and explicit
  dose actions on occIds), `workouts.plans.export` / `workouts.plans.import`, and
  `workouts.equipment.list` / `workouts.equipment.create` / `workouts.equipment.update` /
  `workouts.equipment.delete`, `workouts.locations.list` / `workouts.locations.active.get` /
  `workouts.locations.set_active` / `workouts.locations.export` / `workouts.locations.import`).
  So "97" is the count of the generated file; "114" is what `mcp_help` lists. The same module also applies
  `CLOUD_EXTRA_PARAMS` — params that exist only in the cloud router, merged over the generated
  catalog entries. It is applied as a copy, so no id is
  ever duplicated and the drift-guarded generated module is never mutated in place.
  `internal/mcp/catalogjs/drift_test.go` fails CI when a registry op is neither in the checked-in
  catalog nor excluded, and when the checked-in file is stale.
- **`mcp_help` is compact-by-default.** Full entries for all ops are ~106 KB; the compact
  projection (`id/topic/method/risk/description/required`) is ~30 KB. This started as a hard
  constraint — 106 KB was over the then-64 KiB `maxRelayFrameBytes` — and survives the raise to
  5 MiB as a context-budget one: the frame now fits, but an agent's window still shouldn't spend
  100 KB on a catalog it will use five entries of. Precedence: `operation_id(s)` → full entries,
  `query` → compact matches (never
  auto-expanded), `topic`/no-args → compact catalog + `usage_protocol`.
- **The `mcp_call` envelope** (canonical definition: `createDispatcher` in `web/cloud/js/mcp-responder.js`): `operation_id` (with
  `op` kept as a back-compat alias), `params`, `path_params`, `body`, `mode`, `intent`. The three
  definitions that must stay in lockstep are `web/cloud/js/mcp-responder.js`,
  `cmd/mcpshim/main.go`'s `callInput`, and `internal/cloudserver/mcp_endpoint.go`'s
  `mcpEndpointCallInput` — `TestMCPCallEnvelopeLockstep` fails CI on drift. `path_params` are
  allowlisted against the op's catalog entry and URL-encoded into the op's `{slot}`s. `params` and
  `body` merge (`body` wins on a key collision) for validation and relative-date repair, then split
  back apart by schema: a key the op declares in `params_schema` but not `body_schema` becomes a
  querystring param, everything else is the request body (GET/DELETE take no body, so all of it is
  query). Arrays repeat their key (`tags=a&tags=b`), objects encode as JSON — the only lossless
  option a flat querystring affords. Schema mismatches produce warn-only `warnings` on the
  response, exactly as `registry.ValidateInput` does — they never block a call. The success
  response is `CallResponse`
  (`{status, result, api_calls, warnings?}`) unconditionally: the shape must not depend on the
  input, or an agent that learned where `health.bp.list` puts its rows loses them on the one call
  that happened to trip a warning.
- **Write ops require `mode: 'write'` plus a non-empty `intent`.** Any catalog op with
  `risk: 'write'` is refused otherwise, with an error naming both fields so an agent
  self-corrects. This means an old shim calling `bp.create` with a bare `{op, params}` is now
  refused — intended, not a regression; reads are unaffected. The in-tab callers must state their
  intent too: `features/elevenlabs-call.js`'s voice tools (`log_blood_pressure`, `log_weight`,
  `add_note`, `log_exercise`, `set_workout_status`) send `mode: "write"` plus an intent, and its
  generic `mcp_call` forwards whatever `mode`/`intent` the agent stated rather than stripping
  them.
- **Write frames are deduped by GCM nonce.** The sender draws a fresh random nonce per frame, so
  a byte-identical nonce is always a replay (or a catastrophic sender bug). The responder keeps a
  bounded FIFO ring (4096 entries) of seen write-frame nonces, per pairing, persisted in
  `localdb.js`'s local-only never-synced `device` store — so a tab reload does not reopen the
  hole. A duplicate is answered with a JSON-RPC `-32600` rather than dropped silently, keeping
  id-correlation intact. The ring is keyed by `pairing_id`, and every `connectClaude` mints a new
  one, so `disconnectClaude`/`purgePairing` delete the ring alongside the vault record — otherwise
  each connect/disconnect cycle would strand one ring key forever (the FIFO cap bounds one ring's
  size, not how many rings exist). **Residual gaps**, all closed by the same durable fix (a counter
  bound into the frame AAD), deliberately left to future work:
  - Read frames are not deduped (a replayed read is idempotent).
  - A relay that floods distinct nonces can eventually evict and replay a very old write frame.
  - The ring is per-pairing **but also per-device** — `device` is a local-only store, never synced.
    An honest relay keeps one device leg per pairing, but a *malicious* one can answer a captured
    write frame on device A and then replay it to device B, whose ring has never seen that nonce.
    Single-device use (the common case) is fully protected; two simultaneously-unlocked devices are
    not. Sharing the ring through the oplog would replicate every nonce and is not worth it.
- **Every catalogued op is dispatchable, through the router the UI already uses** (med-csu.3).
  `createDispatcher({ router })` takes `apishim.js`'s `createApiRouter` — the same
  `(endpoint, method, body)` function `window.offlineAwareApiCall` is assigned to — and dispatches
  by *catalog coordinates*: the entry's `method` + `path` are exactly what the router is keyed by,
  so `mcp_call` is a `BY_ID` lookup, a path-param substitution, a querystring build, and one
  `router(...)` call. There is **no second dispatch table** to drift from the first, and no domain
  logic in the responder — an op that needs behavior `web/domain/*` lacks gets it added *there*,
  shared with the UI, never branched into `mcp-responder.js`. MCP and the cloud frontend are one
  code path, which is the JS-side statement of CLAUDE.md's domain-service rule.
  - Because dispatch routes by path, `apishim.js:678`'s unmapped-route `throw` doubles as the
    coverage assertion: a catalogued op the router cannot serve surfaces as a JSON-RPC `-32603`
    naming the missing `METHOD /path`. The sweep in `web/cloud/js/tests/mcp-responder.test.js`
    drives **all 110 ops** (68 of them writes, with payloads synthesized from each op's `required`)
    through the real router and fails naming any op that 404s. A companion test asserts the 48 ops
    carrying a `response_example` return that shape. Do not soften that 404 — it is load-bearing.
  - `food.log.from_description` (AI parse) and `food.products.search` (food DB) reach outside the
    vault. Both reuse C2c's **direct-from-browser** path (the same `foodAI`/`food` instances behind
    `CloudFoodAI`/`CloudFoodSearch`), never the relay — routing them through it would hand the
    server plaintext and break the property cloud mode exists to provide.
- **The honest constraint: a device must be online with an unlocked vault.** A phone with the PWA backgrounded is not reliably reachable (iOS SW execution on push is too constrained to serve queries silently). Realistic availability = a desktop tab left open, or an old phone plugged in at home with the PWA foregrounded — at which point the user has voluntarily re-invented a tiny server, but it's *their* device, zero config, and the guarantee holds. When no device is online, the shim's tools return an actionable MCP error naming the E2E architecture and telling the user to open and unlock their app.
- **PoC ceilings** (each `ponytail:`-marked in code): in-memory pairings, single pairing per
  account, no QR pairing, no packaged shim binary/release artifact.

**Tier 2 — hosted-relay convenience mode (explicit consent, reduced guarantee). PoC implemented**, see
`docs/plans/completed/2026-07-06-cloud-c4-poc-remote-mcp-endpoint.md`. claude.ai's remote MCP cannot run a shim, so the server runs the shim itself: it dials the relay on the account's behalf and exposes a plain streamable-HTTP MCP endpoint that hosted clients connect to directly. The server therefore terminates the client's MCP connection and sees requests/responses **in transit** (never stored); vault data at rest stays E2EE. This is a deliberate, per-account, clearly-labelled downgrade switch, off by default.

```
claude.ai / ChatGPT ──https── cloud server ──wss:// ciphertext ──► cloud relay ──► user's device (PWA)
                      (sees traffic in transit) (holds pairing key, at rest while enabled)
```

- **Connecting Claude Code, Claude (claude.ai / Claude Desktop) or ChatGPT**: Settings → Devices & connectors → "Claude connector" → **Connect an AI app** (bd med-73xx). A consent dialog spells out the downgrade (the server can read requests/answers while relaying; nothing is stored; the pairing key is kept server-side, at rest, until Disconnect). Confirming mints a pairing (same `mcp-pairing.js` as Tier 1) and POSTs the pairing code to `POST /api/mcp/remote`, which returns a one-time 6-character token (`xxx-xxx`, Crockford base32, shown once). The page then shows the same connector URL `https://<account-subdomain>/mcp/<token>` for every client, with per-client instructions behind a Claude Code / Claude app / ChatGPT switch: Claude Code gets a prompt to paste (`claude mcp add --transport http --scope user health <URL>`, then restart Claude Code) plus the bare command as the terminal fallback; Claude app (claude.ai and Claude Desktop): Settings → Connectors → Add custom connector, paste the URL; ChatGPT: Settings → Connectors → Add MCP, paste the URL. Keep an unlocked PWA tab open somewhere — that's what actually answers queries. The URL is stable across server restarts/deploys and changes only on Disconnect + re-enable (which rotates the token). Disconnect tears down the hosted client and the URL stops working immediately.
- **Auth is a capability URL, not OAuth.** The 6-char token (~30 bits) is short enough to type/paste reliably across devices; the real security boundary is a per-account failed-token throttle (100 failed attempts/min, then 429 backoff) rather than token entropy — brute-forcing the token space past that cap takes decades. Constant-time compare; wrong or revoked tokens 404 without revealing whether the account exists. Full OAuth 2.1 + dynamic client registration is out of scope for this PoC.
- **Mutually exclusive with Tier 1 per account** — the relay's PoC ceiling is one pairing per account, so enabling the remote connector disconnects a local shim pairing (and vice versa). The connector page states this inline. **The Tier 1 offer is hidden from the UI** pending a packaged shim (bd med-ztzg): an account already paired through the local shim keeps its status line, Disconnect, and "Connect an AI app instead"; nobody new is offered the build-it-yourself flow. The relay, `mcp-pairing.js` and `cmd/mcpshim` are unchanged.
- **Set-up-once-and-forget**: enablement is persisted (`internal/cloudstore` migration adding `mcp_remote`), so the token and connector URL survive process restarts — on startup the server re-registers each enabled account's pairing with the (in-memory) relay and restarts its hosted shim client. The honest cost of this convenience: the pairing key now sits at rest in the server DB while remote mode is enabled, not just in memory during a live relay session.
- **Token-in-path access-log caveat** (same shape as `initData` in [docs/sse-traefik.md](archive/sse-traefik.md#initdata-exposure-in-traefik-access-logs)): the token travels in the URL path (`/mcp/<token>`), so Traefik's default access log writes it to disk on every request. The leak is bounded by the same throttle that bounds guessing it, but treat Traefik logs as sensitive for this route and consider the same mitigations (drop query/path logging for `/mcp/*`, or a redaction filter) if that's a concern for your deployment.

## Appendix — how the domain layer got here (historical)

> **Implementation record, not current behavior.** This section and the Goja
> spike below explain *why* the browser domain layer is shaped the way it is.
> The work described is done; the design constraints it establishes (§1 and §3)
> are still enforced by tests. Nothing here is a roadmap commitment.

The domain layer was written in JS from an existing implementation, and the cost of that was the dominant cost of the whole design. Two structural decisions kept it tractable and stopped the result from rotting:

1. **Port behind the `/api/*` contract, keep the UI byte-identical.** The existing frontend already speaks only `/api/*`. Cloud mode inserts a fetch shim (SW or wrapper around `apiCall`) that routes `/api/*` to an in-browser router → JS domain services → Dexie stores. `web/static` feature code, the design system, offline plumbing, and all Vitest feature suites are shared verbatim with server mode. The fork is confined to a `web/static/js/localdomain/` layer; the HTTP contract becomes the enforced seam.
2. **Cross-implementation contract tests.** A shared fixture corpus (seed ops → API call sequence → expected JSON responses) runs in CI against both the Go server and the JS domain layer. A behavior change that lands in one implementation fails the other's contract run. This is the drift alarm that makes double maintenance survivable; without it, this proposal should be rejected.
3. **The JS layer is runtime-agnostic, and this is still enforced.** Domain services depend on injected ports — a storage port and a clock/timezone port — never on browser globals. `architecture.domain-purity.test.js` fails CI on a `window`/`document`/`fetch`/`indexedDB` reference in `web/domain/`. That constraint is what keeps the layer embeddable outside a browser at all; the goja spike below is the evidence that it works, and is the only place that possibility has been measured.

### Goja spike (med-07y.1) — measured findings

The C6 unification endgame only holds if goja can actually run the `web/domain/*.js` layer server-side. A throwaway spike (`internal/gojaspike/`) proved it can, with caveats. **This is spike evidence for a decision, not production wiring** — nothing here is on a request path. The spike package itself was deleted with the bot-mode removal (2026-09, epic med-a9n5); the measurements below are kept as historical evidence.

**What the spike is.** BP (`web/domain/bp.js`) and weight (`web/domain/weight.js`) run **unmodified** under goja (pure-Go JS engine, `CGO_ENABLED=0` intact), backed by a SQLite-backed records port, driven by deterministic parity tests (fixed clock, fixed tz `America/New_York`, in-memory SQLite) that assert value-exact equality against the native Go store — plus Go benchmarks.

**Measurement method.** Numbers below are `go test -bench` on Apple M4, darwin/arm64, `CGO_ENABLED=0`, in-memory SQLite, fixed clock/tz. Per-VM memory is `runtime.ReadMemStats` bracketing a GC + a 100-VM allocation batch — order-of-magnitude only, noisy (GC timing, allocator slack), not a precise per-VM figure.

| Benchmark | Result | Notes |
|---|---|---|
| `BenchmarkColdStart` | ~340 µs/op, 363 KB, 5019 allocs | fresh VM: runtime + Intl shim + module read/strip/eval + factory; source re-read each iter |
| `BenchmarkPerCallGoja` | ~38 µs/op, 15 KB, 252 allocs | reused/warm VM, one create |
| `BenchmarkPerCallNative` | ~17 µs/op, 720 B, 12 allocs | native `CreateReading` — goja ≈ **2.2× native latency** |
| `BenchmarkPerRequestVM` | ~382 µs/op | fresh VM + create ≈ **10× the warm per-call** — pooling matters |
| `BenchmarkVMMemory` | ~80 KB heap/VM | 100-VM batch, GC-bracketed; noisy, order-of-magnitude only |

**Proven.** Value-exact parity JS-via-goja vs `internal/store/{bp,weight}` for: BP category buckets, BP create/list (field-by-field: category, ordering, values, pulse/notes/tag/ignore_calc), BP daily-weighted stats (14/30/60), weight EWMA trend (alpha=0.1, bit-exact IEEE-754), and weight create/list. Promise execution is deterministic: every async call captures the returned `*goja.Promise`, drains microtasks, and asserts `Fulfilled` (fails on `Rejected`/`Pending`) — the synchronous records port settles the `await` chain within the top-level call as it unwinds.

**Not proven.** Only **2 of N** domains (BP, weight — the smallest, purest). ESM is handled by a leading-`export `-strip transform in the Go loader, **not** a real module loader — fine for these two files, unverified against imports/circular deps/more complex modules. goja has **no `Intl`**; the harness installs a minimal `time`-backed `Intl.DateTimeFormat.formatToParts` shim (same tz DB as the native store) so tz day-boundary math works — an environment shim, not a module change, but a real dependency the production embedding must also provide. Single-user, single fixed tz. **No concurrency test, no sustained GC-pressure test, no pooling implementation** — only the per-request-vs-warm gap was measured.

**Recommendation (input to C6, not a production decision).** goja is viable and preferred over a Node sidecar on this evidence: it runs the domain files unmodified and keeps `CGO_ENABLED=0` / single binary intact (a sidecar breaks both), and ~2.2× native per-call latency on a warm VM is acceptable for these compute-light domains. The load-bearing caveat is **VM lifecycle**: cold start (~340 µs) and per-request VMs (~10× warm) mean C6 needs a **pooled/reused-VM** design, not a VM per request — and pooling under real concurrency is exactly what this spike did **not** measure. Before committing goja for all domains, C6 should (a) port one *stateful, Intl-heavy* domain (meds/reminders) to expose loader/shim gaps, and (b) benchmark a real VM pool under concurrent load for latency tails and GC pressure. Sidecar stays the fallback only if those two reveal a blocker.

**Reusable idioms (for C6 — the spike proved these three, lift them rather than re-deriving).** All were in the deleted `internal/gojaspike/` package:
- **Promise-drain**: a synchronous port settles the `await` chain within the top-level `RunString`/`FunctionCall` as it unwinds, so the returned `*goja.Promise` is already `Fulfilled` when the Go call returns — no manual microtask pump. `awaitCall` (`harness.go`) captures the promise and switches on `State()` (`Fulfilled`→`Result()`, else error); it asserts `Fulfilled` rather than assuming it, failing loudly on `Rejected`/`Pending`.
- **ESM-strip loader**: goja has no ESM; `loadModule` (`harness.go`) strips only the leading `export ` (`^export `, multiline regex) on an in-memory copy so `createBPDomain`/`createWeightDomain` become globals — `web/domain/*.js` untouched. Cheap for these files; a real module loader is needed once modules `import` each other.
- **Records port + Intl shim**: `RecordsPort` (`port.go`) backs the `records.{list,put,del}` contract with a `records(type,id,data JSON)` table, each method returning an already-settled `vm.NewPromise` (DB/JSON errors → rejection, never dropped). `injectIntlShim` (`harness.go`) supplies the one `Intl.DateTimeFormat().formatToParts` primitive the domains need, backed by Go's `time` (same tz DB as the native store). C6's production embedding must provide both.

## No lock-in — full-vault export and import

A plain file on the user's disk is always an exit door. One canonical one-user-all-domains JSON format (meds + intake log, BP, weight, food, workouts, vitals, sleep, diary, tz history, settings) is both exportable and importable. Format spec: [vault-format.md](vault-format.md).

1. **Settings → Import/Export, no CLI.** Both directions run entirely client-side against the unlocked vault. The zero-knowledge property forces this: plaintext can never be uploaded, so data must enter through an unlocked client that encrypts it locally.
2. **Optional passphrase protection via age, in the browser.** The downloaded file is plaintext JSON, or — if the user supplies a passphrase — an [age](https://age-encryption.org) scrypt-recipient file (`.json.age`, decryptable anywhere with `age -d`). Encryption and decryption happen in the browser via a vendored single-file `typage` build; the server never sees the passphrase and performs no backup crypto. No custom crypto layer.
3. **Import flows through the domain layer, not raw writes.** Records enter via the same validation as live writes, so an import cannot create states the app could not. Bulk lands as **one snapshot, not an op flood** — `replaceAllRecords` + `forceSnapshot` posts a constant 2 requests regardless of vault size; reminder schedules recompute client-side afterwards.
4. **Round-trip is the contract.** Export → import → export must be identity, modulo id/timestamp normalization. A golden fixture pins it on both sides of the transform so the format cannot drift.
5. **Merge mode** (`importAll(json, {mode:'merge'})`, bd med-o7zq.38; rules in [vault-format.md](vault-format.md#record-identity-model)) takes the same mark → `replaceAllRecords` → `forceSnapshot` path, computing the merged set from the current rows inside `replaceAllRecords`' records lock (`replaceAllRecords(fn)`, so a write cannot land between the read and the clear), and keeps the receiver's pending ops (they are receiver rows, so they won the merge; a floored placeholder that yielded is dropped by the overlay). One exception: a receiver row the merge rewrites (a weight-adding merge rewalks every manual `weight_trend` over the merged history; a vitals day batch both sides hold gains the file's samples) has its pending op dropped under that same lock (the overlay would lay its old copy back); the forced snapshot carries those rows. Peers re-bootstrap from the snapshot exactly as after a replace: `replaceAllRecords` re-overlays their pending writes, which stay queued. Every row the file adds is stamped `clientTs = now` (the vault carries none), as on a replace; receiver rows keep theirs. So a peer's offline write to a deterministic id the file also adds (an intake slot, a `-hk-` row) loses LWW on other devices while the peer keeps its own copy until its next write — the same exposure a replace has today.
6. **Secrets are opt-out.** "Include API keys and external provider settings" is on by default. Off means `integrations` and `api_tokens` are **absent** from the file (not present-and-empty — the two are distinguishable), and on import absent means "leave the target's existing keys alone". With the W4 `protection` block (absent keeps the target's nudge state, bd med-ta2n.4) these are the only asymmetric paths in an otherwise pure-replace format, so a secrets-free backup cannot silently unconfigure the destination.

### C1 implementation notes

C1 shipped as **BP + weight through the real `web/static` frontend**, not medications as originally scoped below — a deliberate reorder (see `docs/plans/completed/2026-07-05-cloud-c1-bp-weight-real-frontend.md`) because BP/weight's domain logic (AHA category buckets, EMA trend, daily-weighted stats) is small, pure, and self-contained, making it the cheapest full vertical slice to prove the shim architecture end-to-end.

- **`web/domain/`**: runtime-agnostic ES modules (`bp.js`, `weight.js`) with injected ports (`records`, `now`, `timeZone`) — no `window`/`document`/`fetch`/`indexedDB`/`navigator`, enforced by `architecture.domain-purity.test.js`. This is the C6 portability seam: goja can host the same modules server-side later.
- **The shim (`web/cloud/js/apishim.js`)**: `installApiShim(ctx)` assigns `window.offlineAwareApiCall`, the single slot `web/static/js/core/api.js`'s `apiCall` already delegates through — no frontend call sites changed. A route table maps `/api/bp*` + `/api/weight*` to the domain modules; every other `/api/*` path either returns a stub (boot-path endpoints the frontend calls unconditionally — `/auth/status`, `/api/bootstrap`, reminder status, settings reads) or rejects with a console-warned "unknown route" — that warning list is the deliberate C2 scoping mechanism (see Post-Completion in the plan).
- **Record types** synced via the C0c oplog (`recordsPort(ctx)` = `{list, put, del}` over `sync.js`'s generic `writeRecord`/`listRecords`): `bp` (one per reading), `weight` (one per log), `bpgoal` (singleton, fixed recordId), `weightgoal` (append-only history, mirrors the `weight_goals` table).
- **Cloud boot path**: `cloud-boot.js` runs before `app.js`, sets `window.__MEDTRACKER_CLOUD__`, warm-unlocks via the LDK cache, installs the shim, and kicks `pullOnOpen`. `app.js`'s `checkAuth()` short-circuits on that flag (CLAUDE.md rule 11) — the Telegram login screen never renders in cloud mode. Repaint is optimistic-write + pull-then-`invalidateTags`; another device's write arrives through the `sync-ready` SSE wake (see [Sync protocol](#sync-protocol) → Cross-device wake).
- **Serving**: `cmd/cloud` now serves the full `web/static` app (embedded tree via `webstatic.FS`) on account subdomains; the unlock/claim/recovery shell moved to `/unlock` (`/claim`, `/recover` still rewrite to `signup.html`).
- **Contract test strategy**: no new unit tests. The existing BP/weight Vitest feature suites are re-run under a shim-mode harness (in-memory records port, no crypto/IndexedDB) as additive `cloud.shim-contract.*.test.js` files — a divergence there is a Go↔JS drift bug, not a gap needing new test scaffolding.

C2a shipped **diary/notes, settings (incl. the Integrations BYO-provider-keys screen), and the vitals read side** — the three cheapest remaining domains, following the C1 pattern exactly. Plan: `docs/plans/completed/2026-07-05-cloud-c2a-diary-settings-vitals.md`.

Same purity guard, same injected-port shape as `bp.js`/`weight.js`.
- **Record types**: `note` (one per entry), `settings`/`features`/`taborder`/`foodtargets`/`integrations` (singletons, fixed recordId — the C1 `weightunitpref` pattern), and the vitals streams — `sleep` (one per sleep day at `sleep-hk-<day>` since bd med-0xad.4, the projection of the legacy per-session rows, which stay live as its ledger, bd med-0xad.9), `daystats` (one per day), `hrsample`/`spo2sample` (`stresssample` until bd med-0xad.4, now deleted at boot) (**day-batched**: one record per stream-day, body `{day, samples: [{date_time, tz_offset, value[, info]}]}`, to keep a 90-day Mi-Band history from exploding the oplog into ~9k individual records). `web/domain/vitals.js` expands the batched arrays in-memory before bucketing/averaging.

#### Import self-heal (med-0ol.7) + the single-snapshot invariant (med-0ol.8)

A failed/interrupted bulk import must never chronically wedge a real account, and it must not re-download a bloated oplog on every open. Two follow-ups closed the gap.

**Already covered by #613** (batched flushes + permanent-vs-transient classification + bounded compaction + shared import-UX busy/beforeunload guard) stopped the *tight retry loop* and the over-cap 400 storm, but a permanently-failing write batch still sat in `pending` and was re-POSTed on **every open, forever** — no retry budget, no manual un-wedge. This PR adds both:

- **Write-error retry budget → `syncWedged` pause.** `sync.js` counts consecutive permanent (413/400, via `isPermanentSyncStatus`) write-error opens in a device-local `sync_meta.writeErrorStreak`; at `WRITE_ERROR_BUDGET = 3` it sets `sync_meta.syncWedged`. Once wedged, `flushPending` early-returns before the drain loop — writes still queue durably to `pending` (nothing is lost), the doomed batch just stops being re-posted. Only permanent 4xx increments the streak; transient failures (offline/5xx/429) never touch it, so a flaky network can't wedge a device. Any accepted batch resets the streak to 0. Both keys default-safe when absent (streak 0, not wedged), so older devices upgrade cleanly. `getSyncStatus()` surfaces `wedged`, and `describeSyncStatus()` adds a plain-text recovery hint when set.
- **"Reset local sync (rebuild from server)" affordance.** `resetLocalSync(ctx)` (`sync.js`, wrapped as `window.CloudVault.resetLocalSync` in `cloud-boot.js`, exposed in Settings → Import/Export as a cloud-only control) clears the `records`, `pending`, and `sync_meta` stores in **one atomic IDB transaction** under `withRecordsLock`, then `pullOnOpen` re-bootstraps this device from the server's compacted snapshot + tail. It **discards un-synced local pending writes by design** — the un-wedge escape hatch — and does **not** touch the `device` store (NK/LDK/crypto survive). Clearing `sync_meta` nulls `localLastSeq`/`syncWedged`/`writeError`/`forceSnapshotPending`, so the next bootstrap starts clean; a crash mid-reset leaves a null cursor the next bootstrap heals. It also cheaply escapes a bloated-oplog-every-open device (one snapshot pull, not a full oplog re-download). The Settings button confirms, runs under the shared `importInFlight`/`setImportBusy` re-entry guard so it can't collide with an in-flight import, then reloads.

**med-0ol.8 finding — no fix needed.** Full-vault (archive/json/gzip) `CloudVault.importAll` lands via `replaceAllRecords` (local, zero ops) + `forceSnapshot` → `tryForceSnapshot`, which posts exactly **1 bump op + 1 gzip'd snapshot** — a **constant 2 requests regardless of vault size**, not per-record ops, and it already carries the same shared `setImportBusy` UX safeguards as the `.nxk` import. A snapshot-path invariant test in `web/cloud/js/tests/sync.test.js` (1500 records → exactly one `/api/sync/ops` POST + one `/api/sync/snapshot` POST) pins this so a future regression to per-op writes fails CI.

It flattens them into one `exercises` array where each row carries `log_id` (0 when un-logged) + `exercise_id`, and `log_exercise` picks `logs.update` or `logs.create` off that — otherwise an update against an unknown id succeeds with an empty body and the agent reports a write that never happened. `log_exercise` re-reads before it writes, which is what lets it refuse a session `sessions.next` surfaced for a LATER day (logging into one would record the workout on the wrong date and propagate the numbers into that day's plan) and fall back to the planned targets when the agent says only “skip the rows”. `set_workout_status('in_progress')` routes to `workouts.sessions.start`, not `sessions.status`, so `started_at`/snooze/day-re-keying stay correct, and answers with the re-read workout because a start moves the ids; a terminal transition answers with the written status instead, since `sessions.next` excludes terminal sessions and would hand back an unrelated future workout. `mcp_help`/`mcp_call` are provisioned too (see Scope) — `mcp_call` accepts `params_json`/`path_params_json` strings and `JSON.parse`s them, since ElevenLabs client tools cannot declare nested objects. No MCP relay hop and no crypto for the tools themselves — the tab is both the voice client and the MCP responder host, online + unlocked during its own call. (The agent's LLM turns do pass through the server in transit; see the next bullets.)
- **LLM = the user's own AI, via the voice relay (bd med-h849).** The agent no longer uses ElevenLabs' built-in LLM: `prompt.llm` is `custom-llm` pointing at our server, and each call passes a per-call token through the SDK's `customLlmExtraBody` (`platform_settings.overrides.custom_llm_extra_body`), which ElevenLabs forwards verbatim as `elevenlabs_extra_body` on every LLM request. Server: `internal/cloudserver/voice_llm_relay.go`. `GET /api/voice-llm/device` (session-authenticated WebSocket) mints a random call token, sends it as the first frame `{"type":"hello","call":"<token>"}`, and accepts re-attach with `?call=<token>` within a 30 s grace (`voiceCallGrace`). `POST /api/voice-llm/chat/completions` has no session: the call token is the capability (an unknown/expired token gets HTTP 200 with the spoken fallback "I lost the connection to your app — please hang up and call again." then `[DONE]`; misses count against the 60/min per-IP limiter, which answers 429; body capped at 2 MiB; served on the account subdomain and on the base domain for the one fixed trial-agent URL). The handler strips `elevenlabs_extra_body`, sends `{"id","type":"request","body"}` to the device socket, and streams the device's `chunk` frames to ElevenLabs verbatim as SSE until `end`/`error`; a dropped HTTP request (barge-in) sends `cancel`; a transient failure on a live call (no device within the wait, a device `error` frame, the turn timeout) yields one spoken "Sorry, I didn't catch that — could you say it again?" chunk then `[DONE]` — the hang-up sentence is only for an unknown/expired call; a leg that drops before anything was written gets the request re-sent once on the leg the browser redials, and the browser retries a transient (429/5xx/network) provider failure once before the first chunk (med-h849.11). It is never stored, and the only log line per turn (`voice llm relay: turn`) carries account, a call fingerprint, byte counts, duration, `ttfc_ms` (time to the first chunk written to ElevenLabs, -1 if none) and outcome. The user's AI key never leaves the browser. Disclosed as the `voice-llm-relay` row of the privacy table above.

### Voice relay abuse bounds (bd med-93u1)

`POST /api/voice-llm/chat/completions` has no session, so here is what stops someone from using it as a free LLM. Constants are in `internal/cloudserver/voice_llm_relay.go` unless another file is named.

- **Who can call it.** Only a holder of a live call token. A token is 24 bytes from `crypto/rand` (`voiceCallTokenBytes`), so guessing it is not feasible.
  - An **authenticated account token** is minted by the session-authenticated device leg and expires exactly four hours after that first attach, whether its AI uses an own key or account trial. Reconnects, replacements, activity and turns do not renew it. Detach grace remains 30 s, capped by the absolute deadline; it may end the call sooner. The user must start a fresh call for a new token.
  - An **anonymous token** is minted only by the attested `POST /api/attest/voice/start`. It must attach within 60 s and dies when its minute grant runs out.
  - Unknown tokens count against `voiceBadCallMax`, 60 misses/min per client IP. Real turns come from ElevenLabs' egress IPs, so that bucket is shared and is sized for a post-restart burst of orphaned calls.
  - **Hop secret, anonymous calls only (bd med-k80h).** With `TRIAL_VOICE_RELAY_SECRET` set, a POST for an anonymous token must also carry `X-Voice-Relay-Secret` with that value (compared in constant time). The shared trial agent sends it from `custom_llm.request_headers`, written by `pnpm trial:agent --apply`. A missing or wrong header is treated exactly as an unknown token: it counts against `voiceBadCallMax`, gets the spoken hang-up sentence, and logs `voice llm relay: anon hop secret mismatch` with `has_header` (never the value). So the attested client, which holds its anonymous token, can no longer drive the trial model by curl. **Own-key calls never read the header.** Their turns go to the token owner's own tab and spend that user's own key or account-trial quota, and every party that can see the token (the tab, ElevenLabs, the relay) already sees the plaintext turn. BYO agents are provisioned in the browser and get no header. Unset means the anonymous hop is unauthenticated, as before, with one startup Warn `voice llm relay: anon hop unauthenticated, TRIAL_VOICE_RELAY_SECRET unset` when trial voice is configured.
- **Per call.** Every known token is held to `voiceCallTurnsPerMin`, which is 60 turns/min, the same as the trial stream limiter. This applies on both paths. Over the limit, the turn gets the spoken retry sentence with HTTP 200 and never reaches the device or the trial key. The body is capped at 2 MiB, and device frames at 1 MiB.
- **Anonymous turns (trial key)** run four checks:
  1. the call's minute grant, charged up front: `TRIAL_ANON_VOICE_*` lifetime, per install per day, **global per day** (default 7200 s), and per call;
  2. the per-bucket stream limiter, 60/min;
  3. a **global** in-memory ceiling `voiceAnonTurnsPerMin`, 600/min across all calls;
  4. output ≤ 1024 tokens (`clampMaxTokens`).
  
  The model is forced, `n` and `user` are dropped, and `stream` is forced. Anonymous turns are not counted in `TRIAL_DAILY_GLOBAL`; the seconds budget and the global turn rate bound them instead.
- **Account trial voice** (a call with no AI key, through `/api/trial/openai/chat/completions` with `stream:true`) is counted in the per-account and global daily request budgets. On the OpenAI-compatible provider its output is clamped to the same 1024 tokens. The Anthropic adapter already forces its own `max_tokens`.
- **Trial keys never leave the server.** They are sent only as upstream request headers and never logged. The upstream `model` is stripped from every chunk and response, and upstream errors are sanitized (`trial_proxy.go`, `trial_stream.go`).
- **Observability.** Every limiter refusal logs at Warn under a fixed message, so a spike is easy to grep:
  - `voice llm relay: unknown call rate limited`, with no IP;
  - `voice llm relay: call turn rate limited`;
  - `voice llm relay: turn … outcome=rate_limited|global_rate_limited`.

  Turns are logged at Info with sizes and outcome only, never content.
- **Known limits (follow-ups, not closed here).**
  - On an own-key call nothing proves a POST came from ElevenLabs, so a token holder can send any prompt. It costs the token's owner, not the operator. Without `TRIAL_VOICE_RELAY_SECRET` the same holds for anonymous calls: the attested client holds its token and can drive the trial model directly for its granted minutes, within the bounds above.
  - The four-hour account-token deadline retires the relay capability, cancels relay work and closes a healthy writable device leg with the existing 4404 code. A completion after expiry gets the existing localized instruction to hang up and call again (subject to the unchanged unknown-token miss limiter). A partially streamed answer receives only terminal framing/[DONE], never an appended retry or hang-up sentence. Logical expiry stops new admission, re-sends and queued model forwarding; a write already admitted while live may finish under its existing finite transport bound, followed by one terminal HTTP cleanup allowance of 10 s. Socket write deadlines are separate from capability expiry, so terminal cleanup can finish; a genuinely broken peer can still prevent delivery. This does not proactively speak or immediately disconnect ElevenLabs audio, and is not a connected-audio billing guarantee; output or provider work already sent before cutoff cannot be retracted. Anonymous grant limits remain separate and shorter.
  - Anonymous payload fields other than the ones above are forwarded as sent, and the anonymous body cap is the shared 2 MiB.

  - **Inbound (implemented, med-76c.2)** — inline Confirm/Snooze buttons plus the sealed inbound mailbox, in two parts. Part 1 (PR #511) shipped the `mt/v1/inbox` sealed box, `accounts.inbox_public_key` + `inbox_events`, the `PUT/GET/DELETE /api/inbox*` endpoints and the `SealAndQueue` write seam. Part 2 added `tgclient` `CallbackQuery`/`answerCallbackQuery`/inline keyboards, the `callback_query` branch in `ChildWebhook`, a per-entry `tg_callback` stem on the queue (migration `013_push_tg_callback.sql`), and the client drain. The drain protocol is implemented as specified above:
    1. **Ack after flush** — `drainInbox` awaits `sync.js flushConfirmed(ctx)` and only then `DELETE`s the event. An unconfirmed flush leaves it queued.
    2. **Idempotent re-apply** — a Confirm targets the deterministic `intake-<medId>-<slotUnix>` ids at that slot; a re-drain finds them already `TAKEN` and the domain's `not_pending` guard (swallowed by `inbox-apply.js`) prevents a second inventory decrement. Whether to act is decided by the domain's own resolver (`intake.getIntake`), so an id `confirm()` cannot resolve is **out of date**, never a swallowed `not_pending`. `not_pending` counts as already applied only when the dose IS `TAKEN`/`SKIPPED` at that id; on a dose still open it propagates and the event stays queued. The receipt reads the vault after the writes (bd med-944k): a tap that records nothing still edits the message — "Already taken" only for a dose already `TAKEN`, "Not recorded: marked skipped in the app" for `SKIPPED`, "Not recorded: changed in the app after this tap" for a tap older than the dose's last action (rule 4 of the intake merge above) — and only a redelivery of a tap that already landed whole leaves the message alone. The relay's static "waiting for your device" is never left over a dose still due.
    3. **Concurrent drainers** — the mailbox `DELETE` is per-event and account-scoped, so the first ack wins and a second is a no-op; a losing drainer's `confirm()` raises `not_pending`, which converges.
    4. **Sealed-timestamp order** — events are sorted by the sealed `at_unix` (not mailbox arrival order) and records are backdated to it, so a Confirm tapped at 09:00 records `taken_at` 09:00 even when the app first opens at noon. What `at_unix` *is* depends on the kind (bd med-3hr): a **callback-query tap** (`intake_slot_action`, `workout_session_action`, `measure_reminder_action`) carries the relay's clock at tap time — the message it hangs off is the bot's own reminder, so it has no useful date of its own — while an inbound **message** (`tg_command`, `tg_photo`, `tg_text`) carries the message's own Telegram `date` (`tgclient.Message.AtUnix`), falling back to the relay clock only when Telegram omits it or it is more than 5 minutes in the future. Old dates are never clamped: a webhook retried after relay downtime must still record a `/bp` at the minute it was sent, not at the minute the relay came back.
    5. **Identity on the row, cancel at the tap** (med-kbpf) — the schedule PUT carries `tg_med_ids` (the medication record ids the message names) beside `tg_text`; the relay stores it, copies it down the re-fire chain, and seals it into the tap event. A Confirm therefore **cancels the slot's re-fire chain server-side at tap time**, the drain confirms exactly the named meds (deterministic id first, that med's `minDoseInterval` band as the drift fallback), and only re-arms one re-fire (`POST /api/telegram/rearm-refire`) if a named med is still due after it applies. An in-app confirm still cancels via `POST /api/telegram/cancel-refire` — which since med-r3dm accepts every reminder stem (`s:`/`w:`/`bp:`/`wt:`, validated by `tgclient.ValidCallbackStem`) and also **deletes the message still live in the chat**, so an in-app workout complete/skip/start no longer leaves its reminder sitting there with buttons (migration `023_push_tg_message_id.sql` records the sent message id; the in-app workout call sites are wired in `apishim.js`, and since med-9bmb so are the BP/weight write routes, which rebuild today's `bp:`/`wt:` slot stem from the reminder pref). The sent row keeps `tg_callback`/`tg_med_ids`/`tg_message_id` (`MarkPushSent` scrubs only `ct`/`tg_text`) and the relay's hourly sweep expires them 48h later (`ScrubSentPushIdentity`, the same window the retired `slotmeds` records used), so a tap on last night's message still resolves this morning. A tap carrying no ids (pre-med-kbpf reminder, or one older than that window) applies nothing and answers the message rather than guessing from a time band. Privacy: the relay learns opaque numeric ids per slot — strictly less than the medication NAMES `tg_text` already hands it at `detailed` verbosity. Migration `022_push_med_ids.sql`.

    A tap on an account that has never unlocked a client has no inbox key to seal to; it is **dropped**, never stored readable, and the user is told to open the app once. Free-text commands (`/bp 120/80`, `/food two eggs`) ride the same mailbox and remain future work (med-vcv, med-eas.29).
